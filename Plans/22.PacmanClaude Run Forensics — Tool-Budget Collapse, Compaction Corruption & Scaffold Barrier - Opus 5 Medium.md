# PacmanClaude Run Forensics & Remediation

Run: `outputs/pacmanclaude-2026-08-16T15-57-15-320Z` · Repo: `ErezSCE/PacmanClaude` · PR: [#1](https://github.com/ErezSCE/PacmanClaude/pull/1)

Fix the nine defects that turned a 15-branch greenfield run into a 38-minute, single-branch, 2.3-million-input-token grind that produced one unmergeable PR: a tool budget that collapses under Anthropic's parallel tool calls, a history compactor that writes its own elision placeholder into source files, a respawn handoff that starts every generation blind, a scaffold barrier that never fires, an integrity gate that deletes legitimate Playwright specs, and zero prompt caching.

---

## 0. First: two premises in the bug report are wrong

Before the defect list, two corrections — both verified against the GitHub API.

**"The first dev agent wrote code but didn't open a PR; a different dev agent opened PR #1."**
There is only **one** branch and **one** PR. `PR #1` head is `pacmanclaude/chore/scaffold`, base `project/pacmanclaude`:

```
gh api repos/ErezSCE/PacmanClaude/pulls?state=all
→ 1 | [pacmanclaude] refactor: Create and modify the Vite PWA scaffold … | head=pacmanclaude/chore/scaffold base=project/pacmanclaude
gh api repos/ErezSCE/PacmanClaude/branches
→ main, pacmanclaude/chore/scaffold, project/pacmanclaude
```

What you observed is the designed branch-grouped fan-out: `pacmanclaude/chore/scaffold` carried **4 assignments** dispatched to 3 different agents (`principal-frontend`, `senior-frontend`, `junior-react`, then `principal-frontend` again). Each agent's work is pushed as a *durable commit* the moment it finishes (`run.txt:16:05`, commit `81b45d58`), but `createPullRequest` only runs after **all** assignments on the branch complete and quality gates have been attempted (`run.txt:1410`, 16:32). So the branch has code for ~27 minutes before a PR exists.

That is not a bug, but it *is* an observability defect (**D9** below): a pushed branch with no PR and no run event is indistinguishable from a crash. Nothing in the log or the dashboard says "branch pushed, 3 of 4 assignments done, PR pending".

**"The log shows the run failing / stopping."**
`run.txt` ends mid-sentence at `16:35:29` during review iteration 1. But the git history contains commits from **iterations 2, 3 and 4**:

```
ebbdab5b  fix: address principal-frontend review (iteration 4)
20f82520  fix: address principal-frontend review (iteration 3)
78dec97f  fix: address review comments (no-progress retry, iteration 2)
```

So the run continued past the end of the log. `run.txt` is a **partial snapshot copied while the run was still in flight**, not a crash dump. All conclusions below are drawn from what the snapshot plus git plus the full-response dumps prove; nothing is inferred from the log's abrupt end.

## 2. Sub-plan A — Denominate the tool budget in turns and categories (D1)

### A1. Actually use the per-category budgets

`src/agents/_shared/agent-factory.ts:144`

```diff
-const { tools: guardedTools, isCeilingReached } = withLoopGuard(cfg.tools, cfg.id, cfg.maxToolCalls);
+const { tools: guardedTools, isCeilingReached } = withLoopGuard(cfg.tools, cfg.id, cfg.toolBudgets ?? cfg.maxToolCalls);
```

Add `toolBudgets?: ToolBudgets` to `AgentConfig`. `dev-agent.builder.ts` sets it from `resolveToolBudgets(entry.rank, TOOL_BUDGETS_JSON)` — the function that already exists at `tool-loop-guard.ts:70` and has never been called. Keep `maxToolCalls` for pipeline/reviewer agents so nothing else changes shape.

This alone fixes the D1 → D3 chain: a read-exhausted agent can **still write**. Under the current flat ceiling it cannot, which is precisely why dumps 007/009/021 wrote nothing.

Retune the defaults for parallel-tool-call models (`tool-loop-guard.ts:60`):

| rank | reads | writes | shell |
|------|------:|-------:|------:|
| principal | 30 → **60** | 25 → **30** | 10 → **14** |
| senior | 25 → **50** | 20 → **25** | 8 → **12** |
| junior | 20 → **40** | 15 → **20** | 8 → **12** |

Reads are the cheap, batched category; writes are what we actually need to survive. Add `TOOL_BUDGETS_JSON` to `config.ts` + `.env.example` so this is tunable without a redeploy.

### A2. Add a turn ceiling alongside the call ceiling

The real invariant an agent needs is "how many more times can I *think*", not "how many tool invocations remain". Add to `LoopGuardOptions`:

- `maxTurns` (default `28` principal / `24` senior / `20` junior). Increment a turn counter when a wrapped tool fires with a *new* `runId` (available from the tool `config` argument), i.e. once per model turn regardless of parallel fan-out.
- Exhaustion = `turnsUsed >= maxTurns` **OR** all three categories exhausted **OR** `hardCeiling`.

This makes budget behaviour identical for a model that calls one tool per turn and one that calls eleven.

### A3. Make budget pressure visible *before* it is terminal

Currently the agent learns about its budget only when a tool returns `BUDGET EXHAUSTED` — by then it has no calls left to write anything. Change the wrapper to append a one-line footer to **every** tool result once usage crosses 60 %:

```
[BUDGET: reads 38/60, writes 2/30, turns 17/28 — start writing files now]
```

and at 85 % switch to `[BUDGET CRITICAL: … — write your files and return JSON on your next turn]`. Cost: ~20 tokens per tool result; benefit: the agent gets to *plan* its landing instead of crashing into the ceiling.

### A4. Stop the post-exhaustion spin

After `allExhausted`, `run.txt:1620-1637` shows 7 more tool calls and 3 more ~10 k-token LLM turns before the loop ends. `isExhausted()` returns the guidance string but nothing forces termination; `DEV_RECURSION_LIMIT=140` permits ~100 more turns of this.

Add a `forcedTerminationAfter` counter to the guard: once `allExhausted` has been reported `MAX_POST_EXHAUSTION_CALLS` (default `2`) times, **throw** a typed `ToolBudgetExhaustedError`. `invokeDevAgent` catches it, treats the partial state as the generation result (commits are already durable via `commitWorktree`), and proceeds. Wasted turns drop from ~4 to ~1 per generation.

## 3. Sub-plan B — Make compaction incapable of corrupting files (D2, D8)

### B1. Reject elision placeholders at the write boundary (defence that cannot be bypassed)

`src/tools/fs/workspace-tools.ts` — in `write_file` and `edit_file`, before touching disk:

```ts
const ELISION_RE = /^\s*(\[\d[\d,]* chars elided\]|⟪[^⟫]*elided[^⟫]*⟫)\s*$/;
if (ELISION_RE.test(content)) {
    return JSON.stringify({ error:
        'REJECTED: the content you passed is an orchestrator elision placeholder, not file content. ' +
        'That marker means "this text was removed from your history to save tokens" — the real file is ' +
        'already on disk. If you need it, read_file it. If this is a new file, write the actual code.' });
}
```

Also reject content shorter than 24 chars for a `.ts`/`.tsx`/`.js`/`.py`/`.go`/`.java`/`.cs` path unless it is an explicit re-export stub. This is the load-bearing fix: it holds regardless of how the model is prompted.

### B2. Make the placeholder unmistakable and non-copyable

`history-compactor.ts:101` and `:118`

```diff
-result[key] = `[${value.length} chars elided]`;
+result[key] = `⟪ORCHESTRATOR-ELIDED ${value.length} chars — file already on disk; NEVER copy this marker⟫`;
```

Same treatment for `stubToolContent`. Two properties matter: the marker must not look like plausible source text, and it must carry its own instruction.

### B3. Never elide the *most recent* write args

Extend the recent-window rule: an `AIMessage` whose `tool_calls` include a write is exempt from `elideBigArgs` if it falls in the last `HISTORY_KEEP_RECENT_WRITE_ARGS` (default `2`) write turns. The model needs to see its last couple of writes verbatim to diff against them, and this is exactly the window where the imitation happened.

### B4. Make `keepRecent` turn-aware, not tool-result-aware (D8)

`compactHistory` currently walks back counting `ToolMessage`s. With 11-way parallel calls that boundary lands *inside* the current turn.

Change the boundary computation to count **AI turns with tool calls** (new `HISTORY_KEEP_RECENT_TURNS`, default `3`), then extend the boundary to the start of the oldest kept turn so every kept turn's results are complete. Keep `HISTORY_KEEP_RECENT_TOOL_RESULTS` as a floor. Add a unit test with an 11-parallel-call turn asserting no result from the last 3 turns is stubbed.

## 4. Sub-plan C — Make respawn a real handoff (D3)

### C1. Pass the worktree so verification actually runs

`src/conductor/pr-workflow.ts:512`

```diff
-handoff = buildHandoff(result.messages ?? [], gen + 1);
+handoff = buildHandoff(result.messages ?? [], gen + 1, worktreeWorkspace, baseRef);
```

`buildHandoff` has accepted `worktreeDir`/`baseBranch` since Sub-Plan 08 and this is the only caller. Today `worktreeVerified` is always `false`, byte sizes are always absent, and `filesWritten` is the agent's *claim* — which is why the progress gate at `:516` terminated generations that had, in fact, left plenty of committed work behind.

### C2. Carry forward what the successor would otherwise re-read

Add to `HandoffSummary` / `renderHandoff`:

- **`filesRead: string[]`** — every `read_file`/`list_dir`/`search_code` target from the previous generation, rendered as *"Already inspected (do not re-read unless you intend to change them)"*. Dumps 019/020/021 each re-read the same 24 files; this is the single largest avoidable token sink in the respawn path.
- **`treeSnapshot`** — `git ls-files` of the worktree, capped at 200 entries. Cheap, deterministic, removes the reconnaissance phase entirely.
- **`budgetSpent`** — `reads/writes/turns` used by the previous generation, so the successor knows reconnaissance is already paid for.

### C3. Fix the progress gate's definition of progress

`pr-workflow.ts:516` terminates when `handoff.filesWritten.length === 0`. With C1 that becomes worktree ground truth — but it should also count `run_command` progress. Replace with:

```ts
const madeProgress = handoff.filesWritten.length > 0
    || handoff.commandsRun.some(c => c.exitCode === 0 && /test|build|tsc|lint/.test(c.command));
```

A generation that got the build green without writing files has made progress. Cap consecutive zero-write generations at 1 (currently unbounded until `AGENT_RESPAWN_MAX_GENERATIONS=4`, which is how `junior-react` burned 4 respawns and 882 k input tokens).

### C4. Reconcile the fix path like the PR path

The `Fixing N review comments` path reports the agent's claimed `fileChanges` verbatim (`Fix complete: 3 changes` for a generation with zero `write_file` calls). Run the same `reconcileFileChanges` used at PR creation, and log/record `phantom` entries so the review loop cannot be satisfied by a hallucinated fix.

## 5. Sub-plan D — Anthropic prompt caching (D6)

### D1. Cache the stable prefix

`src/agents/_shared/llm-provider.ts`, Anthropic branch. `@langchain/anthropic@1.5.4` + `@anthropic-ai/sdk@0.115.0` support `cache_control` breakpoints. Place up to the allowed 4:

1. end of the **system prompt** (persona + conventions digest + injected JSON schema — identical for every call to an agent id);
2. end of the **tool definitions** block;
3. end of the **first user message** (the task/context prompt — identical across every turn of an invocation);
4. a rolling breakpoint after the last stubbed history group.

Gate behind `ANTHROPIC_PROMPT_CACHE_ENABLED` (default `true`).

### D2. Prove it, don't assume it

`TokenUsageCallbackHandler` already receives `usage_metadata.input_token_details.{cache_read,cache_creation}` — it is currently discarded. Persist both into `TokenCallRecord`, surface `cacheHitRate` and `cachedInputTokens` in `token-report.ts`, and add a **run-level assertion**: if `SANITY_ASSERT_CACHE=true` and after 20 Anthropic calls the aggregate `cache_read` is still 0, log an `ERROR`. Silent cache misses are exactly the failure mode that produced this run's 23:1 input/output ratio.

Expected effect on the measured workload: `principal-frontend` 863 k input tokens → ~250 k billed (≈ 90 % of each call's input is the stable prefix), i.e. roughly $5.04 → $1.60 for that agent alone.

### D3. Forward the timeout

`createChatModel` ignores `opts.timeout` for Anthropic and Google. Pass `{ clientOptions: { timeout: opts.timeout } }` for Anthropic and `{ timeout }` for Google so `LLM_REQUEST_TIMEOUT_MS` is not silently Anthropic-exempt.

## 6. Sub-plan E — Finish the streaming sanitiser (D7)

### E1. Also drop argument-less `tool_use` blocks

`sanitizeStreamingContentBlocks` keeps `tool_use` blocks that have an `id` but `input: ""` (verified in every Anthropic dump: `{"type":"tool_use","id":"toolu_…","name":"read_file","input":""}` followed by a separate `input_json_delta`). The model's own history therefore shows argument-less tool calls.

Extend the filter: drop a `tool_use`/`server_tool_use` block when its `id` is missing/empty **or** its `input` is `""`/`undefined` **and** a matching `tool_calls` entry exists (the adapter re-materialises it from `tool_calls`, verified in Plan 21 §A2). If no matching `tool_calls` entry exists, rebuild `input` from the sibling `input_json_delta` blocks before dropping them.

### E2. Sanitise once, at the state boundary

The monotonic `dropped 2 … 31` sequence proves we re-scan the same residue every turn. Add an `afterModel` middleware hook that normalises the freshly-returned `AIMessageChunk` into a clean `AIMessage` (text blocks + `tool_calls`, no deltas) **before** it is persisted. Keep `wrapModelCall` sanitisation as the checkpoint-resume safety net, but demote its log line to `debug` when `blocksDropped === 0` at the state level.

Success criterion: the `dropped N` counter stops growing monotonically within an invocation.

## 7. Sub-plan F — Scaffold barrier & integrity gate (D4, D5)

### F1. Recognise the scaffold branch

`src/agents/developers/dispatcher.ts:138`

```diff
-function isScaffoldAssignment(a: Assignment): boolean {
-    return a.taskType === 'chore' || /\/chore\/scaffold$/i.test(a.branchName ?? '');
-}
+function isScaffoldAssignment(a: Assignment): boolean {
+    return a.taskType === 'chore' || /(^|\/)chore\/scaffold$/i.test(a.branchName ?? '');
+}
```

and classify by branch name, not by unanimity of assignment metadata (`:329`):

```diff
-const scaffoldBranches = branchesToProcess.filter(branch => {
-    const branchAssignments = branchGroups.get(branch) ?? [];
-    return branchAssignments.every(isScaffoldAssignment);
-});
+const scaffoldBranches = branchesToProcess.filter(branch =>
+    /(^|\/)chore\/scaffold$/i.test(branch)
+    || (branchGroups.get(branch) ?? []).some(isScaffoldAssignment));
```

Then log the classification unconditionally — `Scaffold barrier: 1 scaffold branch, 14 feature branches (parallel=N, serialised chains=M)` — so a mis-classification is visible in one grep instead of being inferred from an absent line. Add a unit test with a Team-Leader `branchName` of `chore/scaffold` (no project prefix), which is what actually happened.

### F2. Exempt e2e/browser specs from `no-product-import`

`src/conductor/gate-integrity.ts:664`. A Playwright/Cypress spec that drives a browser imports nothing from the product tree **by construction**. Skip the `no-product-import` and `subject-not-in-product` rules when any of:

- path matches `**/e2e/**`, `**/*.e2e.spec.*`, `**/*.pw.spec.*`, `cypress/**`;
- the file imports `@playwright/test`, `playwright`, `cypress`, `@cucumber/*`, `selenium-webdriver`;
- the file references `page.goto(` / `browser.` / `cy.visit(`.

Instead apply a browser-test-specific triviality rule: flag a spec with **no** `expect(`/`assert` call, or one that only asserts on literals.

### F3. Never delete on a `no-product-import` finding

`pr-workflow.ts:1023-1032` unlinks any `trivial-test-added` file and pushes the deletion. Deleting source is not a proportionate response to a heuristic import-graph miss — and here it directly manufactured the `[MAJOR] No test files exist` review comment.

- Split severity: `tautological-assertion` and `single-arithmetic-test` stay `critical` and remain deletable (they are unambiguous gaming of the gate). `no-product-import` and `subject-not-in-product` become `major` and are **reported only**.
- Add `GATE_INTEGRITY_DELETE_TRIVIAL_TESTS` (default `false`). When false, findings are recorded as review comments so the *author* fixes them.
- Whatever the mode, write the deleted bodies to `outputs/<run>/deleted-tests/` before unlinking, so a false positive is recoverable.

### G3. Tell the world a branch is pushed but not yet PR'd

Emit `branch:pushed` (branch, commit, assignments done / total) after each durable commit+push, and `branch:pr-pending` when the last assignment finishes and gates start. Log both at `info`. This closes the 27-minute observability hole that prompted this investigation.

### G4. Keep pipeline artifacts in the repo but out of the review

`docs/agents/*-mission.md` and `.agent/repo-contract.json` are committed to the generated project (6 of the 13 branch commits were `chore: pipeline artifacts`). Rather than moving them out of the repo entirely, keep them in `docs/agents/` so they are available to agents during the run, and instruct reviewers to skip `docs/agents/*.md` files. Add `AGENT_ARTIFACTS_IN_REPO` (default `true`): when true, mission reports go to `docs/agents/` in the product repo and reviewers are told to ignore them; when false, they redirect to `outputs/<run>/agents/` and `docs/agents/` + `.agent/` are added to the managed gitignore block. This preserves the docs for cross-agent reference while eliminating reviewer noise.

## 11. Open question for the user — planner model tier

The measured root cause of the 15-branch, 20-collision, fully-serialised plan is the plan itself. `team-leader` and `product-manager` ran on `gpt-5.4-mini` (~$0.10 total for both) and produced 15 branches for 22 assignments with 20 pairwise module-ownership collisions, which then cost **$7.6 per branch** to execute serially. Spending $1–2 on a stronger planner to produce 5–6 well-separated branches is very likely the highest-leverage change available — larger than any code fix in this plan.

This is a configuration decision, not a code defect, so it is **not** included in the sub-plans above. If you want it addressed I would additionally propose:

- raise `PRODUCT_MANAGER_MODEL` / `TEAM_LEADER_MODEL` to `claude-sonnet-5` or better;
- add a hard `MAX_BRANCHES` constraint to the Team Leader prompt (the dispatcher already warns at `> 8` — the planner never sees that threshold);
- add a post-plan repair pass that merges branches sharing a `moduleId`, reusing the existing `plan-coverage` repair loop.

Please confirm before I include it.

## 13. Risks & trade-offs

- **Raising read budgets raises cost per generation.** Mitigated by D (caching), by A3 (the agent now steers itself), and by C2 (successors stop re-reading). If the ratio does not improve on the integration re-run, lower `maxTurns` rather than the read budget — turns are what cost money, calls are not.
- **B1 could reject a legitimate tiny file.** The regex is anchored and requires the exact elision shape; the short-file rule applies only to source extensions and is bypassable by a two-line file. Worst case the agent gets one rejection and retries with real content — strictly better than writing a placeholder.
- **Prompt caching has a 5-minute TTL and a write surcharge.** Anthropic charges 1.25× on cache writes. Our turns are 3–10 s apart within an invocation, so hits should dominate; if D2's assertion shows otherwise, the flag turns it off with no code change.
- **F3 makes the integrity gate less aggressive.** A model that games the gate with import-free tests would now be caught at review rather than deleted automatically. Acceptable: the current behaviour destroyed 4 legitimate e2e specs and produced zero true positives in this run.
- **A2's turn counting depends on `runId` being present in the tool `config`.** Verify against `langchain@1.5.5` before relying on it; fall back to "any call that arrives after a gap in which the model was invoked" if the id is unavailable.
- **The scaffold-barrier fix changes execution order for existing runs.** Feature branches will now genuinely wait for the scaffold merge, making the run *more* serial but *far* less conflict-prone. Combined with §11's branch-count reduction this is net-positive; on its own it may lengthen wall-clock.
