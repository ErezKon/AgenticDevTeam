## 3. Token economics — will Plan 22 be enough, and what else is there?

### 3.1 What Plan 22 buys, quantified against this run

| Lever | Mechanism | Measured effect on this run's 39.74M input |
|---|---|---|
| Turn ceiling (A2) + forced termination (A4) | 28/24/20 turns per rank instead of a flat 26-call ceiling followed by an unbounded spin to `DEV_RECURSION_LIMIT=140` | Capping each invocation's calls at 28 retains **22.78M (57.3%)** → **−43% raw input**. At cap 20: 17.86M (44.9%). 24 invocations exceeded 40 calls. |
| Category budgets (A1) | Read exhaustion no longer blocks writes | Removes the 15 zero-write generations that were pure loss (each 0.3–1.0M input) |
| Respawn handoff (C1–C3) | `filesRead` + tree snapshot; zero-write generations capped at 1 | Removes the re-reconnaissance in the ≥3rd generation of every branch |
| Prompt cache (D1) | `cache_read` billed at 0.1× | Applies to whatever fraction of the prefix is byte-stable — **see 3.2, this is not automatic** |

Combined, Plan 22 should land this workload around **8–11M billed-equivalent input tokens (≈$25–35)** *if* the cache actually hits. That is the right order of magnitude, but three things stop it from getting there, and they are the content of Sub-Plan C.

### 3.2 Gap 1 — the cache prefix is not byte-stable under compaction (highest-value item in this plan)

`compactHistory()` runs inside `wrapModelCall` on **every** turn (`agent-factory.ts:189`), and `withMessageCacheBreakpoints` then places a rolling breakpoint at `findTurnBoundary(messages, HISTORY_KEEP_RECENT_TURNS)` (`prompt-cache.ts:133`). Because the recent window *slides forward every turn*, a message that was rendered verbatim at turn N is rendered as an elision marker at turn N+1 — **at a byte position behind the new breakpoint**. Anthropic caches the longest matching prefix; a byte change anywhere in the prefix invalidates everything after it. So the history portion of the prefix is re-written every turn and only the system + first-human portion can hit.

Two consequences: the measured `cacheHitRate` will be far below the ~90% Plan 22 projected, and every turn pays a 1.25× cache-write surcharge on the re-created suffix.

**Fix (C1): make compaction monotone.** Memoise each message's compacted rendering by message id, so once a message has been stubbed its bytes never change again for the rest of the invocation. The rendered prefix then becomes append-only and the rolling breakpoint is genuinely stable. Pin it with a test that hashes the serialised prefix up to the breakpoint across five consecutive turns and asserts the hashes are prefix-compatible.

### 3.3 Gap 2 — the cache minimum is measured on the wrong thing

`MIN_CACHEABLE_CHARS = 2000` (`prompt-cache.ts:50`) is ~500 tokens, and it is measured on `systemMessage.content` **alone**. Anthropic's minimum cacheable prefix is 1024 tokens for Sonnet/Opus and **2048 tokens for Haiku**. Two errors follow:

- The system breakpoint also covers the serialised `tools` block (that is Plan 22's whole rationale for spending only one breakpoint there), but the tools are **not counted** in the size test — so a small system prompt with large tool schemas is skipped when it would in fact cache well.
- `junior-*` agents run on `claude-haiku-4-5` (9.9M input tokens, 951 calls in this run). Their prefix must clear 2048 tokens or the breakpoint is a pure 1.25× loss.

**Fix (C2):** count `tools` + `systemMessage` together, make the minimum model-aware (`CACHE_MIN_TOKENS_BY_FAMILY`), and log the decision once per agent so a skipped breakpoint is visible.

### 3.4 Gap 3 — the cost model does not know cache pricing (regression risk)

`estimateCost()` (`utils/cost.ts:14`) is `input × inputPer1k + output × outputPer1k`. It ignores `cacheReadTokens` / `cacheCreationTokens`, which Plan 22 D2 now records faithfully. Once the cache hits, the budget guard will **overstate** cost by up to 10× on cached input. This run finished at `estCostUsd: 123.63` against `MAX_RUN_COST_USD=150` — 82% utilisation. With caching on and cost accounting wrong, a cheaper run will trip the cost circuit-breaker *earlier* than the expensive one did.

**Fix (C3):** `cacheRead × 0.1 × inputPer1k` + `cacheCreation × 1.25 × inputPer1k` + `(input − cacheRead − cacheCreation) × inputPer1k`, surfaced in `token-report.ts` as billed vs list price.

### 3.5 Gap 4 — a parallel-read turn can inject 110k chars of context

`MAX_TOOL_RESULT_CHARS = 10000` is a **per-result** cap. Claude issues up to 11 tool calls per turn (Plan 22's own measurement), so one turn can append ~110k chars ≈ 28k tokens, and `HISTORY_KEEP_RECENT_TURNS = 3` keeps three such turns verbatim. That is the mechanism behind the flat-but-huge ~22k-token resident context in `inv-strong-fixer-146`.

**Fix (C4):** add `MAX_TURN_TOOL_RESULT_CHARS` (default 30000) enforced across the results of a single `langgraph_step` — the turn key Plan 22's guard already computes. When a turn's aggregate exceeds it, shrink each result's share proportionally (floor 1500 chars) rather than truncating the last ones to nothing.

### 3.6 Gap 5 — file reads via shell bypass every control

650 `run_command` invocations, of which **163 start with `cat`**, 32 with `head`, 31 with `find`, plus `for f in $(find src -name '*.ts'); do cat …` chains up to 623 characters long. These reads: are not deduplicated by the loop guard's read cache, do not consume the read budget (they consume the much smaller shell budget), are not covered by `filesRead` in the respawn handoff, and land in history at full size.

**Fix (C5):** classify a `run_command` whose command is a pure read (`cat`/`head`/`tail`/`sed -n`/`less`) as a **read** for budget, caching, and handoff purposes; key the cache on the normalised command; refuse `cat` chains touching more than `SHELL_READ_MAX_FILES` (default 4) files with a message pointing at `read_file` and the injected workspace snapshot.

### 3.7 Gap 6 — the read cache dies at every respawn and every agent handover

The loop guard is constructed per `buildAgent()` call, so each respawn generation and each of the 2 reviewers starts with an empty read cache on the *same worktree*. Plan 22 C2 mitigates this with a "do not re-read" list, which is advisory. **Fix (C6):** a branch-scoped content cache keyed by `(worktreePath, relPath, gitBlobSha)` that survives generations, so a re-read of an unchanged file is free and returns `[CACHED]`.

### 3.8 Gap 7 — no circuit breaker below the run level

There is `MAX_RUN_COST_USD` and `MAX_RUN_WALL_MS` and nothing else. A 105-turn / 2.48M-token invocation is invisible until the run budget notices. **Fix (D-sub-plan):** `MAX_INVOCATION_INPUT_TOKENS` (default 600k) and `MAX_BRANCH_COST_USD` / `MAX_BRANCH_WALL_MS`, each aborting its own scope and salvaging, so one runaway branch cannot consume the four branches that were never attempted.

### Sub-Plan A — PR identity, worktree re-entrancy, fatal provider errors

**Why first:** these three defects, alone, converted a run with 101 verified file changes into zero merged stories. Nothing else in this plan matters until they are closed.

**Read first:** `src/conductor/pr-workflow.ts` (`findExistingPR` ~337, worktree creation ~750–800, salvage ~2460–2500), `src/utils/github-local.ts:220` (`pulls.list`), `src/conductor/pr-failure.ts`, `src/utils/retry.ts`, `src/agents/developers/dispatcher.ts`, `src/utils/run-budget.ts`.

**A1 — `findExistingPR` must never return a PR for a different head (N1).**
- Gate the bare-ref fallback on `GITHUB_MODE === 'local'`. In live mode, `octokit.pulls.list({ head: 'branch' })` without `owner:` is not a head filter and returns every open PR.
- Validate unconditionally in both modes: accept a candidate only when `pr.head?.ref === head` (the local stand-in already stores `pr.head` as the bare branch name, so one predicate covers both). Log the rejected candidate at `warn`.
- Return `null` rather than a mismatched PR, and let the normal `createPullRequest` path run.
- Add a guard at the merge site: assert `ghPr.head.ref === branchName` immediately before `pulls.merge` and before `git.deleteRef`, and throw a typed `PrIdentityMismatchError` if it fails. This is the assertion that would have prevented the deletion of `us-010-screen-manager`.
- Extend the local stand-in's `pulls.list` to also expose `head: { ref }` on each result so the predicate is uniform.

**A2 — worktree creation must be re-entrant (N2).**
- Before `worktree add`, run `git worktree list --porcelain` and remove **any** worktree whose branch is `refs/heads/<branchName>` (including one under `.worktrees-failed/`), then `git worktree prune`.
- Only then attempt `git branch -D`. Check the result: if the branch still exists, reuse it — `git worktree add "<dir>" "<branch>"` followed by `git reset --hard origin/<base>` (falling back to the local base) — instead of failing the whole PR workflow.
- Salvage relocation must record the branch it is holding, so the reuse path can find it. Add the branch name to the salvage directory metadata (a `.salvage-meta.json` next to the worktree) rather than inferring it from the slug.
- The failure must never be silent: on reuse, log `Reusing existing branch <b> for a second dispatch round (previous attempt salvaged)`.

**A3 — classify fatal provider failures and stop the run gracefully (N3).** *(user decision: pause and retry, then halt)*
- New `src/conductor/provider-failure.ts`: `classifyProviderFailure(err)` → `{ kind: 'billing' | 'auth' | 'quota' | 'model-not-found' | 'transient' | 'unknown', pauseable, fatal }`. Match `invalid_request_error` + `/credit balance|insufficient (funds|quota)|billing/i`, `authentication_error`, 401/403, `permission_error`, and the OpenAI/Google equivalents. New `ProviderRecoveryFailedError` for unrecoverable provider failures.
- New `awaitProviderRecovery()` in `src/utils/llm-throttle.ts` (it already owns the process-wide semaphore, so it is the correct chokepoint): on a `pauseable` classification, set a global pause gate, log `Provider unavailable (billing) — pausing all LLM traffic`, and probe with exponential backoff up to `PROVIDER_PAUSE_MAX_MS` (default 900000 = 15 min). All in-flight and queued calls wait on the gate. New `createProviderProbe()` provides a lightweight `/models` endpoint check for the probe callback instead of a dummy function. If recovery succeeds, resume. If it does not, set `providerFailureKind` on the `DispatchResult` so `developmentNode` can bridge it to cancellation.
- The paused interval must be excluded from `MAX_RUN_WALL_MS` accounting (`run-budget.ts` gains `pausedMs`), otherwise a 15-minute outage silently steals 5% of the run.
- **A branch must never consume its attempt on a provider fault.** In `dispatcher.ts`, a branch whose failure classifies as `billing`/`auth`/`quota` is marked `notAttempted`: its assignments stay pending, its worktree and local branch are removed cleanly (not salvaged), and the `DispatchRound` records it separately so `detectUnrecoverable()` does not read a provider outage as a zero-output round.
- **Provider-failure-to-cancellation bridge.** `DispatchResult` gains `providerFailureKind?: string`. Fatal errors (`auth`, `model-not-found`) set it immediately and stop dispatch. Pauseable errors set it after `awaitProviderRecovery()` fails. `developmentNode` checks `result.providerFailureKind` and, if set, writes a periodic snapshot and returns `{ cancelled: true, _stopReason: 'provider-<kind>' }`. The graph's existing cancel routing sends this to `finalizeNode`. New event types `run:budget-stop` and `run:provider-stop` are added to the event bus for observability.

**Tests (`tests/pr-identity.test.ts`, `tests/worktree-reentrancy.test.ts`, `tests/provider-failure.test.ts`):**
- `findExistingPR` returns `null` in live mode when the only open PR has a different head; returns the PR when heads match; the bare fallback is unreachable in live mode.
- Merging with `ghPr.head.ref !== branchName` throws `PrIdentityMismatchError` and no `deleteRef` is issued.
- Real `git init` fixture: create branch + salvage worktree, then re-dispatch → worktree created, branch reset to base, no throw.
- `classifyProviderFailure` on the verbatim 400 body from `run.log:2937` → `{ kind: 'billing', pauseable: true }`; a 429 → `transient`; a 500 → `transient`.
- A branch failing with a `billing` classification leaves its assignments pending and deletes its local branch.

**Exit criteria:** a two-round dispatch over 3 branches, with a simulated provider outage in round 1, produces 3 distinct PRs with correct heads, 0 deleted-wrong-branch events, and 3 branches attempted in round 2.

### Sub-Plan B — Make the merge path able to close

**Why:** every branch reached green gates at least once and none merged. After Plan 22 F stops deleting tests, four mechanisms still stand between a green branch and `main`.

**Read first:** `src/conductor/pr-workflow.ts:1105–1200` (integrity + revert) and `:1990–2190` (strong fixer), `src/conductor/review-policy.ts` (`decideMerge`, `selectEscalationCandidate`), `src/conductor/gate-integrity.ts` (`detectTrivialTests`, reachability), `src/config.ts` (`STRONG_FIXER_*`, `MAX_REVIEW_ITERATIONS`).

**B1 — the strong fixer's final reviewer (N4).** `selectEscalationCandidate('strong-fixer', …)` returns `null` because `'strong-fixer'` is not in `DEV_AGENTS`. Pass the *original author* (`assignments[0].devAgentId`) as `authorId` and keep `'strong-fixer'` out of the exclude list; add an explicit guard `if (!getDevAgent(authorId)) → fall back to the first principal not in excludeIds` so the documented "never returns null for a valid author" contract cannot be broken by a synthetic id again. Unit-test `selectEscalationCandidate` with every synthetic id used in the codebase.

**B2 — gate the strong fixer hard (N5).** *(user decision: fix + gate hard, keep opus)*
- **Precondition on cause.** Build the blocker set from `decideMerge`. Run the fixer only when at least one blocker is an unresolved review comment or a *repairable* gate failure (typecheck/lint/test). Skip when the blockers are exclusively `Product verification failed` (missing assets — Sub-Plan F's job), `critical layout violation`, or `Quorum not met` with zero comments. In this run that alone would have skipped 4 of 7 invocations.
- **One shot per branch.** If a strong-fixer pass on this branch produced zero verified writes (Plan 22 C4's reconciliation gives ground truth), never invoke it again for the same branch.
- **Hard turn cap.** `STRONG_FIXER_MAX_TOOL_CALLS` default 40 → **18** turns, and add `STRONG_FIXER_MAX_INPUT_TOKENS` (default 250000) as an independent abort. Observed: 105 turns / 2.48M tokens on one invocation.
- **Keep `claude-opus-4-6`** as the model (user decision) — the savings come from *not running it*, not from downgrading it.
- Log a one-line decision record every time: `Strong fixer: skipped (blockers not fixer-repairable: …)` or `Strong fixer: running (18 turns, 250k tokens, blockers: …)`.

**B3 — never revert-then-block (N7).** *(user decision)*
- After reverting protected files, re-run the gates. If the gates were green before the revert and red after, the revert caused the failure. ### Sub-Plan C — Input-token economics (beyond Plan 22)

**Read first:** `src/agents/_shared/history-compactor.ts`, `src/agents/_shared/prompt-cache.ts`, `src/agents/_shared/agent-factory.ts:150–250`, `src/agents/_shared/tool-loop-guard.ts`, `src/tools/_shared/truncate.ts`, `src/tools/shell/shell-tools.ts`, `src/utils/cost.ts`, `src/utils/token-report.ts`.

Once a message is rendered as an elision marker it keeps exactly those bytes. **C2 — correct cache minimums (§3.3).** Count the serialised `tools` block together with the system message; make the threshold model-aware (Haiku 2048 tokens, Sonnet/Opus 1024) via a new `CACHE_MIN_TOKENS_BY_FAMILY` map; log once per agent whether each breakpoint was placed and why not.

**C4 — per-turn aggregate tool-result budget (§3.5).** `MAX_TURN_TOOL_RESULT_CHARS` (default 30000), enforced across the results of one `langgraph_step` using the turn key the Plan 22 guard already derives. ### Sub-Plan D — Budget circuit breakers, state persistence, and wall-clock-aware scheduling

**Read first:** `src/utils/run-budget.ts`, `src/utils/run-snapshot.ts`, `src/utils/token-tracker.ts`, `src/agents/developers/dispatcher.ts`, `src/conductor/nodes.ts` (`developmentNode`), `src/conductor/state.ts`, `src/conductor/run.ts`, `src/conductor/continue/state-collector.ts`.

**D1 — per-invocation input ceiling.** `MAX_INVOCATION_INPUT_TOKENS` (default 600000). The token tracker already sees every call and its `invocationId`; when an invocation crosses the ceiling, throw a typed `InvocationBudgetExceededError` that `invokeDevAgent` handles exactly like Plan 22's `ToolBudgetExhaustedError` — commits are already durable. In this run three invocations would have been stopped at 600k instead of reaching 1.8M–2.5M.

**D2 — per-branch caps.** `MAX_BRANCH_COST_USD` (default 6) and `MAX_BRANCH_WALL_MS` (default 900000 = 15 min). On breach, stop the branch, salvage, record `branch:budget-exceeded`, and keep its assignments pending for a later round. Observed: ~22 min and up to $12 per branch.

**D3 — wall-clock-aware admission control.** Before dispatching a branch, compare `remainingWallMs` against a rolling median of completed branch durations. If the branch cannot plausibly finish, do not start it: record it as `deferred` and go straight to `finalize` with an honest `SCOPE` report. Starting a branch that cannot finish is strictly worse than not starting it — it produces a dangling branch (which is exactly what N2 then choked on).

**D4 — pause accounting.** `run-budget.ts` gains `pausedMs` (fed by A3) and excludes it from `elapsedMs`.

**D5 — periodic state snapshots.** New `writePeriodicSnapshot(outputPath, state, phase)` in `run-snapshot.ts`. Every node calls it at `phase:start` — captures the full accumulated state from all previous phases plus a `latest-phase.json` marker. This ensures continue-run has a recent snapshot even if the process crashes mid-phase or the budget stop fires before the finalize node. `checkBudgetStop()` also writes a snapshot before returning the cancellation update. Without this, a run stopped by budget exhaustion may not have a usable `state.json` because the only snapshot was the finalize-time write.

**D6 — budget-stop-to-cancellation bridge.** New `shouldStopRun()` in `run-budget.ts`: returns `true` when `getBudgetStatus().level === 'stop'`. New `checkBudgetStop(state, phase, logger)` helper in `nodes.ts`: called at the top of every node, checks `shouldStopRun()`, and if true emits `run:budget-stop`, writes a periodic snapshot, and returns `{ cancelled: true, _stopReason: 'budget-exhausted:<binding>' }`. The graph's cancel routing sends this to `finalizeNode`. The `_stopReason` field (new `Annotation<string | null>` on `ProjectState`) records why the run stopped — used by `finalizeNode` for manifest status and by continue-run to surface the stop reason.

**D7 — `budget-exhausted` manifest status and continue-run awareness.** `RunManifest` gains `'budget-exhausted'` as a status option. `finalizeNode` checks `state._stopReason` and if it starts with `budget-exhausted` or `provider-`, writes the manifest with status `'budget-exhausted'` instead of the generic `'cancelled'`. `RunStatus` in `token-tracker.ts` gains the same value. `listStoppedRuns()` in `state-collector.ts` surfaces `stopReason` from saved state, so the CLI and REST API show *why* a run stopped (e.g. `budget-exhausted:cost`, `provider-billing`). `continueRun()` in `run.ts` clears both `cancelled` and `_stopReason` when resuming — otherwise the continued run would immediately route to finalize again.

**Tests:** `tests/invocation-budget.test.ts`, `tests/branch-budget.test.ts`, `tests/wall-admission.test.ts`.

**Exit criteria:** a synthetic dispatch of 15 branches under a 60-minute wall budget attempts as many as fit, defers the rest explicitly, and leaves no dangling branches. A node with `shouldStopRun() === true` returns `{ cancelled: true, _stopReason }` without throwing. A budget-exhausted run's manifest has status `'budget-exhausted'` and `listStoppedRuns()` surfaces it with the reason. `continueRun()` on such a run clears the stop reason and resumes from the stopped phase.

## 6. Risks and trade-offs

- **A1 changes PR reuse semantics.** A genuine 422 "already exists" race must still reuse the PR. The head-equality predicate handles it, but the 422 recovery path at `pr-workflow.ts:1321/1338` must be re-tested explicitly, since it also calls `findExistingPR`.
- **A2's branch reuse can carry stale commits.** The `git reset --hard origin/<base>` is what makes it safe; if the previous attempt left commits worth salvaging they are already in `.worktrees-failed/` and `outputs/<run>/salvage/`. Losing them silently would be worse than the current crash, so log the discarded shas.
- **A3's pause can hide a permanent outage as slowness.** `PROVIDER_PAUSE_MAX_MS` bounds it, and D4 keeps the pause out of the wall budget, but an operator watching a dashboard will see a 15-minute silence. Emit a `run:paused` event so the UI can say why.
- **C1's memoisation grows with the invocation.** Bounded by turns × messages; clear it on `thread_id` change. If memory is a concern, cap it and fall back to recomputation (correctness is unaffected, only cache hits).
- **C5 may block a legitimate bulk read.** The limit is 4 files and the refusal names the alternative. Agents in this run used `cat` chains of 10+ files as a *substitute* for the workspace snapshot they had already been given.
- **B2's gating can skip a fixer that would have succeeded.** It succeeded once in seven attempts. The precondition is on *blocker class*, not on likelihood, so the one case that produced 2 file changes (review comments present) still runs.
- **B4 disables a real anti-gaming rule early in a run.** It only disables it while the entry closure is degenerate — precisely the window in which it carries no signal. Once F2's assembly step lands, the closure is populated and the rule re-arms.
- **E3 makes runs more serial per branch but far less conflict-prone.** Combined with D3 this is net-positive on wall clock; on its own, fewer-but-larger branches lengthen individual branch time. Watch `MAX_BRANCH_WALL_MS` after E lands and raise it deliberately rather than letting D2 kill consolidated branches.
- **E1 raises planner cost from $0.52 to perhaps $3.** Against a $123 execution bill this is not a trade-off.
- **D5's periodic snapshots write `state.json` at every phase boundary.** This is a ~1ms write of a ~200KB file, negligible against 22-minute phase durations. If the write itself fails (disk full), it is caught and logged without crashing the run.
- **D6's `_stopReason` is a replace-reducer field.** A continue-run must clear it or the resumed run would immediately see `cancelled=true` from the reconstructed state and route back to finalize. `continueRun()` explicitly sets both `cancelled: false` and `_stopReason: null`.
- **D7's `budget-exhausted` manifest status changes the schema.** `listStoppedRuns()` and the REST API now expose `stopReason`. Existing UI consumers that only check for `cancelled`/`completed`/`failed` will ignore the new status gracefully since `budget-exhausted` is truthy and sorts into the "stoppable" bucket.
