## Sub-Plan 27-B: Sequential Branch Dispatch with Halt-on-Failure

### Problem
Currently, branches are dispatched in parallel batches of `MAX_CONCURRENT_DEVS` (default 2). The dispatcher runs scaffold first (sequentially), then bootstrap, then feature branches in parallel. When the scaffold branch fails (no PR opened, gates blocked), ALL feature branches still proceed — built from an empty base. This wastes tokens on doomed work.

The user wants: **one branch at a time, halt if any branch fails or its PR isn't opened/merged. Save state gracefully on halt.**

### Root Cause
`src/agents/developers/dispatcher.ts` — `runBranches()` (lines 490-661) processes batches of `MAX_CONCURRENT_DEVS` branches via `Promise.allSettled`. The existing `prCreationFailed` flag stops FUTURE dispatching but doesn't halt when a branch fails quality gates (returns `PR-GATES-FAILED` placeholder instead of `pr-creation-failed`).

### Fix

**File: `src/config.ts`**
Add two new config variables:
```typescript

 *  When true, MAX_CONCURRENT_DEVS is forced to 1. Default: true. */

 *  'off' (never halt, original behavior). Default: 'strict'. */

    envString('DISPATCH_HALT_POLICY', 'strict');
```

## Sub-Plan 27-C: Aggressive Tool Budget Overhaul

### Problem
Turns were the binding constraint in 100% of the 40+ budget exhaustion events in the pacmanclaude4 run. Examples from logs:
- `junior-python`: 15/15 turns used, only 2/15 writes — the agent had budget to write but no turns left to plan
- `senior-frontend`: 24/24 turns, 8/25 writes — same pattern
- Plan 26's `COMPLEXITY_MULTIPLIERS` made it worse: `'simple': 0.75` reduced junior turns from 20 to 15

The user wants: **raise base aggressively + adaptive extension**.

### Root Cause
`src/agents/_shared/tool-loop-guard.ts` lines 164-169:
```typescript

    principal: { reads: 60, writes: 30, shell: 14, turns: 28 },

```
The `0.75x` multiplier for `'simple'` and `'trivial'` further reduces these already-tight budgets.

Additionally, the progress bonus (line 596-604) only extends reads, not turns — which is the actual bottleneck.

## Sub-Plan 27-D: Planning Integrity — TL Truncation & Gap-Repair Context

### Problem
Two interrelated failures:

1. **Team Leader output truncated**: The TL's first call produced 64,005 output tokens (limit: 64,000), truncating the response mid-JSON. Only 8 of 46 needed assignments were produced. The truncation recovery code trimmed 1 incomplete element and accepted the 8-assignment prefix.

2. **Gap-repair called with insufficient context**: `buildCoverageGapPrompt()` sends ONLY the list of violations — no project slug, no repo contract, no tech stack, no existing branch map, no previously-produced assignments. The gap-repair call generated 38 assignments blind, producing:
   - Wrong branch prefixes (`pacman/feature/...` instead of `pacmanclaude4/feature/...`)
   - Wrong agent assignments (junior-python on TypeScript tasks)
   - Oversized branches (12+ tasks per branch)
   - Missing chore/scaffold classification on scaffold work

### Root Cause

**Truncation**: `src/config.ts:417-418`:
```typescript
export const PLANNING_MAX_OUTPUT_TOKENS =
    envInt('PLANNING_MAX_OUTPUT_TOKENS', 64000);
```
For a 35-story, 102-task project, the TL needs to produce 46+ assignments with descriptions, dependencies, branch names, module IDs, task IDs, and reviewer arrays. At ~1500 tokens per assignment, that's ~69K tokens. The 64K ceiling truncates mid-stream.

**Gap-repair context**: `src/conductor/plan-coverage.ts:291-347` — `buildCoverageGapPrompt()` takes only `violations` and `nextAssignmentId`. The calling code at `src/conductor/nodes/planning.ts:381-395` passes only the gap prompt as `userMessage`, losing all the context sections (architecture, tech stack, repo contract, project slug, stories, tasks) that were in the original TL call.

### Fix

**Part 1: Raise PLANNING_MAX_OUTPUT_TOKENS**

**File: `src/config.ts` (line 417-418)**
```typescript
export const PLANNING_MAX_OUTPUT_TOKENS =
    envInt('PLANNING_MAX_OUTPUT_TOKENS', 128000);
```
Rationale: Claude Sonnet 5 supports 128K output tokens. Doubling from 64K to 128K ensures the TL can produce a full assignment plan for projects up to ~80 stories.

## Sub-Plan 27-G: SIGINT-Aware Graceful Shutdown

### Problem
When the user killed the process (`Ctrl+C` / `kill -INT`), the existing SIGINT handler in `src/utils/crash-handlers.ts:40-43` immediately calls `process.exit(130)` after flushing the token report. It does NOT:
1. Write a final state snapshot (`state.json`)
2. Flush the ledger
3. Set `_stopReason` on the state for continue-run
4. Cancel in-flight LLM calls

### Root Cause
`src/utils/crash-handlers.ts:40-43`:
```typescript
process.on('SIGINT', () => {
    flushTokenReportOnExit('SIGINT', logFn);
    process.exit(130);
});
```
Only the token report is flushed. The state and ledger are lost.

### Fix

**File: `src/utils/crash-handlers.ts`**

Replace the simple SIGINT handler with a comprehensive graceful shutdown:

```typescript
import { writeStateSnapshot } from './run-snapshot';
import { appendLedger } from './run-ledger';
import { getRunContext } from './run-context';

/** Registered shutdown hooks — called on graceful shutdown (SIGINT/SIGTERM). */
const shutdownHooks: Array<() => void> = [];

/** Register a hook to run during graceful shutdown. */
export function onGracefulShutdown(hook: () => void): void {
    shutdownHooks.push(hook);
}

/** Flag to prevent double-shutdown. */
let _shuttingDown = false;

function gracefulShutdown(signal: string, logFn: (msg: string) => void): void {
    if (_shuttingDown) return; // prevent re-entrant shutdown
    _shuttingDown = true;
    
    logFn(`\n${signal} received — performing graceful shutdown...`);
    
    // 1. Run registered shutdown hooks (state snapshot, ledger flush, etc.)
    for (const hook of shutdownHooks) {
        try { hook(); } catch { /* best-effort */ }
    }
    
    // 2. Write ledger entry recording the shutdown
    try {
        appendLedger({ 
            kind: 'phase', 
            phase: 'development' as any, // approximate
            event: 'end' as any, 
        });
    } catch { /* best-effort */ }
    
    // 3. Flush token report
    flushTokenReportOnExit(signal, logFn);
    
    logFn(`Graceful shutdown complete. Use 'continue-run' to resume.`);
    process.exit(signal === 'SIGINT' ? 130 : 143);
}

export function installProcessHandlers(
    logFn: (msg: string) => void = console.error,
): void {
    process.on('SIGINT', () => gracefulShutdown('SIGINT', logFn));
    process.on('SIGTERM', () => gracefulShutdown('SIGTERM', logFn));
    process.on('uncaughtException', (err) => {
        logFn(`Uncaught exception: ${err.message}`);
        gracefulShutdown('uncaughtException', logFn);
    });
    process.on('unhandledRejection', (reason) => {
        logFn(`Unhandled rejection: ${reason}`);
        gracefulShutdown('unhandledRejection', logFn);
    });
}
```

## Risks / Considerations

1. **Sequential dispatch is slower** — A 7-branch run that previously took ~2h with parallel dispatch will take longer sequentially. However, the current parallel approach wastes tokens when early branches fail. Net token spend should decrease.

2. **128K output tokens is expensive** — The TL call with 128K output ceiling will cost more per-token. But it avoids the truncation→gap-repair cascade that wastes a second TL call plus produces lower-quality assignments.

3. **Raised budgets increase per-agent cost** — 45 turns vs 28 turns means ~60% more LLM calls per agent. But this is cheaper than the current pattern of budget exhaustion → respawn → re-read everything → respawn again (which was observed to consume 3-4x the budget of a single well-resourced run).

4. **SIGINT handler may not fire on forced kill** — `kill -9` bypasses all handlers. Document that users should use `Ctrl+C` or `kill -INT` for graceful shutdown.
