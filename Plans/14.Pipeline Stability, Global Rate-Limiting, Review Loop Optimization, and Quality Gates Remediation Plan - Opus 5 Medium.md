Logs analysed:

## A1. THE run-killer: `qa-unit` blows the recursion limit and nothing catches it

**This is why both runs "failed" — the existing analysis document missed it.**

Run 6 tail (05:11:31 → 05:11:40): `qa-unit` makes exactly 7 tool calls (`list_dir .`, `list_dir tests`, `list_dir src`, `list_dir .`, `search_code`, `search_code`, `list_dir .`), then:

```
2026-08-05T05:11:40.537Z [Run] ERROR Autonomous run failed — token report saved with partial data.
```

Run 5 tail is identical in shape: `qa-unit` makes 7 tool calls, then the log stops.

Mechanism:
1. `qaNode` (`src/conductor/nodes.ts:768`) calls `invokeAgent(qaUnitAgent, …)`.
2. `invokeAgent` (`src/conductor/nodes.ts:142-177`) passes `recursionLimit: PIPELINE_RECURSION_LIMIT`.
3. `PIPELINE_RECURSION_LIMIT` = **15** (`src/config.ts:115`). LangGraph counts ~2 steps per tool call → **~7 tool calls max**.
4. `qa-unit` has 6 tools (5 workspace + `run_command`) and its mission is "write test files, install deps, run tests" — it needs 20-40 calls. It hits the wall during *exploration*, before writing a single test.
5. LangGraph throws `Recursion limit of 15 reached…`. `retryWithBackoff` does not treat it as retriable, so it rethrows.
6. `qaNode` has **no try/catch** around the qa-lead / qa-unit calls (only around the E2E block, lines 785-808).
7. The exception propagates through the LangGraph node → `conductor.invoke()` → `runAutonomous`'s catch (`src/conductor/run.ts:59-66`), which logs a message that **does not include `err.message`**, then rethrows. `src/index.ts:113-122` swallows it into a WebSocket broadcast.

**Consequences:** the `devops` and `finalize` phases never run; the run is reported as failed even though 19 PRs were merged; and the log gives no clue why (observability bug).

Same latent bug for `devopsNode` (`nodes.ts:888-940`): it also uses tools (`write_file` × many + `run_command` docker builds) with `PIPELINE_RECURSION_LIMIT` = 15 and has **no try/catch**. It would have crashed the run immediately after QA anyway.

## A2. Rate-limit storm: no global coordination + retry amplification

Run 6: **1,171** `[retry] WARN … rate-limited` lines; **202** lines mentioning 429 / attempt 5-of-5; dozens of hard `ERROR … 429 Request limit exceeded` (dev agents, fix attempts, reviewers). One `429 Token limit exceeded` (tokens-per-minute, a *different* quota).

Causes:
1. **No global limiter.** Each agent has its own `ChatOpenAI`. `MAX_CONCURRENT_DEVS=3` (`.env:30`) → 3 PR workflows in parallel; each runs a dev agent then 2 reviewers, plus the pipeline agents. Everything shares one Dell gateway quota with zero coordination.
2. **Retry amplification.** `ChatOpenAI` is created with `maxRetries: 6` (`src/agents/_shared/agent-factory.ts:195`) *inside* `retryWithBackoff(…, attempts=5)` (`src/utils/retry.ts`). A single logical LLM call can therefore fire up to **30 HTTP requests**, each of which counts against the quota — the retries themselves sustain the 429 storm.
3. **No 429 feedback loop.** When one agent gets a 429 the others keep hammering. `Retry-After` is never read.
4. **Work is destroyed on failure.** `retryWithBackoff` exhaustion throws; the dev agent's partial work is discarded and re-done from scratch on the next iteration (`pr-workflow.ts:502-505`, `870-892`).

## A3. Reviewers use the **wrong base branch**, burn their step budget, and die

Log evidence (run 6 tail, run 5 tail) — the same reviewer, same PR:

```
[git] diff --stat main...HEAD
[git] diff master...HEAD -- src/components/Calculator.tsx
[git] diff main...HEAD -- src/components/Calculator.tsx
…
[PR-Workflow] ERROR Reviewer principal-frontend failed: Recursion limit of 15 reached…
```

Causes:
1. The real PR base is the **system branch** `project/calc6`, but `git-tools.ts` defaults `baseBranch` to `GIT_DEFAULT_BRANCH` (`git-tools.ts:208, 240, 264`), which `.env:55` sets to **`master`** — a branch that does not exist in the generated repo. The tool returns a git error, so the model guesses `main` (also wrong: it is the repo default, not the PR base), producing meaningless or oversized diffs.
2. `buildReviewerAgent` (`src/agents/developers/reviewer-agent.builder.ts:52`) never receives the actual base branch, so it cannot inject the right default.
3. Reviewers get `REVIEWER_RECURSION_LIMIT = 15` (~7 tool calls) and **no `maxToolCalls`**, so the loop guard (default ceiling 22) never fires first — the hard LangGraph error wins, the whole review is lost, and the iteration is wasted (`pr-workflow.ts:782-785`).

## A4. Loop guard only detects *consecutive* repeats

`withLoopGuard` (`agent-factory.ts:130-160`) counts identical arg-signatures **only at the tail** of the history. The `qa-unit` sequence `list_dir . → list_dir tests → list_dir src → list_dir .` is not consecutive, so nothing fires and the wasted calls consume the recursion budget. Run 5 still logged **177** loop-guard triggers, so the non-consecutive case is pure additional waste.

Also `MUTATING_TOOL_NAMES` clears the history for `write_file`/`edit_file`/… but there is no result cache, so re-reading the same unchanged file re-pays full tokens.

## A5. Review-loop churn (the cost driver)

Run 6: 26 assignments → 26 branches → 19 PRs, each up to 5 review iterations × 2 reviewers, **5,115 LLM calls**, ~8 h wall-clock.

Specific defects in `src/conductor/pr-workflow.ts`:
1. **Reviewers re-review unchanged code.** When the fix attempt fails (429/recursion), the loop continues to the next iteration and reviewers re-analyse the identical commit, producing identical comments — burning iterations 2-5 for nothing. There is no "did HEAD move?" check.
2. **`iteration--` inside a `for` loop** (line 875) on rate-limit — this can spin the loop with no bound.
3. **Cosmetic comments block merges.** Any `changes_requested` — even 6 `[SUGGESTION]`/`[MINOR]` comments (see run 6 tail) — triggers another dev+review round trip.
4. **No test gate before PR.** `runPostDevTests` (lines 144-167) runs `npm test --silent` with a 60 s timeout and **never installs dependencies**; failures are only pasted into the PR body, so reviewers spend iterations reporting "test suite must contain at least one test" / missing-module errors that a `npm install` would have avoided.
5. Merge conflicts at the end (`Cannot resolve conflicts …`, `Merge failed: Pull Request has merge conflicts`) are a direct consequence of 26 long-lived branches off one base.

## A6. Generated-output quality defects (reviewer-reported, real)

- `Dockerfile` listed inside `.dockerignore` → `docker build` cannot see it. No prompt rule forbids this (`src/agents/devops/devops.prompt.ts`).
- `DOCKER_TAG` used with no default; CI configured for `push` **and** `pull_request` contradicting the docs.
- Dead code shipped (`HttpError`, Winston `logger` defined but never wired).
- Agents read out-of-domain files (`senior-frontend` reading `docs/agents/principal-backend-mission.md`, `backend/src/evaluator.ts`).

## Sub-Plan 2 — Global LLM throttle: kill the 429 storm

### Context you need
- Every agent's LLM client is built in **one place**: `buildAgent` in `src/agents/_shared/agent-factory.ts:179-220`. It creates `ChatOpenAI` with a custom `oauthFetch` (lines 182-187) and `maxRetries: 6`.
- `oauthFetch` is therefore the single choke point through which **all** LLM HTTP traffic flows.
- `src/utils/retry.ts` wraps agent invocations with 5 attempts / exponential backoff + jitter.
- Run 6 produced 1,171 rate-limit warnings; the actual gateway limits are unknown → everything must be env-configurable with sane defaults and adaptive self-tuning.

### User Added Context - Rate Limits per model (Request Per Minute):
- gpt-oss-120b: 20
- gpt-oss-20b: 20
- mistral-small-3-1-24b-instruct-2503: 30
- llama-3-2-3b-instruct: 30
- llama-3-3-70b-instruct: 30

### Change 1 — new module `src/utils/llm-throttle.ts`

Create a process-wide scheduler. Requirements (implement exactly these behaviours):

```ts
/**
 * Process-wide LLM request throttle.
 *
 * All agent LLM traffic funnels through `throttledFetch`, giving us a single
 * point to enforce concurrency, request spacing, and a GLOBAL cooldown when
 * the gateway returns 429. Without this, N parallel agents each retry
 * independently and sustain the rate-limit storm (runs 5 & 6: 1,171 retries).
 */
```

- `LLM_MAX_CONCURRENT_REQUESTS` (default `2`): a semaphore; at most N requests in flight process-wide.
- `LLM_MIN_REQUEST_INTERVAL_MS` (default `400`): minimum spacing between request *starts* (a single monotonic `nextSlotAt` timestamp).
- FIFO queue so waiting requests are served in order (no starvation).
- **Global cooldown gate.** Keep `cooldownUntil: number` and `consecutive429: number`. Before starting a request, `await` until `Date.now() >= cooldownUntil`.
- On a response with `status === 429` (or a thrown error whose message contains `429`, `Request limit`, `Token limit`, `Rate limit`):
  - `consecutive429++`
  - delay = `Retry-After` header (seconds → ms) if present, else `min(LLM_COOLDOWN_BASE_MS * 2^(consecutive429-1), LLM_COOLDOWN_MAX_MS)` with ±25 % jitter. Defaults: `LLM_COOLDOWN_BASE_MS=5000`, `LLM_COOLDOWN_MAX_MS=90000`.
  - `cooldownUntil = Date.now() + delay`
  - log once per cooldown escalation: `log.warn(\`Global LLM cooldown ${delay}ms (consecutive 429s: ${n}, in-flight: ${x}, queued: ${y})\`)` using `getLogger('[llm-throttle]', 214)`.
- On a successful (non-429) response: `consecutive429 = 0`. Also, after 20 consecutive successes, if the interval was adaptively increased, decay it back toward the configured value (see next bullet).
- **Adaptive spacing (self-tuning, because the real limits are unknown):** on every 429, `currentIntervalMs = min(currentIntervalMs * 1.5, LLM_MAX_REQUEST_INTERVAL_MS)` (default max `5000`). After 20 consecutive successes, `currentIntervalMs = max(currentIntervalMs / 1.2, LLM_MIN_REQUEST_INTERVAL_MS)`.
- Counters `{ total, throttledWaits, rateLimited, cooldownMsTotal }` exposed via `getThrottleStats()`, plus a `logThrottleStats()` helper.
- Export:
  ```ts
  export function throttledFetch(inner: typeof globalThis.fetch): typeof globalThis.fetch
  export function getThrottleStats(): ThrottleStats
  export function logThrottleStats(): void
  ```
- Must be a module-level singleton (plain module-scoped `let`s) so **all** agents share it. No classes needed.
- Do not swallow non-429 errors — rethrow after releasing the semaphore. Release in a `finally`.

### Change 1 — `createGitTools` takes a default base branch (`src/tools/git/git-tools.ts`)

```ts
export function createGitTools(
    workspaceRoot: string,
    gitContext?: GitContext | null,
    defaultBaseBranch?: string,
) {
    /**
     * Resolve the base branch for merge-base diffs.
     *
     * Priority: explicit tool argument → the branch this PR actually targets
     * (defaultBaseBranch) → gitContext.defaultBranch → GIT_DEFAULT_BRANCH.
     * If the resolved ref does not exist locally, fall back to `origin/<ref>`.
     * Runs 5 & 6 wasted whole review iterations on `diff master...HEAD`
     * because `master` does not exist in generated repos.
     */
    const resolveBase = (arg?: string): string => {
        const candidates = [
            arg,
            defaultBaseBranch,
            gitContext?.defaultBranch,
            GIT_DEFAULT_BRANCH,
        ].filter(Boolean) as string[];
        for (const c of candidates) {
            if (!git(workspaceRoot, `rev-parse --verify --quiet ${c}`).startsWith('Error')) return c;
            const remote = `origin/${c}`;
            if (!git(workspaceRoot, `rev-parse --verify --quiet ${remote}`).startsWith('Error')) return remote;
        }
        return candidates[0] ?? GIT_DEFAULT_BRANCH;
    };
```

Note: `git()` returns the string `Error (exit …)` on failure (it does not throw) — check with `.startsWith('Error')`.

Replace `const base = baseBranch ?? GIT_DEFAULT_BRANCH;` with `const base = resolveBase(baseBranch);` in `gitMergeBaseDiffTool`, `gitDiffFileTool`, `gitDiffStatTool`, and `const base = fromBranch ?? GIT_DEFAULT_BRANCH` with `resolveBase(fromBranch)` in `gitCheckoutBranchTool`.

## Sub-Plan 4 — Loop guard: catch non-consecutive repeats and cache read results

### Context you need
- `withLoopGuard` in `src/agents/_shared/agent-factory.ts:81-171`. Current logic counts identical arg signatures **only at the tail** of per-tool history (`MAX_REPEATED_TOOL_CALLS = 2`, `LOOP_TOLERANCE = 1`), poisons all tools past the threshold, and clears history whenever a mutating tool runs.
- Failure mode from the run-6 log (`qa-unit`): `list_dir . → list_dir tests → list_dir src → list_dir .` — a repeat that is not consecutive, so nothing fires and 2 of the agent's 7 available calls are wasted.
- Run 5 logged 177 loop-guard triggers, so repeats are rampant.

### Change 1 — count *total* repeats, not consecutive ones

Replace the per-tool `string[]` history with a `Map<string, number>` keyed by `` `${toolName}::${argSig}` ``:

```ts
/** Total identical (tool, args) invocations allowed before warning. */
const MAX_REPEATED_TOOL_CALLS = 2;   // 1st call runs, 2nd call warns
/** Extra identical attempts tolerated after the warning before poisoning. */
const LOOP_TOLERANCE = 1;
```

Logic per call:
1. `const key = \`${toolName}::${argSig}\``; `const seen = callCounts.get(key) ?? 0`.
2. If `seen >= MAX_REPEATED_TOOL_CALLS + LOOP_TOLERANCE` → poison (keep the existing `POISON_MSG` and the `factoryLog.error` wording, but say "identical args (total)" instead of "in a row").
3. If `seen >= MAX_REPEATED_TOOL_CALLS` → warn + return the existing loop-break error JSON, and **append the remaining budget**: `` `You have ${MAX_TOTAL_CALLS - totalCalls} tool calls left.` ``
4. Otherwise `callCounts.set(key, seen + 1)` and execute.

Mutating tools (`write_file`, `edit_file`, `create_file`, `delete_file`) still `callCounts.clear()` — the workspace changed, so re-reading is legitimate.

### Change 2 — result cache for read-only tools

Add a `Map<string, string>` `resultCache` alongside `callCounts`:

```ts
/** Read-only tools whose results can be served from cache within one agent run. */
const CACHEABLE_TOOL_NAMES = new Set([
    'read_file', 'list_dir', 'search_code',
    'git_diff_file', 'git_diff_stat', 'git_merge_base_diff', 'git_log', 'git_status',
]);
```

- On the **first** call of a cacheable tool, store the stringified result.
- On the warned (2nd) call, return the cached result **prefixed** with a short note instead of re-executing:
  `` `[CACHED — identical to your earlier call. Do not call this again.]\n${cached}` ``
  This is cheaper than re-running the tool and gives the model the data it apparently missed.
- Clear `resultCache` whenever a mutating tool runs **or** when `run_command` runs (a command may change files). Do **not** clear `callCounts` for `run_command` — that would re-enable `run_command` loops.

### Change 3 — surface the budget in the guard messages

Include `totalCalls`/`MAX_TOTAL_CALLS` in both the warn and poison log lines so run logs show how close agents run to the ceiling.

### Acceptance criteria
- Non-consecutive identical calls are detected.
- Cacheable read tools are executed at most once per identical argument set per agent run.
- `run_command` can still be re-run after edits, but not looped with identical args.
- Existing behaviour for dev agents (`maxToolCalls` 30/35/40) is unchanged.

- `npx tsc --noEmit`
- New `tests/loop-guard.test.ts` — export the guard for testing (either `export function withLoopGuard(...)` from `agent-factory.ts` or extract it to `src/agents/_shared/tool-loop-guard.ts` and import it in `agent-factory.ts`; **prefer extraction**, it keeps `agent-factory.ts` focused). Tests:

# PART D — Risks and trade-offs

| Change                                                     | Risk                                                                                                    | Mitigation                                                                                                                              |
| ------------------------------------------------------------| ---------------------------------------------------------------------------------------------------------| -----------------------------------------------------------------------------------------------------------------------------------------|
| Global throttle                                            | Serialises LLM traffic → longer wall-clock per phase, though fewer wasted retries should net out faster | All knobs are env vars; adaptive interval decays after sustained success                                                                |
| `maxRetries: 0` on `ChatOpenAI`                            | Loses LangChain's retry of transient non-429 network errors                                             | `retryWithBackoff` still retries the whole invocation; attempts raised to 8                                                             |
