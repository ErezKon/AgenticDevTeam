# Fix HITL Dashboard — Make the UI Interactive with Agents

The Angular dashboard has no run session page or HITL controls, so after starting a human-in-the-loop run the pipeline stalls after intake — the user has no way to approve/deny/enhance phases from the UI.

---

## Root Cause Analysis

The log at `outputs/calc8-2026-08-10T11-36-50-723Z/run.log` shows intake completed successfully (repo created, workspace set up, system branch pushed). The LangGraph state machine then paused at the `interruptBefore: ['architect', ...]` checkpoint — **which is correct HITL behavior**. The graph is waiting for the user to approve the next phase.

**The problem is entirely on the dashboard side:**

1. **No Run Session page exists** — After starting a run, `new-run.component.ts` shows "Run started successfully! Thread ID: xxx" but provides zero UI to interact with the paused pipeline. There is no route `/run/:id`.

2. **No HITL controls anywhere** — The dashboard has no approve/deny/enhance buttons, no phase output viewer, no feedback textarea. The CLI (`src/cli.ts`) has all of this as a terminal-based while-loop, but the dashboard was never built to match.

3. **No HITL waiting notification** — The server (`src/index.ts`) doesn't emit a `hitl:waiting` WebSocket event when the graph pauses, so the dashboard has no way to reactively know it should show approval controls.

4. **API uses legacy format** — `api.service.ts` calls `approvePhase(id, approved: boolean)` (legacy) instead of the current `{ decision: 'approve'|'deny'|'enhance', feedback }` format.

5. **No post-start navigation** — After starting a run, the user stays on the new-run form page instead of being redirected to a run session view.

### How the CLI does it (reference for the dashboard)

The CLI (`src/cli.ts` lines 301-375) implements a working HITL loop:
```
while (running) {
  state = session.getState()
  printPhaseStatus(state)        // show phase, counts, workspace
  show last 5 transcript messages
  prompt: approve / deny / enhance / show-state
  session.resume(decision, feedback)
}
```

The dashboard must replicate this loop as a reactive UI.

# Post Implementation Fixes

## Plan 18.2: HITL Fixes — Agent Report Rendering, Unified CLI/UI, Log Splitting

Fix three critical HITL issues discovered after Plan 18's implementation: agent output is not displayed (raw JSON shown instead), CLI and UI behavior are not unified, and each HITL approval creates a separate log directory.

### Issue Analysis

#### Issue 1: Agent output is not displayed — raw JSON shown instead of mission report

**Symptom**: When the HITL UI pauses for approval, the user sees a tabbed state viewer showing raw JSON and structured state fields. The agent's actual markdown mission report (like `architect-mission.md`) is never shown.

**Root Cause**: Two problems compound here:

1. **`interruptBefore` semantics**: The graph uses `interruptBefore: HITL_PHASES` (graph.ts L240). This pauses BEFORE the agent node runs. When paused before `architect`, the architect hasn't executed yet — `state.architecture` is `null`, `state.artifacts` is `[]`. The user is being asked to approve execution of an agent that hasn't produced any output. This is backwards from the user's expectation of reviewing the agent's work.

2. **No artifact content serving**: Even if the agent HAD run (with `interruptAfter`), the UI has no way to display the markdown report. The `ArtifactRef` in state only stores `{ agentId, filePath, title }` — a reference, not the content. There is no API endpoint to read the actual file content, and no markdown/mermaid renderer in the dashboard.

**Evidence**:
- `src/conductor/graph.ts` L240: `interruptBefore: HITL_PHASES`
- `src/conductor/nodes.ts` L835-847: architect writes `architect-mission.md` via `writeArtifact()`, but only AFTER the agent runs
- `dashboard/run-session.component.html` L382-384: Raw JSON tab shows `prettyJson(state)`, no markdown rendering
- `src/agents/_shared/schemas/artifact-ref.schema.ts`: only `agentId`, `filePath`, `title` — no `content` field

#### Issue 2: CLI and UI HITL behavior are not unified

**Symptom**: CLI's HITL loop (cli.ts L301-375) shows `printPhaseStatus()` — a basic summary of counts (stories: 0, tasks: 0, etc.) — and option `s` dumps full JSON. Neither displays the agent's markdown report. The UI has similar problems (Issue 1). Neither interface shows the user what the agent actually produced.

**Root Cause**: Both interfaces consume `state` object directly but never read the artifact files from disk. The CLI has no markdown rendering capability, and the UI doesn't attempt to load artifact content.

**Evidence**:
- `src/cli.ts` L92-107: `printPhaseStatus()` shows counts, not report content
- `src/cli.ts` L369: option `s` dumps `JSON.stringify(redactState(state))`

#### Issue 3: Each HITL approval creates a new log directory (log splitting)

**Symptom**: A single HITL run for `calc10` created 6 separate output directories (one per intake + 5 per approval attempt), fragmenting logs across: `calc10-2026-08-10T12-56-39-219Z`, `calc10-2026-08-10T12-56-51-022Z`, `calc10-2026-08-10T12-56-56-466Z`, `calc10-2026-08-10T12-57-02-311Z`, `calc10-2026-08-10T12-57-07-164Z`, `calc10-2026-08-10T12-57-23-236Z`.

**Root Cause**: The `session.resume()` function in `run.ts` calls `conductor.invoke({ approvals: [...] }, config)`. LangGraph interprets this as a new invocation from `__start__`, not a resume from interrupt. This causes `intakeNode` to re-execute each time, calling `createRunOutputDir()` (workspace.ts L43-53), which creates a new timestamped directory.

**Evidence** (from `outputs/calc10-2026-08-10T12-56-51-022Z/run.log`):
```
[Run] INFO Phase "architect" approved. Resuming...
[Intake] INFO Starting intake phase...         <-- intake re-runs!
[TokenTracker] INFO Token tracker reset
[workspace] Created run output dir: .../calc10-2026-08-10T12-56-56-466Z  <-- new dir!
[Intake] INFO Creating new GitHub repo: ErezSCE/Calc10
[RepoManager] ERROR Repository creation failed: name already exists  <-- crash!
```

The correct LangGraph resume pattern is:
1. `conductor.updateState(config, stateUpdates)` — merge approvals into the checkpoint state
2. `conductor.invoke(null, config)` — resume from the checkpoint without re-starting from `__start__`

Additionally, `intakeNode` has no idempotency guard — it always creates new workspace/output dirs without checking if `state.outputPath` already has a value.

### Fix Plan

#### Sub-Plan E: Fix HITL Resume (Log Splitting) — Backend Core

**Goal**: Fix the fundamental HITL resume mechanism so the graph properly resumes from checkpoints instead of re-running from `__start__`, and make `intakeNode` idempotent.

**Context files to read first**: `src/conductor/run.ts`, `src/conductor/nodes.ts` (L453-732), `src/conductor/graph.ts`

**Changes**:

##### E1. Fix `resume()` in `run.ts` to use updateState + invoke(null)

In the `runHumanInTheLoop` function's inner `resume()` (and the `resumeRun` version), change the invocation pattern from:
```typescript
// BEFORE (wrong — re-starts from __start__):
const result = await conductor.invoke(
    { approvals: [approval] },
    { configurable: { thread_id: threadId } },
);
```
To:
```typescript
// AFTER (correct — merges state then resumes from checkpoint):
await conductor.updateState(
    { configurable: { thread_id: threadId } },
    { approvals: [approval] },
);
const result = await conductor.invoke(
    null,
    { configurable: { thread_id: threadId } },
);
```

Apply this pattern to all three decision branches (approve, deny, enhance). For enhance, also include `pendingRerun` and `phaseFeedback` in the `updateState` call. For deny, include `cancelled: true`.

##### E2. Make `intakeNode` idempotent

Add guards at the top of `intakeNode` in `nodes.ts`:
```typescript
// Skip if already initialized (prevents re-creation on graph replay)
if (state.outputPath && state.workspacePath) {
    intakeLog.info('Intake already completed — skipping (idempotent guard).');
    return {};
}
```

##### E3. Guard `tokenTracker.reset()` in intakeNode

The `tokenTracker.reset()` at the top of intakeNode wipes all accumulated token data. With the idempotency guard above, this line will only execute once. But as an extra safety measure, move `tokenTracker.reset()` inside the `if (!state.outputPath)` guard.

- `src/conductor/run.ts` — Fix `resume()` in both `runHumanInTheLoop` and `resumeRun`

## Plan 18.3: Fix HITL Phase Off-By-One — Enhance Targets Wrong Phase

Fix a critical phase off-by-one inconsistency discovered during live HITL testing: `state.phase` points to the NEXT phase instead of the just-completed phase, causing enhance to re-run the wrong phase, incorrect UI labels, and wrong auto-tab selection.

### Evidence

Run log (`outputs/calc12-2026-08-10T17-28-38-003Z/run.log`):
```
[Architect] INFO Starting architecture phase...
[Architect] INFO Wrote artifact: architect-mission.md (3917 chars)
...
[Run] INFO Phase "product-manager" enhance requested with feedback.    ← WRONG: should be "architect"
[Product Manager] INFO Re-running product-manager with user feedback   ← WRONG: should re-run architect
```

The user wrote enhancement feedback in the UI to change the architect's React choice to Angular. Instead of re-running the architect with that feedback, the product-manager was re-run with architect-intended feedback.

---

### Root Cause Analysis

Every pipeline node in `src/conductor/nodes.ts` sets `state.phase` to the **next** phase in its return value. For example:

```typescript
// architectNode returns:
return {
    ...
    phase: 'product-manager' as PhaseName,   // ← sets phase to NEXT, not self
};
```

With `interruptAfter: HITL_PHASES` (graph.ts L242), the graph pauses AFTER the architect node completes. By this time, `state.phase` is already `'product-manager'`.

**Impact chain when user sends enhance feedback for architect:**

1. `state.phase === 'product-manager'` (wrong — should be 'architect')
2. `resume()` reads `state.phase`, sets `pendingRerun: 'product-manager'`
3. Feedback stored under `phaseFeedback['product-manager']` (wrong key)
4. `invoke(null)` resumes from architect's interrupt point
5. Conditional edge `rerunRouter('architect', 'product-manager')` checks `pendingRerun === 'architect'` → NO → routes to PM
6. PM starts, sees `pendingRerun === 'product-manager'` → re-runs itself with architect's feedback
7. Result: wrong phase re-ran with misaddressed feedback

**Secondary impacts:**
- UI shows "Phase 'product-manager' has completed" after architect finishes (wrong label)
- Phase timeline marks PM as "current" and architect as "completed" (wrong timeline)
- `autoSelectTab()` selects 'stories' tab (PM's tab) instead of 'architecture' tab

**Key insight:** `state.phase` is NOT used for graph routing anywhere. All routing decisions use conditional edges, `pendingRerun`, `cancelled`, `state.input.runType`, etc. The `phase` field is purely informational/metadata. Changing it to reflect the current (not next) phase is safe.
