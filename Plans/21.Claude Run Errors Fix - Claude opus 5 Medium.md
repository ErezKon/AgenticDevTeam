# Run-Log Remediation Plan (run.txt, 2026-08-16)

Fix the six defects that turned the `pacmanclaude` greenfield run into a 7-minute, zero-output, zero-cost-visibility loop: the Anthropic streaming `tool_use.id` failure, the OpenAI Responses-API `response_format` failure, dead runaway-detection, blind token accounting, corrupt bug-fix story ids, and an opaque git-fetch failure.

## 2. Sub-plan A — Anthropic streaming tool-call corruption (E1)

### A1. Keep `streaming: true` on `ChatAnthropic` — guard with sanitiser

`src/agents/_shared/llm-provider.ts:96`. Anthropic's HTTP endpoint times out after **~10 minutes** on non-streaming requests; agent runs routinely exceed this, so `streaming: true` must stay. The chunk-reassembly bug (E1) is instead neutralised by the A2 sanitiser, which strips residue before every LLM call. Streaming also changes where token usage lands (`usage_metadata` instead of `llmOutput.usage`) — handled by D's two-tier lookup.

### A2. Defensive content-block sanitiser

New `sanitizeStreamingContentBlocks(messages)` in `src/agents/_shared/history-compactor.ts` (it already owns pre-flight message rewriting and already runs on every model call):

- for each `AIMessage` with array content, drop blocks whose `type` is `input_json_delta` (or any `*_delta`) and drop `tool_use`/`server_tool_use` blocks with a missing/empty `id`;
- if dropping a `tool_use` block would orphan an entry in `tool_calls`, leave `tool_calls` untouched — the provider adapter re-materialises it (verified above);
- operate on a **copy**; never mutate persisted state (same invariant as `compactHistory`).

Wire it into the `history-compaction` middleware in `src/agents/_shared/agent-factory.ts:146-159`, **before** `compactHistory`, gated by a new `SANITIZE_STREAM_BLOCKS` config flag (default `true`). This makes the pipeline immune regardless of provider-package version, and also protects against `MemorySaver`/`file-checkpointer` resume of an already-corrupt history.

### A3. Wire through the dead `topP` / `topK`

`src/agents/_shared/agent-factory.ts:104-115` — add `topP: cfg.topP`, `topK: cfg.topK` to the `createChatModel()` call. Keep the `?? undefined` normalisation in `llm-provider.ts` (correct for `@langchain/anthropic@1.x`, where both default to `undefined` rather than the old `-1` sentinel).

### A4. Fail loudly on systemic dev-agent failure

`src/conductor/pr-workflow.ts:~1043` already logs `WARN No commits on branch …`. Add to `dispatchDevelopers` (`src/agents/developers/dispatcher.ts:458`): when **every** branch in a round produced zero commits, log `ERROR` and record it so Sub-plan C can halt. This is the observability gap that let 34 identical 400s scroll past as per-branch warnings.

### A5. Adaptive-only model sampling param guard

`@langchain/anthropic@1.5.4` added `ADAPTIVE_ONLY_MODEL_PREFIXES` — models whose names start with `claude-opus-4-7`, `claude-opus-4-8`, `claude-opus-5`, `claude-fable-5`, `claude-mythos-5`, or `claude-mythos-preview`. These models reject `temperature`, `topK`, and `topP` at call time via `validateInvocationParamCompatibility()` (the validation reads the **class properties**, not the constructor args, so simply omitting the constructor field does not suffice — the class default can re-surface).

In `llm-provider.ts`, detect adaptive-only models by regex and **omit all three sampling params from the constructor object entirely** when matched. All other constructor args (model, maxTokens, streaming, callbacks, anthropicApiKey, clientOptions) are passed normally. A debug log records the detection.

### Verification
- New `tests/anthropic-streaming-sanitizer.test.ts`: feeds the exact corrupt shape from issue #9798 through the sanitiser + `compactHistory` and asserts a clean 2-block assistant message; asserts `result.messages` (state) is unmodified.
- `tests/llm-provider.test.ts`: assert `ChatAnthropic` is constructed **with** `streaming: true`; `topP`/`topK` reach the constructor for non-adaptive models; temperature/topP/topK are **omitted** for every adaptive-only prefix.

## 3. Sub-plan B — OpenAI Responses-API JSON mode (E2)

### Root cause, precisely

`@langchain/openai@1.5.6` `chat_models/index.js:570-575` → `_useResponsesApi()` returns true when `_modelPrefersResponsesAPI(model)`, which matches `*codex*`, `gpt-5.2-pro`, `gpt-5.4-pro`, `gpt-5.5-pro`. `QA_MODEL=gpt-5.3-codex` therefore hits `chat_models/responses.js`, whose `invocationParams` spreads `...this.modelKwargs` straight into the Responses payload — where `response_format` is rejected. `gpt-5.4-mini` (PM/DBA/Team-Leader) stayed on Chat Completions, which is why only QA Lead died.

### Fix — pass `response_format` as a call option, not a model kwarg

In `src/agents/_shared/llm-provider.ts:117-136`, drop the `modelKwargs: { response_format: … }` branch and instead return

```ts
const model = new ChatOpenAI({ /* unchanged */ });
return opts.jsonMode
    ? model.withConfig({ response_format: { type: 'json_object' } })
    : model;
```

`withConfig` stores the option in `defaultOptions`, which `_combineCallOptions` merges into every call. `ChatOpenAIResponses.invocationParams` then runs it through `_getResponseFormat()` and emits the correct `text: { format: … }`; `ChatOpenAICompletions` still emits `response_format`. One code path, both APIs, no model-name sniffing to keep in sync with upstream.

Notes checked:
- `withConfig` does `new ChatOpenAI(this.fields)`, and `callbacks` (the `TokenUsageCallbackHandler`) is part of `fields` — token attribution survives.
- `response_format` is **not** in `_useResponsesApi`'s trigger list (only `options.text` is), so this does not accidentally force Chat-Completions models onto the Responses API.
- Return type stays assignable to `BaseChatModel`, so `createAgent({ model })` is unaffected. If TS narrows awkwardly, cast at the return boundary only.

### Hardening
- `qaNode` (`src/conductor/nodes.ts:1320+`) already survives a QA-Lead crash by synthesising `QA-LEAD-FAILED`. Keep that, but log the provider error body at `ERROR` with the model name so the next occurrence is diagnosable in one line.

### Verification
- `tests/llm-provider.test.ts`: `jsonMode: true` + `gpt-5.3-codex` → `withConfig` called with `{ response_format: { type: 'json_object' } }`, and `modelKwargs` is **not** set; `jsonMode: false` → no `withConfig`.
- Assert `invocationParams()` on a real (unauthenticated) `ChatOpenAI('gpt-5.3-codex')` yields `text.format.type === 'json_object'` and no top-level `response_format`.

## 4. Sub-plan C — Resurrect runaway detection (E3)

### Root cause

`src/conductor/acceptance-gate.ts:461-475` `detectUnrecoverable()` reads `state.dispatchRounds`. `src/conductor/state.ts:309` declares the channel. **No node ever returns it** — `developmentNode` (`nodes.ts:1299-1313`) returns `fileChanges`, `pullRequests`, … but not `dispatchRounds`. The check is unreachable. Secondly, even if populated, `r.prs` would have been `16` because `pr-workflow.ts:1046-1060` pushes a `PR-SKIPPED-<branch>` placeholder (`prNumber: 0`, `status: 'closed'`) for every no-commit branch — so `allZero` would still be `false` despite the comment saying "0 **merged** PRs".

### Fix

1. `developmentNode` returns
   ```ts
   dispatchRounds: [{
       fileChanges: result.fileChanges.length,
       prs: result.pullRequests.filter(p => p.status === 'merged').length,
       completed: result.completedAssignmentIds.length,
   }]
   ```
   (append reducer — one entry per round, matching the `DispatchRound` contract's documented intent.)
2. Call `detectUnrecoverable()` at the **top of `bugfixTriageNode`** (and keep the existing acceptance-gate call). Today `unrecoverable` is only ever set post-e2e, so `haltIfUnrecoverable` in `developmentNode`/`qaNode`/`devopsNode` can never fire inside the QA→triage→dev loop — which is exactly the loop that ran away.
3. Change the dispatcher's summary log (`dispatcher.ts:458`) to distinguish merged from skipped: `… N PRs (M merged, K skipped)`. The `16 PRs` line in the log actively misled.

### Verification
- `tests/acceptance-gate.test.ts` (extend): two consecutive `{fileChanges:0, prs:0}` rounds → `unrecoverable: true`; a round with `prs: 1` where that PR is `PR-SKIPPED` → still counted as 0.
- New test: `bugfixTriageNode` short-circuits and returns an `unrecoverable` halt when the previous two rounds were empty (with `RUN_FAIL_POLICY=halt`).

## 5. Sub-plan D — Universal token accounting (E4)

### Root cause

`src/utils/token-callback.ts:44-53` reads only `output.llmOutput?.{tokenUsage,token_usage,usage}`. Verified against installed packages:

| Path | Where usage actually lands |
|---|---|
| Anthropic, non-streaming | `llmOutput.usage` ✅ (works today — restored by A1) |
| Anthropic, streaming | `generations[0][0].message.usage_metadata` ❌ |
| OpenAI Chat Completions | `llmOutput.tokenUsage` ✅ |
| OpenAI **Responses API** (`*codex*`, `gpt-5.x-pro`) | `llmOutput.estimatedTokenUsage` ❌ (`responses.js:102,122`) |
| Google Gemini | `generations[…].message.usage_metadata` ❌ |

### Fix

Extend `handleLLMEnd` with a two-tier lookup:

1. `llmOutput.tokenUsage ?? token_usage ?? usage ?? estimatedTokenUsage`;
2. fallback: walk `output.generations` and sum `message.usage_metadata` (`input_tokens` / `output_tokens` / `total_tokens`, including `input_token_details.cache_read|cache_creation` which Anthropic reports separately).

Factor the summing into a reusable helper and have `src/utils/token-usage-extractor.ts` (which already reads `usage_metadata`) share it, so the per-call and per-invocation paths cannot drift.

Downgrade the "No token usage" line from `DEBUG` to a **once-per-agent-per-model `WARN`**: a silent zero here disabled `MAX_RUN_COST_USD` for the entire run and must not be invisible again.

### Verification
- `tests/token-callback.test.ts` (extend/new): one case per row of the table above, asserting `tokenTracker.recordCall` receives the right numbers; a case with usage in **both** places asserts no double-counting.

## 6. Sub-plan E — Bug-fix triage story-id integrity (E5)

### Root cause

`src/conductor/test-sufficiency.ts:159-170` mints bug ids `QA-<kind>[-<storyId>]` (e.g. `QA-story-untested-US-001`, `QA-no-tests`) and puts the real story only in prose (`suspectedArea: "Story US-001"`). `bugfixTriageNode` (`nodes.ts:1815-1837`) hands those bugs to the Team Leader **without a list of valid story ids**, then applies `namespaceBugfixAssignments` which rewrites `id`/`dependsOn`/`taskIds` but never touches `storyId`. The LLM reasonably copies the bug id into `storyId`, and `pr-workflow.ts:748` later reports it as a planning defect — after the developer has already lost its acceptance criteria.

### Fix (two layers — prompt *and* validator; the validator is the guarantee)

1. **Schema**: add optional `storyId?: string` to `Bug` (`src/agents/_shared/schemas/bug.schema.ts`) and populate it in `sufficiencyViolationsToBugs` from `v.storyId`. Purely additive — existing consumers unaffected.
2. **Context**: in `bugfixTriageNode`, add a `Valid Story IDs` section listing `state.userStories.map(s => s.id)` and instruct that `storyId` must be one of them (mirrors the Team Leader's own plan-coverage prompt).
3. **Validator** (the load-bearing part): new `sanitizeAssignmentStoryIds(assignments, userStories, bugs)` in `src/conductor/assignment-policy.ts`, applied inside/after `namespaceBugfixAssignments`:
   - if `storyId` is a known story id → keep;
   - else if it matches a bug whose `storyId` is known → remap;
   - else if it matches `/^QA-.*-(US-\d+)$/` and that story exists → remap (belt for pre-existing state);
   - else drop it (and from `additionalStoryIds`) and `WARN` once — a dropped id is better than a phantom one, since `storiesForIds` then simply omits the section instead of the developer silently getting *no* AC while the prompt claims otherwise.
4. Keep `pr-workflow.ts:748` as the last-resort tripwire.

### Verification
- New `tests/bugfix-story-ids.test.ts`: `QA-story-untested-US-001` → `US-001`; `QA-no-tests` → dropped + warned; a legitimate `US-004` → untouched; `additionalStoryIds` filtered the same way.

## 7. Sub-plan F — Diagnosable git failures (E6)

### Root cause

`src/utils/git-exec.ts:38-40` returns `` `Error: ${err.stderr ?? err.message}` ``. On an `execSync` **timeout** the child is SIGTERM'd: `stderr` is empty *and* `err.message` is empty → the literal string `"Error:"`. `workspace-sync.ts:96` then logs `Failed to fetch origin/project/pacmanclaude: Error:` and returns `strategy: 'failed'`. `gitExecVerbose()` already exists for exactly this reason (its JSDoc cites "the opaque `Error:` string observed in pacman8") but `workspace-sync.ts` never adopted it.

### Fix

1. `gitExec`: when `stderr` and `message` are both empty, synthesise a real message from `err.status` / `err.signal` / `err.code` (e.g. `Error: git exited via SIGTERM (timeout after 30000ms)`), and always append the failing subcommand.
2. `syncWorkspaceToBranch` (`workspace-sync.ts:93-98`): use `gitExecVerbose` for the network `fetch`, log `stderr` + exit code, and retry the fetch (2 extra attempts, exponential backoff) with a longer timeout for network operations.
3. Add a `timeoutMs` parameter to `gitExec`/`gitExecVerbose`, defaulting to the current 30 s, and use a longer value (e.g. `GIT_NETWORK_TIMEOUT_MS`, default 120 s) for `fetch`/`push`/`clone`. 30 s is too tight for a GitHub fetch on a loaded machine.

### Verification
- `tests/git-exec.test.ts` (extend/new): a command that times out yields a non-empty, signal-bearing error string; `syncWorkspaceToBranch` retries a transient fetch failure then succeeds (mock `gitExecVerbose`).

## 11. Risks & trade-offs

| Risk | Mitigation |
|---|---|
| E1 may already be fixed by the dep bump, making A2 look redundant | A2 is cheap, and the failure mode is total + silent + billable. A2 also covers checkpoint-resume of already-corrupt histories, which the upstream fix does **not**. |
| Keeping `streaming: true` reintroduces chunk-reassembly residue | A2's sanitiser strips residue before every LLM call, and runs even when history compaction is disabled. The alternative (non-streaming) hits Anthropic's ~10-minute HTTP timeout on long agent runs. |
| Adaptive-only prefix list drifts from `@langchain/anthropic` | The regex in `llm-provider.ts` must stay in sync with `ADAPTIVE_ONLY_MODEL_PREFIXES` in the SDK's `params.ts`. A comment marks the coupling. Mismatch is noisy (the SDK throws), not silent. |
| `withConfig` returns a new instance; callbacks/config could be lost | `callbacks` is passed in the constructor `fields`, which `withConfig` re-uses. Explicitly asserted in the new test. |
| Halting after 2 zero rounds could abort a run that would have recovered | `UNRECOVERABLE_ZERO_ROUNDS` is already env-configurable and defaults to 2 by prior design; a round with *any* merged PR or file change resets the condition. |
| Dropping an unresolvable `storyId` loses information | It is strictly better than a phantom id: `storiesForIds` currently emits a story section header with no content while claiming AC exist. The drop is logged. |
| Longer git timeouts slow down genuine failures | Only applied to network subcommands (`fetch`/`push`), and retries are bounded at 3 attempts. |
| Touching `Bug` schema cascades (AI_Context rule 5) | The field is optional and additive; consumers traced: `test-sufficiency.ts`, `assignment-policy.ts` (`dedupeBugs`), `nodes.ts` triage, `traceability.ts`. None require changes. |
