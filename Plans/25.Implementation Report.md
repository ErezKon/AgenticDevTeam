# Sub-Plan 26-04: Correctness Fixes — Implementation Report

> **Date:** 2026-08-18
> **Scope:** 13 targeted behavioral bug fixes across 7 source files
> **Verification:** `tsc --noEmit` passes; `npm run test:unit` passes (84 suites, 1,344 tests)

---

## Summary

Sub-Plan 26-04 addresses 13 correctness bugs identified by the codebase audit that silently degrade pipeline quality. These include fail-open security gates, stale iteration data causing looping, lost assembly bugs, summary data computed after the string was already built, and a worktree disposal bug that always took the wrong branch.

---

## Changes by Step

### Step 1: acceptance-gate.ts — Filter test counting to executed tests only

**Problem:** `MIN_TEST_REPORTS` threshold counted LLM-claimed and quality-gate test reports, allowing the acceptance gate to pass even with zero real test execution.

**Fix:** Added `source === 'executed'` filter so only test reports from actual runners count toward the minimum.

### Step 2: acceptance-gate.ts & nodes.ts — Read integrityFindings from PR records

**Problem:** The INTEGRITY acceptance criterion searched `state.bugs` for `TAMPER-` prefixed IDs, but no code ever created bugs with that prefix. The integrity findings are stored on `pullRequests[].integrityFindings` (populated by pr-workflow.ts).

**Fix:** Changed `evaluateAcceptance()` and the finalize node's summary to read from `state.pullRequests[].integrityFindings` instead. Updated the corresponding test.

### Step 3: security-gates.ts — Filesystem walk fallback on git failure

**Problem:** When `git ls-files` failed (non-git workspace), `scanForSecrets()` returned an empty array — silently skipping the entire secret scan.

**Fix:** Added a `walkFilesForSecretScan()` helper that recursively walks the filesystem (pruning `node_modules`, `.git`, `dist`, etc.) and returns relative paths. On git failure, the scan now uses this fallback instead of returning empty.

### Step 4: security-gates.ts & nodes.ts — Fail-closed on sub-gate exceptions

**Problem:** `prStatus` was overloaded as both a PR status tracker and a merge-blocking sentinel. Multiple checks set `prStatus = 'open'` to prevent merge, conflating "genuinely open" with "blocked for a specific reason."

# Sub-Plan 26-14: RunContext & Singleton Elimination

**Goal:** Make the system safe for concurrent runs in server mode by replacing global mutable singletons with per-run scoped state via `AsyncLocalStorage`.

## What Changed

### 1. `src/utils/run-context.ts` (new — 130 lines)

Core of the concurrency fix. Defines:

- **`RunContext`** class — holds per-run instances of every previously-global singleton: `tokenTracker`, `eventBus` (buffer + emitter), `budget` (wall-clock, level, pause), `ledger` (output path), `responseLog` (dir, seq, system prompt dedup), `logger` (run log path), `snapshot` (debounce timer), `compactionMemo`, `compactionStats`, `breakpointLoggedAgents`.
- **State classes** (`EventBusState`, `RunBudgetState`, `RunLedgerState`, `ResponseLogState`, `LoggerState`, `RunSnapshotState`) — each mirrors the mutable module-level variables in its corresponding singleton module.
- **`AsyncLocalStorage<RunContext>`** — the transport. `getRunContext()` returns the active per-run context (or `undefined` in CLI mode). `runWithContext(ctx, fn)` establishes a scope.

## Design Decisions

1. **Proxy for `tokenTracker`** — The `tokenTracker` singleton is exported as a class instance and accessed via method calls (`tokenTracker.recordCall(...)`) in 16+ files. A `Proxy` transparently routes all property access to the active per-run instance, avoiding changes to any import site.

2. **`_active()` pattern for function-based singletons** — Event-bus, budget, ledger, response-log, logger, and snapshot modules export functions rather than objects. Each function calls an `_active()` helper that returns a getter/setter view over the per-run state or the module-level default.

3. **AsyncLocalStorage propagation** — Node.js automatically propagates `AsyncLocalStorage` through `setTimeout`, `setInterval`, `Promise`, and `EventEmitter` callbacks. This means `TokenTracker.scheduleRefresh()` timers, `writePeriodicSnapshot()` debounce, and all async pipeline code correctly resolve to the originating run's context.

4. **No circular imports** — `run-context.ts` defines all state classes inline and imports only from `../config`. Singleton modules import `getRunContext()` from `run-context.ts` (one-way dependency). `run.ts` imports `RunContext` + `runWithContext` from `run-context.ts`.
