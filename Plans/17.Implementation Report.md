# Implementation Report: Token Reduction Plan - Steps 1-11

**Date:** 2026-08-08 (Steps 1-8), 2026-08-09 (Steps 9-11)
**Plan reference:** `Plans/17.Token reduction plan - Opus 5 Medium.md`
**Steps implemented:** Step 1 (Config flags) + Step 2 (Cap tool results at the source) + Step 3 (preModelHook history compaction) + Step 4 (Isolate the repair loop) + Step 5 (Shrink the fixed per-call preamble) + Step 6 (Distilled conventions digest) + Step 7 (Remove git tools; tighten ceilings) + Step 8 (Fresh-context respawn with summarised handoff) + Step 9 (Second-pass state slicing) + Step 10 (Measurement infrastructure) + Step 11 (Update README.md)

---

## Summary

All 11 steps of the token-reduction plan have been implemented. Steps 1-3 introduce config flags, cap tool results at the source, and add preModelHook history compaction. Step 4 isolates the repair loop onto a fresh thread to avoid replaying bloated ReAct history for simple schema fixes. Step 5 shrinks the fixed per-call preamble by introducing a compact developer persona (~2,500 chars vs ~7,000), removing redundant sections (git_workflow, output_rules, TDD as separate block), conditionally appending maintain_mode, compacting the reviewer persona's tool_usage, and aggressively stripping JSON schema descriptions. Step 6 replaces per-agent `read_file` calls for convention files with a compact in-prompt digest of extracted imperative rules and headings. Step 7 removes git tools from dev agents (the PR workflow already handles commits/pushes) and lowers tool-call ceilings since git ceremony calls are eliminated and history is now compacted. Step 8 replaces "poison and flail" with "summarise and respawn": when a dev agent hits the tool-call ceiling, a deterministic handoff summary is extracted from the message history and a fresh agent is spawned with clean context and the compact handoff. Step 9 applies second-pass state slicing (quality fixes including the QA-lead acceptance criteria bug) and removes the dead `CONTEXT_COMPACT` toggle. Step 10 adds per-invocation measurement infrastructure (Invocation Efficiency table, cumulative compaction stats). Step 11 updates `README.md` to document all context compaction features, new environment variables, new project files, and the `agent:respawn` event. Together they are projected to save **~60-75% of input tokens** per run.

## Step 2 - Cap Tool Results at the Source

### 2a. New shared truncation utility

**New file:** `src/tools/_shared/truncate.ts`

The `truncateToolResult(result, label, maxChars?, headRatio?)` function:
- Returns the input unchanged if it fits within the budget
- When over budget, keeps a head portion and a tail portion with an omission marker in between
- The marker includes the label, count of omitted chars, and instructions to use `read_file` with `offset`/`limit` or `search_code` to retrieve specific regions
- Supports a configurable `headRatio` parameter (default 0.6 = 60% head, 40% tail) for tools where the tail matters more (e.g. shell output where errors print last uses 0.2)

## Step 3 - `preModelHook` History Compaction

**Expected saving: ~25-35% of input tokens.** This is the single biggest lever and it directly fixes lost-in-the-middle.

### 3a. History compactor

**New file:** `src/agents/_shared/history-compactor.ts`

The `compactHistory(messages, opts?)` function applies four rules in order:

1. **Never touch the first message** (the task) or the last `keepRecent` tool results — the model needs both to make its next decision.
2. **Stub older ToolMessages** — replaces the content of older tool results with a one-line receipt: `[read_file -> 4210 chars, elided]`. Preserves `tool_call_id` and `name` for provider validity.
3. **Elide big args in older AIMessage tool calls** — replaces any string argument longer than 400 chars with `[N chars elided]`. This targets `write_file` and `edit_file` calls where the full file content stays in the tool-call args and is replayed on every subsequent step. Short args (e.g. `filePath`) are preserved verbatim.
4. **Hard ceiling** — if still over `HISTORY_MAX_CHARS` after stubbing, drops the oldest stubbed AI/ToolMessage groups. Groups are always dropped together to maintain the critical provider invariant.

**Key design decisions:**
- **Pure function** — no I/O, no LangGraph types beyond `BaseMessage`. Takes messages in, returns compacted messages out.
- **Never mutates** — creates new `ToolMessage` and `AIMessage` instances for stubbed/elided entries. Original messages array and its contents are untouched (verified by immutability tests).
- **Provider-validity invariant** — every `AIMessage` with `tool_calls` must always be followed by matching `ToolMessage`s. This is enforced as a unit-test invariant. Messages are stubbed (never deleted individually) unless the entire AI+Tool group is dropped together.
- **`keepRecent` boundary** — walks backwards counting `ToolMessage`s to find the recent window. When `keepRecent > total tool results`, nothing is stubbed. When `keepRecent=0`, all tool results are eligible for stubbing.
- **Returns stats** — `CompactionStats { originalChars, compactedChars, toolResultsStubbed, writeArgsStubbed }` for logging.

### 3b. Agent factory integration

**Modified file:** `src/agents/_shared/agent-factory.ts`

- Added imports for `BaseMessage`, `RunnableLambda`, `HISTORY_COMPACTION_ENABLED`, and `compactHistory`
- Created a `preModelHook` using `RunnableLambda.from()` that:
  - Calls `compactHistory(state.messages)` to compact the history
  - Logs compaction stats at debug level when compaction occurs
  - Returns `{ llmInputMessages: compactedMessages }` — the replacement message list used only for the LLM call, leaving the durable `messages` state intact
- The hook is only created when `HISTORY_COMPACTION_ENABLED` is `true` (default)
- Passed to `createReactAgent({ ..., preModelHook })` — LangGraph's `preModelHook` support is confirmed in `@langchain/langgraph@1.4.8`

**How it works with LangGraph:** The `preModelHook` returns `{ llmInputMessages }` which is consumed by the agent node for the LLM call only. The durable `messages` state (used by `MemorySaver`, token extraction, and JSON parsing of the last message) is untouched. This is the correct seam — nothing downstream changes.

## Step 4 - Isolate the Repair Loop

**Expected saving: ~2-4%, plus higher repair success rate.**

### 4a. Fresh thread for repair

**Modified file:** `src/conductor/nodes.ts`, `invokeAgent` function

The repair loop previously re-invoked on the **same** `thread_id`, replaying the entire ReAct history (potentially 15K+ tokens of tool noise) just to fix a JSON schema violation. Changed to:

1. **Fresh thread per repair attempt** — `repairThreadId = ${threadId}-repair-${attempt}` with its own `MemorySaver` history. The repair agent sees only the repair message, not the full tool loop.
2. **`recursionLimit: 2`** — prevents a repair round from starting its own tool loop. The repair should just correct the JSON, not invoke tools.
3. **Previous raw JSON included** — the repair message now carries the first 4,000 chars of the agent's previous (invalid) JSON so the model corrects rather than regenerates from scratch.

### 4b. Updated `buildRepairMessage`

**Modified file:** `src/utils/structured-output.ts`

Added optional `previousRaw` parameter to `buildRepairMessage(issues, originalRequest, previousRaw?)`:
- When `previousRaw` is supplied, the first 4,000 chars are included in a fenced code block with a "Your previous (invalid) JSON:" header
- Content beyond 4,000 chars is truncated with a `[N chars truncated]` marker
- When not supplied, the message is unchanged from the previous behavior
- The `originalRequest` parameter is kept for signature compatibility but was already not interpolated into the output

### 4c. Unit tests

**Modified file:** `tests/structured-output.test.ts` — 3 new tests added:

| Test | What it covers |
|------|----------------|
| includes previousRaw when supplied | Verifies the previous JSON appears in the repair message |

## Step 8 - Fresh-Context Respawn with Summarised Handoff

**Expected saving: ~10-15%, and this is the structural fix for context rot.** Today, hitting the ceiling produced 114 `poisoning all tools` events — the agent then kept getting invoked with a *maximal* history while every tool returned an error. That was the most expensive possible state. Respawn replaces "poison and flail" with "summarise and respawn".

### 8a. Tool loop guard: `isCeilingReached` getter

**Modified file:** `src/agents/_shared/tool-loop-guard.ts`

- Added `LoopGuardResult` interface: `{ tools: StructuredToolInterface[], isCeilingReached: () => boolean }`
- Changed `withLoopGuard` return type from `StructuredToolInterface[]` to `LoopGuardResult`
- `isCeilingReached()` returns the value of the internal `poisoned` flag — true once the guard has poisoned all tools (either from the total ceiling or from repeated-call detection)
- Empty tools array returns `{ tools: [], isCeilingReached: () => false }`

### 8b. Agent factory: expose `isCeilingReached` on agent

**Modified file:** `src/agents/_shared/agent-factory.ts`

- Destructured `withLoopGuard` return: `const { tools: guardedTools, isCeilingReached } = withLoopGuard(...)`
- `buildAgent` now returns `Object.assign(agent, { isCeilingReached })` — the agent retains all existing methods (`.invoke()`, etc.) and gains an `isCeilingReached()` method
- This is backward-compatible: all existing call sites that use `agent.invoke()` continue to work unchanged; only the respawn logic accesses `isCeilingReached`

### 8c. Deterministic handoff extraction

**New file:** `src/conductor/agent-respawn.ts`

`HandoffSummary` interface:
```ts
interface HandoffSummary {
    generation: number;
    filesWritten: { path: string; action: string }[];
    commandsRun: { command: string; exitCode: number }[];
    keyFindings: string[];
    remainingWork: string;
}
```

`buildHandoff(messages, generation)` walks `AIMessage.tool_calls` and their `ToolMessage` results:
- `write_file` / `edit_file` / `create_file` calls -> `filesWritten` (path + action only, never content). Deduplicates by path, keeping the last action.
- `run_command` calls -> `commandsRun` (command + exit code parsed from the result). Parses `Exit code: N`, `exited with N`, or infers non-zero from error keywords.
- The agent's last non-empty text content, clipped to 800 chars -> `keyFindings`.
- `remainingWork` derived from failed commands or file-write state.

**Key design decisions:**
- **Deterministic extraction** — no extra LLM call, so the summary itself is free. An LLM-generated summary would cost a full-history call, which is precisely what we are trying to avoid.
- **Never includes file content** — only paths and actions. Content is already on disk; the successor agent reads it if needed.
- **Compact output** — `renderHandoff` stays under 1,200 chars even for 30-tool-call histories (verified by unit test).

`renderHandoff(h)` produces a short, front-loaded prompt section:
```
## Previous Attempt (generation 1) — you are continuing this work
Files already written: src/Board.tsx (created), src/Board.test.tsx (created)
Commands run: `npm test` (exit 1)
Findings: Board.test.tsx fails - `cells` prop is undefined in the render assertion.
Remaining: fix the failing assertion, re-run tests, then report.
Do NOT re-read files you already wrote unless you need to change them.
```

### 8d. Respawn loop in `invokeDevAgent`

**Modified file:** `src/conductor/pr-workflow.ts`

Added imports for `AGENT_RESPAWN_ENABLED`, `AGENT_RESPAWN_MAX_GENERATIONS`, `buildHandoff`, and `renderHandoff`.

Extracted `parseDevResult()` from `invokeDevAgent` — parses a single agent invocation result into `DeveloperOutput`. This allows the respawn loop to call it per-generation.

`invokeDevAgent` now accepts an optional `buildAgentFn?: () => any` parameter. When `AGENT_RESPAWN_ENABLED=true` and `buildAgentFn` is provided:

1. Runs a generation loop from `gen = 0` to `AGENT_RESPAWN_MAX_GENERATIONS` (default 2)
2. For generation 0: uses the pre-built agent with the base message
3. For generation > 0: builds a fresh agent via `buildAgentFn()` (new `MemorySaver`, new `thread_id`) and prepends the rendered handoff to the base message
4. After each invocation, checks `agent.isCeilingReached()`
5. If ceiling not reached OR max generations reached: returns the result
6. If ceiling reached and more generations available: extracts handoff via `buildHandoff`, emits `agent:respawn` event, and continues the loop
7. All token usage from all generations is accumulated and returned

When `buildAgentFn` is not provided or `AGENT_RESPAWN_ENABLED=false`, falls back to the original non-respawn behavior.

Return type extended to `{ output, tokenUsage, allTokenUsage? }` where `allTokenUsage` contains token records from all respawn generations when more than one generation ran.

## Expected Impact

### Step 2: Tool result capping (~15-20% savings)
- A capped result is cheaper on the step it appears (direct savings)
- A capped result is cheaper on **every subsequent replay** in the ReAct loop (compounding savings)
- `read_file` previously returned entire files with no cap; 985 `read_file` calls in Pacman4 each dumped full file contents into history
- `run_command` previously kept 5000+2000=7000 chars; now capped at 6000 with tail-weighted preservation of error context
- Git diffs are now consistently truncated through the same utility rather than ad-hoc slicing
- The `offset`/`limit` parameters on `read_file` provide an escape hatch for agents that need specific file sections

### Step 3: History compaction (~25-35% savings)
- Directly fixes the O(steps^2) input-token growth that dominates cost
- Older tool results are stubbed to ~60-char receipts instead of replaying thousands of chars on every subsequent call
- Large `write_file`/`edit_file` arguments (full file contents) are elided from older history entries — the file is already on disk, the model doesn't need the content replayed
- The hard ceiling (`HISTORY_MAX_CHARS=40000`) prevents runaway growth even if stubbing alone isn't sufficient
- Steps 2 and 3 compound: Step 2 caps each result at entry, Step 3 then stubs older entries further — a 20K-char file read becomes 6K (Step 2) on entry, then ~60 chars (Step 3) on subsequent calls

### Step 4: Isolated repair loop (~2-4% savings)
- Repair attempts no longer replay the full ReAct history — a single repair call sends ~500 chars of issues + ~4,000 chars of previous JSON instead of 10K-15K chars of accumulated tool history
- `recursionLimit: 2` prevents repair from starting tool loops
- Including the previous raw JSON improves repair success rate — the model corrects rather than regenerates

### Step 5: Compact preamble (~10-15% savings)
- Developer persona reduced from ~7,000 chars to ~2,500 chars — a ~4,500 char saving billed on every LLM call across all ~3,000 dev-phase calls
- Removing `<git_workflow>` eliminates 5-10 wasted git tool calls per invocation (each carrying the full bloated history)
- `<maintain_mode>` only included when relevant, saving ~950 chars on greenfield runs
- Reviewer `<tool_usage>` compressed from 9 lines to 2 lines
- Aggressive JSON schema stripping removes all descriptions, `additionalProperties`, `$schema`, and empty `required` arrays — estimated ~300-500 chars per call across 3,406 calls
- Combined: ~(4500 + 300) × 3400 ≈ 16.3M chars ≈ 4M tokens saved

### Step 6: Conventions digest (~8-12% savings)
- Eliminates ~42 convention file reads per run (observed in Pacman4 logs)
- Each `read_file` for a convention file (e.g. `React.md` at 10,923 chars) landed in ReAct history and was replayed for the rest of the tool loop — roughly 2-3M tokens alone
- The digest extracts imperative rules and key headings into ~1,500 chars injected once in the system prompt
- The escape hatch (`read one ONLY if you need detail beyond the rules above`) lets agents access full files when needed, but they almost never need to
- Combined with Step 3 (history compaction), even if an agent does read a full convention file, it gets stubbed to ~60 chars on subsequent calls

### Step 7: Remove git tools; tighten ceilings (~8-12% savings)
- Removing 8 git tool schemas from every dev request saves ~2,000-3,000 chars per LLM call across ~3,000 dev-phase calls
- Eliminating 5-10 git ceremony calls per invocation removes those calls AND the replay of all history before each one — a compounding effect
- Lowered ceilings (principal: 40→26, senior: 35→22, junior: 30→18) mean agents hit the ceiling sooner, reducing the maximum history size
- The `DEV_GIT_TOOLS_ENABLED=true` flag restores the old surface for environments where dev agents must handle git directly
- Combined: ~3000 × 3000 + (7.5 calls × 5000 chars × 3000 invocations) ≈ ~120M chars ≈ ~30M tokens saved (with history compaction, the actual savings are lower but still substantial)

### Step 8: Fresh-context respawn (~10-15% savings)
- Eliminates the "poison and flail" pattern: 114 `poisoning all tools` events in Pacman4 each continued billing at peak context size while every tool returned an error string
- Respawn bounds each invocation's context to O(ceiling) instead of O(max steps) — generation 2 starts at ~4k input tokens with better signal than generation 1 had at 15k
- The handoff is deterministic (no extra LLM call), so the summary itself costs zero tokens
- `renderHandoff` stays under 1,200 chars, ensuring the successor agent's first call is well under budget
- Compounds with Steps 2-3: the successor agent benefits from tool-result capping and history compaction from the very start of its fresh context
- With `AGENT_RESPAWN_MAX_GENERATIONS=2` (default), a task gets up to 3 agent lifetimes (gen 0 + 2 respawns = 78 max tool calls vs 26 with old poisoning), each with clean context
