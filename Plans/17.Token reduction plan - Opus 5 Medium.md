# AgenticDevTeam Input-Token Reduction Plan

Cut input tokens ~60–75% by attacking ReAct message-history replay inside single agent invocations (the real cost driver), shrinking the fixed per-call preamble, capping tool outputs, and adding fresh-context agent respawn — not by re-slicing shared state, which is already near-optimal.

---

## 0. Evidence — what actually costs money

Measured from `TokenOptimization/{Pacman3,Pacman4,BattleshipRun}/run.log`:

| Run | LLM calls | Input tokens | Output tokens | In:Out | Avg input/call | State context sent (whole run) |
|---|---|---|---|---|---|---|
| Pacman4 | 3,406 | 30,974,521 | 1,675,598 | 18.5:1 | 9,093 | 113,860 chars (~28k tokens) |
| Pacman3 | 2,538 | 19,643,114 | 955,997 | 20.5:1 | 7,740 | 158,093 chars (~40k tokens) |
| Battleship | 1,355 | 10,732,477 | 588,893 | 18.2:1 | 7,921 | 155,121 chars (~39k tokens) |

**The state-slicing hypothesis is wrong.** `context-builder.ts` + `CONTEXT_COMPACT=true` already reduce all per-phase state context to **~0.1% of total input tokens** (28k of 31M in Pacman4). Every planning agent already receives a summarised, per-role slice; dev agents already receive only their own branch's stories (`storiesForIds`). Deleting *all* state context would save well under 1%.

**Where the 31M actually goes** (Pacman4):

1. **ReAct history replay — the dominant cost.** Every tool-loop step re-sends the entire conversation. A single `principal-frontend` invocation traced in the log grew `in=` monotonically: 3,995 → 4,085 → 4,133 → 4,284 → 4,674 → 5,022 → 5,470 → 6,116 → 6,782 → 7,301 → 7,552 … i.e. input cost per invocation is **O(steps²)**. 2,992 of 3,406 calls are `development` phase; 355 are `review`.
2. **Fixed preamble re-billed 3,406 times.** First dev call is `in=3995` for `out=85` — that's system persona (~7,000 chars), injected JSON schema, 11 tool schemas, and the task message. `≈4,000 × 3,406 ≈ 13.6M tokens (44% of all input)` is the *same text* re-sent.
3. **Unbounded tool results pinned in history.** `read_file` (workspace-tools.ts:47) returns whole files with no cap; `run_command` returns up to 7,000 chars; `write_file` args carry the *full file body*. 985 `read_file`, 81 `write_file`, 213 `run_command` calls in one run — each result then replayed on every later step of that invocation.
4. **Convention files read through the tool loop.** `React.md` is 10,923 chars (~2,800 tokens); the log shows 42 `.conventions/*.md` reads. Each one lands in history and is re-billed for the rest of the loop — roughly 2–3M tokens alone.
5. **Agents run to the wall.** 114 `poisoning all tools` events. Agents routinely exhaust the 30/35/40 tool-call ceiling, which is exactly where per-call input is largest. Post-poison, the agent keeps being invoked with a maximal history while every tool returns an error string.
6. **Repair loop reuses the bloated thread.** `invokeAgent` (nodes.ts:379) re-invokes with the **same `thread_id`**, so a JSON-repair round replays the entire ReAct history. `retryWithBackoff` re-runs whole invocations from scratch on failure.

### Agent lifecycle (answering the question directly)

Agents **are** created fresh per task and do **not** carry state across tasks:
- `buildAgent` (agent-factory.ts:48) allocates a **new `MemorySaver` per agent instance**.
- `buildDevAgent` / `buildReviewerAgent` are called fresh for every dev-per-branch, every quality-gate repair, and every review-fix round (pr-workflow.ts:456, 549, 804, 957, 1063).
- Every invocation uses a unique `thread_id` (`...-${Date.now()}`), so no history is shared.

**So there is no cross-task context rot. All rot is *intra-invocation*** — up to 40 tool-call rounds accumulating file dumps, shell output and diffs, with the task instructions stranded at the very top of a 15k-token window. That is a textbook lost-in-the-middle setup and it is also where 100% of the excess cost lives.

**Target:** 60–75% input-token reduction (Pacman4-equivalent run: ~31M → ~8–12M; ~$206 → ~$60–80), with equal or better quality (better, if lost-in-the-middle is reduced).

---

## Decisions taken (confirmed with user)

- Focus on the ReAct loop first; a smaller second pass on state slices.
- **Aggressive** behaviour changes are allowed (tool surface, persona, conventions).
- Include **full agent respawn** with summarised handoff.
- Validate with **cassette replay + unit tests** (no live-run spend required).

Every change is still gated behind an env flag defaulting to the new behaviour, so a single `.env` edit reverts it.

### Step 2 — Cap tool results at the source

**Expected saving: ~15–20% of input tokens.** A capped result is cheaper on the step it appears *and* on every replay.

**New file:** `src/tools/_shared/truncate.ts`

```ts
import { MAX_TOOL_RESULT_CHARS } from '../../config';

/**
 * Clip a tool result to a character budget, keeping head and tail.
 * The middle is replaced by a marker so the model knows content is missing
 * and can request a specific slice instead of assuming it saw everything.
 */
export function truncateToolResult(
    result: string,
    label: string,
    maxChars: number = MAX_TOOL_RESULT_CHARS,
): string {
    if (result.length <= maxChars) return result;
    const headSize = Math.floor(maxChars * 0.6);
    const tailSize = maxChars - headSize;
    const omitted = result.length - maxChars;
    return [
        result.slice(0, headSize),
        `\n... [${label}: ${omitted} chars omitted of ${result.length} total.`,
        `Use read_file with offset/limit, or search_code, to see a specific region.] ...\n`,
        result.slice(-tailSize),
    ].join('');
}
```

Unit-test it in a new `tests/truncate.test.ts`: under budget passes through unchanged; over budget returns exactly `maxChars` + marker length; head and tail are both present.

### Step 3 — `preModelHook` history compaction

**Expected saving: ~25–35% of input tokens.** This is the single biggest lever and it directly fixes lost-in-the-middle.

`createReactAgent` from `@langchain/langgraph@1.0.7` supports `preModelHook`, which returns `{ llmInputMessages }` — a *replacement* message list used only for the LLM call, leaving the durable `messages` state intact (verified in `node_modules/@langchain/langgraph/dist/prebuilt/react_agent_executor.js:143,220`). This is exactly the right seam: nothing downstream (token extraction, JSON parsing of the last message) changes.

**New file:** `src/agents/_shared/history-compactor.ts`

```ts
import { AIMessage, ToolMessage, type BaseMessage } from '@langchain/core/messages';
import {
    HISTORY_KEEP_RECENT_TOOL_RESULTS, HISTORY_MAX_CHARS, MAX_TOOL_RESULT_CHARS,
} from '../../config';

export interface CompactionStats {
    originalChars: number;
    compactedChars: number;
    toolResultsStubbed: number;
    writeArgsStubbed: number;
}

/**
 * Compact a ReAct message history for the next LLM call.
 *
 * Rules, in order:
 *  1. Never touch the first message (the task) or the last `keepRecent`
 *     tool results — the model needs both to make its next decision.
 *  2. Replace the CONTENT of older ToolMessages with a one-line receipt:
 *     `[read_file src/App.tsx -> 4,210 chars, elided]`.
 *  3. Replace the `content` / `newString` ARGUMENTS of older write_file /
 *     edit_file tool calls with `[<n> chars elided - file already written]`.
 *     The tool NAME and PATH stay, so the model still knows what it did.
 *  4. If still over `HISTORY_MAX_CHARS`, drop the oldest stubbed pairs
 *     (never the first message, never the last `keepRecent`).
 *
 * Pure function - no I/O, no LangGraph types beyond BaseMessage.
 */
export function compactHistory(
    messages: BaseMessage[],
    opts?: { keepRecent?: number; maxChars?: number },
): { messages: BaseMessage[]; stats: CompactionStats } { /* ... */ }
```

Implementation notes for the implementer:

- Identify tool results with `ToolMessage.isInstance(m)`; identify tool-call arguments on `AIMessage.isInstance(m) && m.tool_calls?.length`.
- Build the "recent" window by walking backwards and counting `ToolMessage`s until `keepRecent` is reached. Everything before that index is eligible for stubbing.
- Stub a `ToolMessage` by constructing a **new** `ToolMessage({ content: stub, tool_call_id: m.tool_call_id, name: m.name })`. Never mutate in place — `messages` is durable state.
- Stub `AIMessage` tool-call args by cloning the message with `new AIMessage({ content: m.content, tool_calls: m.tool_calls!.map(tc => ({ ...tc, args: elideBigArgs(tc.args) })), id: m.id })`. `elideBigArgs` replaces any string arg value longer than 400 chars with `[${len} chars elided]`. **Critical:** an `AIMessage` with `tool_calls` must always be followed by its matching `ToolMessage`s or providers reject the request — stub, never delete, unless you drop the whole AI/Tool group together in rule 4.
- Return stats so the caller can log them.

**File:** `src/agents/_shared/agent-factory.ts`

```ts
import { RunnableLambda } from '@langchain/core/runnables';
import { compactHistory } from './history-compactor';
import { HISTORY_COMPACTION_ENABLED } from '../../config';
// ...
const preModelHook = HISTORY_COMPACTION_ENABLED
    ? RunnableLambda.from((state: { messages: BaseMessage[] }) => {
        const { messages, stats } = compactHistory(state.messages);
        if (stats.originalChars !== stats.compactedChars) {
            factoryLog.debug(
                `${cfg.id}: history ${stats.originalChars} -> ${stats.compactedChars} chars ` +
                `(${stats.toolResultsStubbed} results, ${stats.writeArgsStubbed} write args stubbed)`,
            );
        }
        return { llmInputMessages: messages };
    })
    : undefined;

return createReactAgent({ llm: model, checkpointer, prompt, tools: guardedTools, preModelHook });
```

Unit-test in `tests/history-compactor.test.ts`:
- History under budget is returned unchanged (referentially equal array contents).
- The first message and the last `keepRecent` tool results are never altered.
- An old `read_file` result of 20,000 chars is replaced by a stub under 120 chars.
- A `write_file` tool call with a 5,000-char `content` arg is elided but keeps `filePath`.
- Every `AIMessage` with `tool_calls` still has a matching `ToolMessage` for each `tool_call_id` after compaction (the provider-validity invariant).

### Step 8 — Fresh-context respawn with summarised handoff

**Expected saving: ~10–15%, and this is the structural fix for context rot.** Today, hitting the ceiling produces 114 `poisoning all tools` events — the agent then keeps getting invoked with a *maximal* history while every tool returns an error. That is the most expensive possible state.

Replace "poison and flail" with "summarise and respawn": bound each invocation's context to O(threshold) instead of O(max steps), and hand the successor a clean, purpose-built brief.

**File:** `src/agents/_shared/tool-loop-guard.ts`

Add an optional `onCeilingReached?: () => void` callback and a `ceilingReached` getter. Change the return type to `{ tools, isCeilingReached() }`. Keep poisoning as the fallback when respawn is disabled or exhausted. Update all four call sites (`agent-factory.ts:96`, and the tests).

**New file:** `src/conductor/agent-respawn.ts`

```ts
export interface HandoffSummary {
    generation: number;
    filesWritten: { path: string; action: string }[];
    commandsRun: { command: string; exitCode: number }[];
    keyFindings: string[];
    remainingWork: string;
}

/**
 * Build a compact handoff brief from a completed (or ceiling-terminated)
 * agent invocation. Derived DETERMINISTICALLY from the message history -
 * no extra LLM call, so the summary itself is free.
 */
export function buildHandoff(messages: BaseMessage[], generation: number): HandoffSummary;

/** Render a HandoffSummary as the prompt section for the successor agent. */
export function renderHandoff(h: HandoffSummary): string;
```

`buildHandoff` walks `AIMessage.tool_calls` and their `ToolMessage` results:
- `write_file` / `edit_file` calls → `filesWritten` (path + action only, never content).
- `run_command` calls → `commandsRun` (command + the exit code parsed from the result's first line).
- The agent's last non-empty text content, clipped to 800 chars → `keyFindings`.

Deterministic extraction is deliberate: an LLM-generated summary would cost a full-history call, which is precisely what we are trying to avoid.

**File:** `src/conductor/pr-workflow.ts`, `invokeDevAgent` (lines 226–262)

Wrap in a generation loop:

```ts
for (let gen = 0; gen <= AGENT_RESPAWN_MAX_GENERATIONS; gen++) {
    const agent = buildAgentFn();               // fresh agent -> fresh MemorySaver
    const message = gen === 0
        ? baseMessage
        : [baseMessage, renderHandoff(handoff)].join('\n');
    const result = await agent.invoke(/* fresh thread_id */);

    if (!ceilingReached(agent) || gen === AGENT_RESPAWN_MAX_GENERATIONS) return parse(result);

    handoff = buildHandoff(result.messages, gen + 1);
    log.info(`Respawning ${agentId} (generation ${gen + 1}): ` +
             `${handoff.filesWritten.length} files carried forward`);
    emitRunEvent('agent:respawn', { agentId, generation: gen + 1, files: handoff.filesWritten.length });
}
```

`renderHandoff` output is the point of the whole exercise — short, ordered, and front-loaded:

```
## Previous Attempt (generation 1) — you are continuing this work
Files already written: src/Board.tsx (created), src/Board.test.tsx (created)
Commands run: `npm test` (exit 1)
Findings: Board.test.tsx fails - `cells` prop is undefined in the render assertion.
Remaining: fix the failing assertion, re-run tests, then report.
Do NOT re-read files you already wrote unless you need to change them.
```

Generation 2 therefore starts at ~4k input tokens with *better* signal than generation 1 had at 15k. Because the successor gets a fresh `MemorySaver` and a fresh `thread_id`, this is genuinely clean context — the mechanism the user asked for.

## Risks / Considerations

- **Compaction hides something the model needed.** Mitigated by always keeping the last 3 tool results verbatim, by stubs that name the file and its size so the model can re-read deliberately, and by `HISTORY_COMPACTION_ENABLED=false` as an instant revert. The loop guard's result cache already makes a re-read cheap.
- **Provider rejects a malformed message sequence.** The strictest real constraint: every `AIMessage.tool_calls[i].id` must have a matching `ToolMessage`. Enforce this as an explicit unit-test invariant and never delete a tool message without its AI parent.
- **`preModelHook` + `MemorySaver` interaction.** `llmInputMessages` is consumed for the LLM call only; durable `messages` state is untouched, so `extractTokenUsageFromMessages` and last-message JSON parsing are unaffected. Verify on the first cassette replay.
- **Removing git tools changes dev behaviour.** The PR workflow already commits and pushes, so this should be a no-op — but confirm on the cassette run that commits still land. `DEV_GIT_TOOLS_ENABLED=true` restores the old surface.
- **Lower tool ceilings could truncate legitimate work.** This is exactly what respawn is for: hitting the ceiling now continues with clean context instead of aborting. If quality drops, raise ceilings *and* keep respawn.
- **Conventions digest loses nuance.** The full files stay in `.conventions/` and the digest explicitly tells agents they may read one. Reviewers still enforce conventions against the full text.
- **Truncation could hide a test failure.** `run_command` uses a tail-weighted split precisely because failures print last; keep `MAX_TOOL_RESULT_CHARS` at 6,000 for shell output rather than lowering it further.
- **Ordering.** Steps 1–4 are independent and safe to land first. Step 7 (ceilings) should land **after** Step 8 (respawn), otherwise lower ceilings just mean more poisoned agents.
- **What is deliberately not done:** re-slicing shared state for cost reasons. The measurements do not support it, and the Step 9 changes are justified by output quality (notably the QA-lead acceptance-criteria bug), not by tokens.
