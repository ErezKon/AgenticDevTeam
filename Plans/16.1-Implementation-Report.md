# Plan 16 — Implementation Report

## Sync the workspace to the merged system branch (fixes A1)

**Finding addressed:** A1 — The workspace QA and DevOps operate on never receives the merged developer code.

**Root cause:** `executePRWorkflow` does all development inside isolated git worktrees and squash-merges PRs on the remote via `octokit.pulls.merge`. Nothing ever fast-forwards the main checkout at `state.workspacePath`, so `qaNode` and `devopsNode` see a tree containing only `docs/` artifacts and `.conventions/` — none of the merged application source. QA burned its entire tool budget exploring an empty directory, and DevOps wrote configs for a project it couldn't see.

---

## Changes Made

### 1. New module: `src/utils/git-exec.ts`

Extracted `gitExec`, `gitPush`, and `findGitRoot` from their duplicated definitions in `nodes.ts` (lines 73-96) and `pr-workflow.ts` (lines 73-101, 203-211) into a single shared module. All three functions are now imported from one place.

## Sub-Plan 2 — Assignment lifecycle: never redo completed work (fixes A2)

**Finding addressed:** A2 — The bug-fix loop re-runs every already-completed assignment.

**Root cause:** `assignments` uses the **append** reducer, so after a bug-fix triage round the state holds the original assignments AND the new fix assignments. `developmentNode` called `dispatchDevelopers(apiKey, state.assignments, ...)` with the entire accumulated list, re-running every completed assignment on every bug-fix iteration — up to 4x the intended development cost. Additionally, `fileChanges` was injected as full pretty-printed JSON (`JSON.stringify(state.fileChanges, null, 2)`) into every developer's context prompt, growing without bound.

---

### Changes Made

#### 1. New module: `src/conductor/assignment-policy.ts`

Pure functions for assignment lifecycle management:

| Function | Purpose |
|----------|---------|
| `selectPendingAssignments(assignments, completedIds)` | De-duplicates by id (first occurrence wins), then removes completed ids. Returns only assignments still needing dispatch. |
| `completedIdsFromPullRequests(prs)` | Extracts assignment ids from PRs with status `merged` or `approved`. Excludes `open`, `closed`, and `escalated_open`. |
| `namespaceBugfixAssignments(assignments, iteration)` | Prefixes ids with `BUGFIX-<n>-` to avoid collisions. Rewrites intra-batch `dependsOn` entries; leaves external refs unchanged. |
| `dedupeBugs(bugs)` | De-duplicates bugs by id (first occurrence wins). Bugs use append reducer, so duplicates accumulate across iterations. |

## Sub-Plan 3 — Make QA E2E reachable and verify deployment for real (fixes A3, A5)

**Findings addressed:**
- A3 — QA E2E can never run (the E2E block was inside `qaNode`, gated on `state.devopsPlan?.serviceUrls` which was always `null` because DevOps hadn't run yet).
- A5 — `docker-runner.ts` is dead code; deployment status is an LLM self-report (nothing imported docker-runner.ts, and `buildStatus`/`runStatus`/`serviceUrls` came straight from the DevOps agent's unverified JSON).

**Root cause (A3):** The graph edges were `qa -> devops -> finalize`, so `devopsPlan` was always `null` when `qaNode` ran. The Playwright MCP integration, the `qa-e2e` agent, and the E2E section of the README were unreachable code.

**Root cause (A5):** `src/executor/docker-runner.ts` exported `buildImage`, `runContainer`, `healthCheck`, and `stopContainer` (208 lines, dockerode-based) but nothing in `src/` imported them. `devopsPlan` fields came from the DevOps agent's JSON response with no actual verification that images build, containers start, or services answer.

### Changes Made

#### 1. Added `'e2e'` to `PhaseName` schema

Updated `src/agents/_shared/schemas/phase.schema.ts` to include `'e2e'` in the `PhaseNameSchema` enum, making it a valid pipeline phase.

#### 2. New module: `src/conductor/devops-verify.ts`

Implements actual deployment verification using the previously-dead `docker-runner.ts`:

| Function | Purpose |
|----------|---------|
| `chooseDeploymentMode(workspacePath)` | Picks deployment strategy: `'compose'` (docker-compose.y[a]ml), `'dockerfile'` (Dockerfile only), or `'none'`. |
| `deriveServiceUrls(composePsJson, hostname?)` | Parses `docker compose ps --format json` NDJSON output into `{service, url}[]`. Skips services with no published port. |
| `verifyDeployment(workspacePath, projectSlug)` | Builds and runs what the DevOps agent wrote, health-checks it. Returns verified `buildStatus`, `runStatus`, `serviceUrls`, `healthChecks`, `containerNames`, and `logs`. Never throws: Docker-less environments degrade to `buildStatus: 'skipped'`. |
| `teardownDeployment(workspacePath, containerNames)` | Stops and removes containers started by `verifyDeployment`. Uses `docker compose down` for compose mode, `stopContainer()` for dockerfile mode. |

The module imports and uses `buildImage`, `runContainer`, `healthCheck`, and `stopContainer` from `src/executor/docker-runner.ts` -- making it no longer dead code.

Deployment modes:
- **compose**: validates with `docker compose config -q`, then `docker compose up -d --build`, then `docker compose ps --format json` -> `deriveServiceUrls`, then health-checks each URL.
- **dockerfile**: calls `buildImage()`, parses `EXPOSE` ports from the Dockerfile, maps them to host ports starting at `DEVOPS_VERIFY_BASE_PORT`, calls `runContainer()`, then health-checks.
- **none**: returns all-`skipped`.

Gated by `DEVOPS_VERIFY_ENABLED` (default `true`). When disabled or Docker is unreachable, returns all-`skipped` and logs at info.

## Sub-Plan 4 -- Multi-language quality gates that actually gate (fixes A6)

**Finding addressed:** A6 -- The pre-PR quality gate is npm-only.

**Root cause:** `ensureDepsAndRunTests` (`pr-workflow.ts:152-201`) was npm-only: no `package.json` or no real `scripts.test` returned `null`, meaning no gate at all. The system ships 11 developer agents covering C#/.NET, Java/Spring, Go, and Python -- **any non-Node project got no build, no lint, no test gate whatsoever**. Reviewers were the only line of defence, and Plan 14 taught them not to block on anything below `major`. ## Sub-Plan 5 -- Validate agent output against its Zod schema, with one repair round (fixes A7)

**Finding addressed:** A7 -- Agent output is never validated against its schema.

**Root cause:** `buildAgent` accepts `cfg.responseFormat` (a Zod schema) but only stringifies it into the prompt via `z.toJSONSchema()` -- it is **never** passed to `createReactAgent` and never used to `parse`. `invokeAgent` JSON-parses with three fallbacks (direct parse, code-fence extraction, first `{...}` run) and returns whatever comes out as `any`. Every consumer is written defensively with `?? []` / `?? 0` defaults, which converts schema violations into silent zeros rather than errors. A `testReport` missing `status` silently becomes a pass. The same 3-strategy JSON parse was duplicated in `pr-workflow.ts` for dev and reviewer outputs.

---

### Changes Made

#### 1. New module: `src/utils/structured-output.ts`

Consolidates the three duplicate JSON-extraction strategies and adds Zod-based schema validation with repair prompt support:

| Function | Purpose |
|----------|---------|
| `parseAgentJson(raw)` | Extract a JSON object from LLM response using the 3-strategy ladder: direct `JSON.parse` -> fenced `` ```json `` block -> first balanced `{...}` run. Returns `{ ok, value }` or `{ ok: false, error }`. |
| `summariseZodIssues(issues, max?)` | Compact, model-readable summary of Zod issues: at most `max` (default 10) `path: message` lines. Handles nested paths (e.g. `architecture.style`) and root-level issues (`(root)`). |
| `validateAgentOutput(schema, parsed)` | `safeParse` the parsed output; returns `ValidationOutcome<T>` with `ok`, `value`, `issues`, and `repaired` fields. |
| `buildRepairMessage(issues, originalRequest)` | Prompt text asking the agent to fix specific schema violations. Instructs: "Return the SAME information, corrected, as a single valid JSON object. Do not add commentary." |
| `getValidationStats()` | Returns `{ validated, repaired, failed }` -- module-level singleton counter. |
| `logValidationStats()` | Logs the stats at info level (mirrors `logThrottleStats` pattern). |
| `_resetValidationStats()` | Reset for testing (mirrors `_resetThrottleState` pattern). |
| `_recordValidated/Repaired/Failed()` | Increment individual counters. |
