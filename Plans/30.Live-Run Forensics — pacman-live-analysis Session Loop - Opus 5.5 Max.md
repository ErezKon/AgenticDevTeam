### Session 0/1 (pre-run + `pacman-live-analysis`)

#### F1 — critical — Unsupported Node runtime crashes the first LLM call
- **Evidence:** `run.log:31-32` contains `[Run] ERROR Autonomous run failed: AbortSignal.any is not a function` at `langchain/src/agents/errors.ts:123` (`Function.wrap`), called from `AgentNode.ts:701` (`wrappedHandler`, i.e. the `wrapModelCall` middleware path). `debug/errors.jsonl` seq 64 shows `retry giveup retryable:false`. The ledger stops at `architect start`, and `token-usage.json` has 0 records.
- **Root cause:** the user shell resolves nvm's default **Node v19.8.1**. `AbortSignal.any()` exists only from Node 20.3 / 18.17. The installed dependency floors are `langchain@1.5.5`, `@langchain/core@1.2.5`, `@langchain/anthropic@1.5.4` and `@langchain/openai@1.5.6` at `>=20`, `@langchain/mcp-adapters@1.1.3` at **`>=20.10.0`**, and `@octokit/rest` at `>=20`. All previous successful runs ran as root on Node **v25.9.0** (`outputs/claudeopus5-*/debug/environment.json`). `package.json` has no `engines` field and nothing checks the runtime, so the failure surfaced only inside the first agent invocation, after intake had already created the repo.
- **Fix:** Sub-Plan 30-A (runtime preflight before any side effect + `engines`). Session workaround: launch with nvm's Node v20.11.1.

#### F2 — major — `new-repo` intake is not idempotent; a leftover repo makes the rerun crash with `422`
- **Evidence:** the user's interrupted attempt at 22:44Z left `ErezSCE/pacman-live-analysis`, private, holding only GitHub's auto-init `Initial commit` (04f94766). Starting the same parameters again would call `octokit.repos.createForAuthenticatedUser` → `422 name already exists on this account`, which throws out of `intakeNode` before any work is done. With the user's approval the leftover was deleted manually before session 1.
- **Root cause:** `createGitHubRepo()` in `github-repo-manager.ts` has no "already exists" path. An interrupted or crashed intake (sessions 0 and 1 both qualify) always leaves the repo behind.
- **Fix:** Sub-Plan 30-B. On `422 already exists`, reuse the repo **only if it carries no work**: the default branch has ≤ 1 commit and every other branch points at the same SHA. Otherwise fail with an actionable message (pick another name, or use `Existing GitHub repository`).

#### F3 — critical (money) — `claude-opus-5-5` is unpriced, so the cost budget cannot bind on the principal tier
- **Evidence:** `MODEL_PRICING` in `src/config.ts` has `claude-opus-5` and `claude-opus-4-8` but **not** `claude-opus-5-5`, which `.env` uses for `PRINCIPAL_DEV_MODEL`. `STRONG_FIXER_MODEL` defaults to that model, and so do the principal reviewers. `estimateCost()` returns `0` for unknown models (by design, "never throws"), and nothing warns. In `claudeopus5`, $7.48 of the real $32.88 (23 %) was invisible to `MAX_RUN_COST_USD`.
- **Secondary:** Opus 5.5 cache reads are billed at **0.05×** input ($0.20 vs $4.00 / MTok), not the 0.1× default.
- **Root cause:** pricing is a hand-maintained table keyed by exact model id, and unpriced configured models fail **open** (rule 16 spirit).
- **Fix:** Sub-Plan 30-C. Add the current Anthropic ids at official list prices, then warn loudly at run start for every configured model with no price. Session workaround: `MODEL_PRICING_OVERRIDES` passed via env at launch.

#### F4 — minor — intake never writes a ledger `phase end`
- **Evidence:** both `pacman-live-analysis` and `claudeopus5` ledgers have `intake start` immediately followed by `architect start`. The `claudeopus5` forensic summary reports "intake: no end recorded".
- **Root cause:** `intakeNode` calls `appendLedger({… event: 'start'})` but not the matching `end`. It is the one node outside the `phaseNode()` decorator that skips it, which contradicts Plan 27-F.
- **Fix:** Sub-Plan 30-D. Append `{kind:'phase', phase:'intake', event:'end', durationMs}`.

#### F5 — minor — `package-lock.json` in the working tree was rewritten to `lockfileVersion: 1`
- **Evidence:** `git diff --stat package-lock.json` shows `1532 insertions(+), 5417 deletions(-)`. The `HEAD` lockfile is v3, while the working copy is v1 with npm-6 style `dependencies`. The installed `node_modules` still match `HEAD` exactly (langchain 1.5.5, core 1.2.5, langgraph 1.4.9, anthropic 1.5.4, openai 1.5.6).
- **Root cause:** an `npm install` was run with an old npm (Node 14/16 era, e.g. `/usr/local/bin/npm` or nvm v14/v16). This is the same "wrong runtime on PATH" theme as F1.
- **Action:** not a code fix, and left untouched because it is the user's uncommitted change. Recommendation: `git checkout package-lock.json`, then always install with Node ≥ 20.10 / npm ≥ 10. The `engines` field from 30-A makes npm warn about this.

#### F6 — major — external side effects happen before the run has proven it can call an LLM
- **Evidence:** session 1 created a repo (`run.log:9`) and pushed `project/pacman-live-analysis` (`run.log:15`). The crash followed 0.1 s after the first model call was attempted. The orphaned repo is exactly what produces F2 on the next attempt.
- **Fix:** Sub-Plan 30-A. The preflight runs inside `runAutonomous` / `runHumanInTheLoop` / `continueRun` before `createConductor()`, so a runtime problem is reported before intake touches GitHub.

#### F7 — major (latent) — the provider-recovery probe is provider-agnostic
- **Evidence:** `createProviderProbe()` in `src/utils/llm-throttle.ts:281-306` always probes `${OPENAI_BASE_URL}/models` with `OPENAI_API_KEY || ANTHROPIC_API_KEY`. In this configuration (both keys set), an **Anthropic** credit-balance outage is "probed" against **OpenAI**. OpenAI answers 200, so `awaitProviderRecovery()` declares recovery after the first 10 s back-off and traffic resumes into the same billing error. In addition, `/models` listing is free on both providers, so it cannot detect billing recovery for either one.
- **Relevance:** the Claude balance is finite ($88.97) and this loop could exhaust it. The intended graceful `provider-billing` stop would then degrade into a retry storm.
- **Fix:** Sub-Plan 30-E (deferred unless observed live; see §4).

#### F8 — major — graceful shutdown (SIGINT/SIGTERM) saved nothing while reporting success
- **Evidence:** `kill -INT` at 23:21:56Z printed `SIGINT received — performing graceful shutdown...` and `Graceful shutdown complete. Use 'continue-run' to resume.`, but:
  - `state.json` was **not** rewritten (mtime 23:21:06Z, the PM periodic snapshot) and still holds `_stopReason: null`, `cancelled: false`
  - `ledger.jsonl` has no `graceful-shutdown` invariant entry
  - no `State snapshot saved on shutdown.` or `Token report saved (SIGINT).` line was printed
  - `debug/errors.jsonl` holds only `crash signal`
- **Root cause:** signal handlers run **outside every `AsyncLocalStorage` scope**. All three shutdown hooks in `run.ts` (autonomous, HITL and continue, the same 12-line block copy-pasted) and steps 2–4 of `gracefulShutdown()` call `getRunContext()` at signal time. That call is always `undefined`, so `lastKnownState`, the per-run ledger path and the per-run token tracker are all unreachable. The same bug class was fixed for HITL `session.resume()` in Plan 29, but not here. The Plan 27-G behaviour ("saves `state.json` with `_stopReason: 'manual-kill'`, writes invariant ledger entry, flushes token report") has therefore never worked in CLI or server runs. This is consistent with `claudeopus5` ending in `crash:signal` with no stop reason recorded.
- **Impact:** a run stopped with Ctrl+C or `kill -INT` is not marked stopped. Continue-run sees a run that looks mid-phase with no stop reason, and the token report is not flushed.
- **Fix:** Sub-Plan 30-F.

#### F9 — minor — Ctrl+C at the CLI was swallowed while a run was executing
- **Evidence:** a `^C` byte written to the CLI's TTY during the architect/PM call produced no output. `kill -INT <pid>` worked at once.
- **Note:** readline keeps the TTY in raw mode, and Node only converts Ctrl+C to `SIGINT` when the interface has no `'SIGINT'` listener and no pause handling. The user's own session-0 Ctrl+C did work, so this may be specific to the injected byte. It is recorded but not acted on. The documented `kill -INT` path is the reliable one.

#### F12 — major (waste) — the loop guard refuses a legitimate re-read after a mutating shell command
- **Evidence:** `debug/trace.jsonl` seq 488–496 shows `senior-frontend` reading `src/main.ts`, `angular.json`, `src/index.html` (1st). Seq 531 is `run_command npm install @angular/service-worker`. Seq 539–541 shows the **re-reads refused** with `Tool "read_file" has been called 2 times with the same arguments. This indicates a loop.` Seq 578 is `edit_file src/main.ts` → `old_string not found` (a blind edit). Seq 584: the re-read succeeds only after an intervening `write_file` reset the counters. That is 4 wasted tool calls plus a turn for one occurrence, and the pattern repeats every time an agent runs `npm install`/a build and then inspects files.
- **Root cause:** in `withLoopGuard()` (`src/agents/_shared/tool-loop-guard.ts:556-560`) a non-read shell command clears `resultCache`/`shellReadCache` **but not `callCounts`**. The next identical read reaches `count >= MAX_REPEATED_TOOL_CALLS` and finds no cached result, so it returns the "loop" error instead of executing. File mutations (`:541-551`) already clear `callCounts` (keeping their own key).
- **Fix:** Sub-Plan 30-H. A mutating shell command resets `callCounts` exactly like a file mutation, keeping the command's own count so genuine shell loops are still caught.

#### F13 — major — the dispatcher's periodic snapshot overwrites `state.json` with a 4-key partial object
- **Evidence:** at 23:54Z `state.json` contained only `['phase','pullRequests','fileChanges','completedAssignmentIds']`. Architecture, stories, tasks, assignments and git context were all gone until the shutdown snapshot rewrote it.
- **Root cause:** `dispatcher.ts:686-694` calls `writePeriodicSnapshot(outputPath, { phase, pullRequests, fileChanges, completedAssignmentIds }, 'development')`. `writePeriodicSnapshot` → `writeStateSnapshot` replaces the whole file. Any crash or `kill -9` during development leaves continue-run with **no** planning state (the "Full" confidence path then reconstructs from a gutted file). The graceful-shutdown snapshot uses `lastKnownState` from development *entry*, so dispatch progress (merged PR #1, completed ASSIGN-001..003) is lost either way.
- **Fix:** Sub-Plan 30-I. The dispatcher merges its progress into the run's `lastKnownState` (append semantics for `pullRequests`/`fileChanges`/`completedAssignmentIds`), stores the merged object back as `lastKnownState`, and snapshots the **full** merged state.

#### F14 — critical — keyword-based bootstrap detection promoted the *final* integration branch to run first and created dependency cycles
- **Evidence:** `run.log:95` `Bootstrap barrier: 1 bootstrap assignment(s) detected — injecting dependencies`, `:97` `topoSort: 20 assignment(s) have cyclic dependencies — dispatching in one parallel batch`, `:835` `Branch classification: 0 scaffold, 1 bootstrap [pacman-live-analysis-3/feature/us-034-app-integration]`, then `Working on assignment ASSIGN-022 [critical/very-complex]` (principal, `claude-opus-5-5`). The matched assignment is **ASSIGN-023** ("Final accessibility & colorblind pass across the already-wired app … only add styles/attributes/toggle **wiring**"), which `dependsOn: ['ASSIGN-022']`. ASSIGN-022 ("Wire everything into the app shell") `dependsOn` **18** feature assignments.
- **Root cause:** `isBootstrapAssignment()` (`dispatcher.ts:208-221`) fires on any description containing `bootstrap|wiring|entry point|app initializ|composition root`, regardless of dependencies, and `isBootstrapBranch()` promotes the **whole branch**. `injectBootstrapDependencies()` then makes all 18 assignments that ASSIGN-022 depends on also depend on ASSIGN-023, a cycle, so `topoSort` gives up on ordering entirely. The most expensive agent was integrating 18 modules that did not exist yet, guaranteeing scope creep, conflicts with every later branch and wasted spend. The keyword heuristic also matches the scaffold's own text ("create src/main.ts (bootstrap)"), which only the scaffold short-circuit hides.
- **Fix:** Sub-Plan 30-J:
  - A bootstrap assignment must not depend on any non-scaffold assignment. Wiring that *consumes* features is integration, not bootstrap.
  - `injectBootstrapDependencies()` never adds an edge that would create a cycle: it skips assignments the bootstrap transitively depends on.
  - Regression tests cover this exact plan shape.

#### F16 — critical — a `chore` assignment on a feature branch is treated as scaffold; branch dispatch ignores cross-branch dependencies
- **Evidence (session 4):**
  - `run.log:98` `topoSort: 20 assignment(s) have cyclic dependencies — dispatching in one parallel batch`, with no bootstrap involved this time
  - the TL plan has **ASSIGN-019** `taskType: 'chore'` on `feature/us-015-audio-persistence`, `dependsOn: [ASSIGN-001, ASSIGN-016, ASSIGN-017, ASSIGN-018]`

### Sub-Plan 30-T — Only each reviewer's latest review can block (F24)

### Sub-Plan 30-U — The scaffold boundary is never crossed, and is always the root (F18, F25)

- `orderBranchLayers(…, isRoot)`: root branches (the dispatcher passes `isScaffoldBranch`) have no dependencies, so the scaffold is always layer 0.
- `topoSort()` breaker: **most dependents first** (the foundation), then fewest unmet dependencies, then plan order.
- Tests (`tests/dispatch-order.test.ts`):
  - scaffold-boundary collapsing in both directions, while same-side collapsing still works

  - foundation-first breaking
  - **session 9's exact plan**: scaffold alone in layer 0 with 3 assignments, maze before movement/ghosts, ghosts before fruit, integration last

## 5. Risks and considerations

- **Preflight false positives:** the Node floor is taken from dependency `engines`, so it is exact rather than speculative. `AbortSignal.any` is feature-detected rather than inferred from the version string.
- **Repo reuse safety:** a repo is reused only when it provably carries no work (≤ 1 commit and all branch tips identical). Any other repo with the same name still fails, now with a clear message.
- **Pricing drift:** list prices change. The table is a default, and `MODEL_PRICING_OVERRIDES` remains the escape hatch. The new warning makes drift visible instead of silent.

## 6. Live-monitoring method (all sessions)

- Read-only monitor `/tmp/runmon/runmon.py <system-slug>`, outside the repo. It aggregates `token-usage.jsonl` per agent/model/invocation at **official list prices incl. cache** and also flags unpriced models. It shows the last ledger entries, the `debug/errors.jsonl` census and the `run.log` WARN/ERROR counts.

  - a repeated input-ceiling or budget-exhausted outcome with `filesWritten: []`

  - a strong-fixer pass on a PR that the gates already block
