# Multi-Repo Project Targeting Feature

Enable users to choose whether a new greenfield project should live in the existing AgenticDevTeam repo or in a separate GitHub repository (new or existing), using a dedicated project GitHub token.

---

## Overview

Currently, all generated projects live as subdirectories within the single AgenticDevTeam repo. All git operations (push, PR creation, reviews, merges) target `GITHUB_OWNER/GITHUB_REPO` using `GITHUB_TOKEN`. This feature adds:

1. **New env vars**: `GITHUB_PROJECT_TOKEN` and `GITHUB_PROJECT_OWNER` for a second GitHub identity
2. **User choice**: At run start (CLI + dashboard), ask if the project should go to the existing repo or a different repo
3. **New repo creation**: If "different repo" is chosen, optionally create a new GitHub repo via API
4. **Dynamic GitHub context**: All downstream git/GitHub operations use the correct token, owner, and repo based on the user's choice

---

## Architecture Summary

### Current Data Flow (what changes)
```
CLI/Dashboard -> RunOptions -> intakeNode -> workspacePath (local dir inside generated-projects/)
                                          -> system branch (project/<slug>)
                                          -> gitPush to GITHUB_OWNER/GITHUB_REPO

Development -> dispatcher -> pr-workflow -> gitPush/PR to GITHUB_OWNER/GITHUB_REPO
                                         -> Octokit with GITHUB_TOKEN

git-tools.ts -> gitPush to GITHUB_OWNER/GITHUB_REPO
github-tools.ts -> Octokit with GITHUB_TOKEN
```

### New Data Flow
```
CLI/Dashboard -> asks "same repo or different repo?"
              -> if different: asks "create new or use existing?"
              -> passes repoTarget config into RunOptions

RunOptions -> intakeNode -> if separate repo:
                             -> create/validate target repo via GITHUB_PROJECT_TOKEN
                             -> git init + remote setup in workspace
                           -> else: same as today

All git operations -> use GitContext (token, owner, repo) from state
                   -> GitContext resolved at intake, stored in ProjectState
```

### Key Design Decisions

1. **GitContext object in state**: A new `gitContext` field in `ProjectState` carries `{ token, owner, repo, defaultBranch }`. All modules read from this instead of config constants.
2. **Backward compatible**: If no project token is set and user picks "same repo", behavior is identical to today.
3. **Greenfield only**: The "different repo" option only appears for greenfield runs, not maintain mode.
4. **Full PR workflow**: When using a separate repo, the full PR/review cycle works exactly the same way.

## Sub-Plans

### Sub-Plan 1: Environment & Configuration Layer

**Goal**: Add new env vars and config exports, create the `GitContext` schema, update `RunInput` schema.

**Scope**: Config/schema only, no behavioral changes.

**Files**:
- `.env.example` - Add new vars
- `src/config.ts` - Export `GITHUB_PROJECT_TOKEN`, `GITHUB_PROJECT_OWNER`
- `src/agents/_shared/schemas/git-context.schema.ts` - **CREATE** new file with:
  ```ts
  export const GitContextSchema = z.object({
    token: z.string().describe('GitHub PAT for this repo'),
    owner: z.string().describe('GitHub repo owner (org or user)'),
    repo: z.string().describe('GitHub repository name'),
    defaultBranch: z.string().default('main').describe('Default branch name'),
  });
  export type GitContext = z.infer<typeof GitContextSchema>;
  ```
- `src/agents/_shared/schemas/run-input.schema.ts` - Add `repoTarget` field:
  ```ts
  repoTarget: z.object({
    type: z.enum(['same-repo', 'new-repo', 'existing-repo']),
    repoName: z.string().optional(), // for new-repo or existing-repo
    isPrivate: z.boolean().optional().default(true), // for new-repo
  }).optional()
  ```
- `src/agents/_shared/schemas/index.ts` - Add export for `git-context.schema`
- `src/conductor/state.ts` - Add `gitContext` to `ProjectState`:
  ```ts
  gitContext: Annotation<GitContext | null>({
    reducer: replaceReducer,
    default: () => null,
  }),
  ```

**Verification**:
- `npx tsc --noEmit` passes
- Existing tests still pass

### Sub-Plan 3: Intake Node - GitContext Resolution & Repo Setup

**Goal**: Update the `intakeNode` to resolve `GitContext` based on user's `repoTarget` choice and set up the target repo.

**Scope**: `intakeNode` changes + helper function updates in `nodes.ts`.

**Files**:
- `src/conductor/nodes.ts` - Modify `intakeNode`:
  1. After workspace creation, check `state.input.repoTarget`
  2. If `same-repo` or undefined: build `GitContext` from existing `GITHUB_TOKEN/OWNER/REPO` config (backward compatible)
  3. If `new-repo`:
     - Use `GITHUB_PROJECT_TOKEN` + `GITHUB_PROJECT_OWNER` (fall back to main token if project token not set)
     - Call `createGitHubRepo()` to create the repo
     - Call `initializeRepoLocally()` to set up the workspace as a standalone git repo
     - Build `GitContext` with new repo details
  4. If `existing-repo`:
     - Use `GITHUB_PROJECT_TOKEN` + `GITHUB_PROJECT_OWNER`
     - Call `validateGitHubRepo()` to ensure it exists
     - Clone or init+remote the workspace
     - Build `GitContext`
  5. Return `gitContext` in the state update
  6. Update `gitPush` helper in `nodes.ts` to accept `GitContext` instead of reading config globals
  7. Update all `gitPush` calls in `nodes.ts` to use `state.gitContext`

**Verification**:
- TypeScript compiles
- Manual test with `repoTarget: { type: 'same-repo' }` produces same behavior as before
- Manual test with `repoTarget: { type: 'new-repo', repoName: 'test-project' }` creates repo and pushes

## Risks & Considerations

1. **Token security**: `GITHUB_PROJECT_TOKEN` must never be logged. The existing pattern of injecting tokens into push URLs is maintained but kept out of log output.

2. **Separate git root**: When targeting a new repo, the workspace is NOT inside the AgenticDevTeam git repo. The `intakeNode`'s git root detection logic must handle this — the workspace IS its own git root.

3. **Backward compatibility**: If `GITHUB_PROJECT_TOKEN` is not set and user picks "new repo", fall back to `GITHUB_TOKEN` with a warning. If `GITHUB_TOKEN` also lacks the `repo` scope for creating repos, fail with a clear error.

4. **Workspace path change**: For separate repos, `createProjectWorkspace()` may need to create the directory outside `generated-projects/` (since that dir is inside AgenticDevTeam). Alternatively, keep it in `generated-projects/` but init a fresh git repo there. The latter is simpler and maintains the current directory structure.

5. **PR base branch**: For new repos, the default branch is `main` (set during repo creation). The `GitContext.defaultBranch` tracks this.

6. **Maintain mode excluded**: The "different repo" option is only for greenfield. Maintain mode inherently works on an existing project path that already has its own git context.
