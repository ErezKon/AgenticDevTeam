# Continue Run Feature — Comprehensive Plan

Reconstruct pipeline state from persisted artifacts (state.json, run-manifest.json, ledger.jsonl, agent mission reports, full-responses, git branches/PRs, generated code) and resume execution from the last completed phase.

---

## Problem Statement

When a run stops (crash, error, SIGINT, budget exhaustion, or manual cancellation), the current system loses in-memory state. The existing `resumeRun()` in `run.ts` only works with `CHECKPOINT_PERSIST=true` (default: **false**) and requires an intact `checkpoints.json`. Most stopped runs leave only:

- `outputs/<run>/state.json` — full ProjectState snapshot (written on crash or at finalize)
- `outputs/<run>/run-manifest.json` — summary with status, phase, counts, paths
- `outputs/<run>/ledger.jsonl` — timestamped evidence trail (phase start/end, agent invocations, gates)
- `outputs/<run>/run.log` — human-readable log
- `outputs/<run>/full-responses/` — raw LLM responses per agent invocation (when `FULL_RESPONSE_LOG_ENABLED`)
- `outputs/<run>/token-usage.json` — token consumption records
- `generated-projects/<name>/` — the workspace with generated code, git history, branches
- `generated-projects/<name>/docs/agents/*.md` — agent mission reports
- Git branches (local + remote), PRs (GitHub), commits

The goal is to reconstruct `ProjectState` from these artifacts and resume the pipeline from the phase after the last successfully completed one.

## Design Decisions (User-Confirmed)

| Decision | Choice | Rationale |
|----------|--------|-----------|
| **Output directory** | **Same directory** — append to the original run's `outputs/` dir | Simpler; keeps all evidence in one place |
| **Missing workspace** | **Fatal error** — cannot continue without workspace | Generated code is irreplaceable; prompt user to fix |
| **GitHub repo** | **Auto-detect from state** — read `gitContext` from `state.json` and reuse | No user friction; repo already exists |
| **Partial development** | **Skip completed + cleanup** — skip merged assignments, clean up stale worktrees and open PRs | Prevents resource leaks while preserving completed work |

---

## Architecture Decision

**Approach: State Reconstruction from `state.json` + Git Ground Truth**

Rather than replaying LLM calls or re-running agents, we:

1. Load `state.json` (primary state source — always written on crash)
2. Cross-validate with git state (branches, commits, PRs) for development-phase accuracy
3. Determine the resume phase based on which phases completed successfully
4. Inject the reconstructed state into a new graph invocation, skipping completed phases

This is the simplest approach that handles all failure modes. The `state.json` is already a complete snapshot of `ProjectState`, redacted only for secrets (which are re-supplied via `.env`).

## Sub-Plan 01: State Collector

**Goal:** Read all artifacts from a stopped run's output directory and workspace into a structured `CollectedRunState` object.

### Files to Create
- `src/conductor/continue/state-collector.ts`

### Implementation

```typescript
interface CollectedRunState {
  /** From outputs/<run>/state.json */
  stateSnapshot: ProjectStateType | null;
  /** From outputs/<run>/run-manifest.json */
  manifest: RunManifest | null;
  /** From outputs/<run>/ledger.jsonl */
  ledgerEntries: LedgerEntry[];
  /** From outputs/<run>/full-responses/index.jsonl */
  responseIndex: ResponseLogEntry[];
  /** From generated-projects/<name>/docs/agents/*.md */
  agentArtifacts: Array<{ agentId: string; filePath: string; content: string }>;
  /** Git branches in the workspace */
  gitBranches: { local: string[]; remote: string[] };
  /** Git log (recent commits on current branch) */
  gitLog: Array<{ hash: string; message: string; date: string }>;
  /** Workspace file tree (ls-files) */
  workspaceFiles: string[];
  /** Which PR branches were merged, open, or failed */
  prBranchStatus: Array<{ branch: string; status: 'merged' | 'open' | 'failed-salvaged' | 'unknown' }>;
  /** Output path */
  outputPath: string;
  /** Workspace path */
  workspacePath: string;
}
```

### Key Logic

1. **`collectRunState(outputPath: string): CollectedRunState`**
   - Read `state.json` via `JSON.parse(fs.readFileSync(...))`
   - Read `run-manifest.json`
   - Read `ledger.jsonl` via existing `readLedger()`
   - Read `full-responses/index.jsonl` via existing `readResponseLogIndex()`
   - Resolve `workspacePath` from `state.json` → `stateSnapshot.workspacePath`
   - If workspace exists, scan `docs/agents/` for mission report files
   - If workspace is a git repo, run read-only git commands to collect branch/log info
   - Scan for salvage patches in `outputs/<run>/salvage/`

2. **`findRunOutputs(identifier: string): string`**
   - Locate the output directory by: exact path, run name, or timestamp prefix
   - Scans `outputs/` directory for matching entries
   - Returns the resolved absolute path

### Risks
- `state.json` may not exist if the crash happened before `intakeNode` completed → we need a guard
- Workspace directory may have been deleted → detect and warn

## Sub-Plan 02: State Reconstructor

**Goal:** Build a valid `ProjectState` object that can be fed into the LangGraph graph as initial state.

### Files to Create
- `src/conductor/continue/state-reconstructor.ts`

### Implementation

1. **Primary path: `state.json` exists**
   - Parse the snapshot and restore all fields
   - Re-inject secrets from current `.env` (gitContext.token was redacted)
   - Validate field shapes against Zod schemas (best-effort — log warnings, don't fail)

2. **Fallback path: `state.json` missing but manifest + ledger exist**
   - Reconstruct a minimal state from `run-manifest.json`:
     - `input` (systemName, runType) from manifest
     - `phase` from manifest.finalPhase
     - Counts give us the scope but not the actual data
   - Fill in what we can from agent mission reports (parse markdown to extract structured data)
   - This is a degraded mode — warn the user that only limited continuation is possible

3. **`reconstructState(collected: CollectedRunState): ReconstructedState`**
   ```typescript
   interface ReconstructedState {
     state: Partial<ProjectStateType>;
     resumePhase: PhaseName;
     confidence: 'full' | 'partial' | 'minimal';
     warnings: string[];
   }
   ```

4. **Secret rehydration:**
   - `gitContext.token` → from `GITHUB_PROJECT_TOKEN` or `GITHUB_TOKEN`
   - `gitContext.owner` → from state or `GITHUB_PROJECT_OWNER` / `GITHUB_OWNER`
   - `gitContext.repo` → from state
   - `gitContext.defaultBranch` → from state or detect from git

### Key Considerations
- The `state.json` uses `replaceReducer` for scalars and `appendReducer` for arrays — when we inject the state into the graph, we need the arrays to already contain all accumulated data
- `tokenUsage` from the previous run should be preserved so the final report covers both runs
- `iteration.bugfix` must be preserved to avoid resetting the loop counter

## Sub-Plan 03: Phase Resolver

**Goal:** Determine which phase completed successfully last and which phase to resume from.

### Files to Modify
- `src/conductor/continue/state-reconstructor.ts` (add phase resolution logic)

### Phase Resolution Algorithm

```
1. Read state.phase — this is the phase that was ACTIVE when the run stopped
2. Read ledger entries for phase start/end events
3. Build a completed-phases set from ledger entries where kind='phase' && event='end'
4. Cross-validate with state contents:
   - intake: workspacePath + outputPath set
   - codebase-analyzer: codebaseAnalysis not null (maintain only)
   - architect: architecture not null + epics.length > 0
   - product-manager: userStories.length > 0 + tasks.length > 0
   - dba: dbDesign not null (or skipped if no DB needed)
   - team-leader: assignments.length > 0
   - development: fileChanges.length > 0 or pullRequests.length > 0
   - qa: testReports.length > 0
   - bugfix-triage: handled by iteration counter
   - devops: devopsPlan not null
   - e2e: e2eStatus !== 'not-run'
   - acceptance-gate: acceptance not null
   - finalize: should not resume — run is complete
5. Resume from the FIRST phase whose evidence is incomplete
6. Special cases:
   - If crashed during development (fan-out), check which assignments
     completed and which didn't — partially resume development
   - If crashed during QA, re-run QA entirely (it's read-only and fast)
   - If in a bugfix loop, resume from bugfix-triage
```

### Phase-to-Phase Map (what to skip)
```
intake → always skip on continue (workspace already exists)
codebase-analyzer → skip if codebaseAnalysis exists
architect → skip if architecture + epics exist
product-manager → skip if userStories + tasks exist
dba → skip if dbDesign exists
team-leader → skip if assignments exist
development → complex (see below)
qa → re-run from start (deterministic)
bugfix-triage → resume if bugs + iteration suggest it
devops → skip if devopsPlan exists
e2e → re-run (depends on running containers)
acceptance-gate → re-run (cheap evaluation)
finalize → re-run (writes reports)
```

### Development Phase Special Handling

The development phase uses `dispatchDevelopers()` which fans out across branches. On continue:
- Check `completedAssignmentIds` to know which assignments finished
- Check `pullRequests` for merged/open/blocked status
- Check `salvageBranches` for failed branches
- Filter `assignments` to only dispatch those not in `completedAssignmentIds`
- The existing `selectPendingAssignments()` in `assignment-policy.ts` already handles this

## Sub-Plan 04: Graph Entry Point

**Goal:** Allow the LangGraph graph to start execution from any phase, not just `__start__`.

### Files to Modify
- `src/conductor/graph.ts` — add continue-mode graph builder
- `src/conductor/run.ts` — add `continueRun()` function
- `src/conductor/nodes.ts` — add idempotency guards to all nodes

### Approach: State Injection + Phase Routing

LangGraph's `invoke(null, config)` resumes from the last checkpoint. For continuation without a checkpoint, we:

1. Create a new conductor graph
2. Use `conductor.updateState()` to inject the reconstructed state into a new thread's checkpoint
3. Use a **routing node** at `__start__` that reads `state.phase` and routes to the correct resume point

**Alternative (preferred):** Add a `continueNode` as the entry that:
- Checks if this is a continuation (a `_continueFromPhase` field in state)
- If yes, returns the reconstructed state and routes to the appropriate phase
- If no, routes to `intake` as usual

### Implementation

```typescript
// In graph.ts
function afterContinueRouter(state: ProjectStateType): string {
  if (state._continueFromPhase) {
    return state._continueFromPhase;
  }
  return 'intake';
}

// New internal state field (not persisted)
_continueFromPhase?: PhaseName;
```

**Actually, a simpler approach:** Since we have the full state, we can:

1. Build the graph normally
2. Create a checkpoint with the reconstructed state already populated
3. Set the checkpoint's "next" to the resume phase
4. Call `conductor.invoke(null, config)` to continue from there

This leverages LangGraph's existing checkpoint-resume mechanism. The key insight is that `FileCheckpointer` already supports this pattern — we just need to construct the right checkpoint data.

### Recommended Approach: updateState + invoke(null)

```typescript
export async function continueRun(opts: ContinueRunOptions): Promise<RunSession | ProjectStateType> {
  const collected = collectRunState(opts.outputPath);
  const { state, resumePhase, warnings } = reconstructState(collected);
  
  // Rehydrate singletons
  rehydrateSingletons(state, opts.outputPath);
  
  const conductor = createConductor({ mode: opts.mode, outputPath: opts.outputPath });
  const threadId = opts.threadId ?? `continue-${Date.now()}`;
  
  // Seed the graph with reconstructed state via intake
  // We modify intakeNode to detect continuation and skip initialization
  const result = await conductor.invoke(
    { ...state, _isContinuation: true, _resumePhase: resumePhase },
    { configurable: { thread_id: threadId } }
  );
  
  return result;
}
```

### Node Idempotency

Most nodes already have some idempotency (e.g., `intakeNode` skips if `outputPath` is set). We need to ensure **all** planning nodes skip if their output already exists in state:

| Node | Idempotency Check |
|------|------------------|
| `intakeNode` | Already has: `if (state.outputPath && state.workspacePath)` |
| `codebaseAnalyzerNode` | Add: `if (state.codebaseAnalysis)` |
| `architectNode` | Add: `if (state.architecture && state.epics.length > 0)` |
| `productManagerNode` | Add: `if (state.userStories.length > 0 && state.tasks.length > 0)` |
| `dbaNode` | Add: `if (state.dbDesign)` |
| `teamLeaderNode` | Add: `if (state.assignments.length > 0)` |
| `developmentNode` | Uses `selectPendingAssignments()` — already handles completed work |
| `qaNode` | Re-run always (depends on current code state) |
| `bugfixTriageNode` | Re-run (triage is cheap) |
| `devopsNode` | Re-run (depends on current code state) |
| `e2eNode` | Re-run (depends on running services) |
| `acceptanceNode` | Re-run (evaluates current state) |
| `finalizeNode` | Re-run always (writes final reports) |

The idempotency check must be gated behind a `_isContinuation` flag so normal re-runs (HITL enhance) are not affected.

| `setLocalBareRepoPath()` | intakeNode (local mode) | Detect from workspace git config or `outputPath/origin.git` |
| `refreshTokenReport()` | intakeNode | Call to create/update skeleton |

### Token Budget Handling

The previous run may have consumed significant tokens. On continuation:
- Load `token-usage.json` from the previous run
- Feed the cumulative totals into `tokenTracker` so budget calculations are accurate
- `startRunBudget()` should account for the existing spend
- This prevents the continued run from exceeding the overall budget

## Sub-Plan 08: Git State Reconciliation

**Goal:** Ensure the workspace git state is clean and consistent before resuming.

### Files to Create
- `src/conductor/continue/git-reconciliation.ts`

### Checks and Fixes

1. **Workspace exists and is a git repo**
   - If workspace is gone → fatal error with clear message (user-confirmed decision)
   
2. **Current branch is the system branch** (`project/<slug>`)
   - If on wrong branch → `git checkout <systemBranch>`
   
3. **Working tree is clean** (no uncommitted changes)
   - If dirty → commit with message `chore: auto-commit pre-continuation`
   
4. **Remote is reachable** (for live GitHub mode)
   - Test with `git ls-remote origin`
   
5. **Worktree cleanup** (user-confirmed: skip completed + cleanup)
   - Remove all `.worktrees/<branch>` directories from the previous run
   - Remove `.worktrees-failed/<branch>` directories
   - Run `git worktree prune` to clean stale worktree references
   - This is critical: stale worktrees block `git worktree add` for the same branch
   
6. **Stale lock files**
   - Remove `.git/*.lock` files that may remain from a killed process
   - Remove `.git/worktrees/*/locked` files
   
7. **Branch cleanup for partially-completed development**
   - For each branch in `pullRequests`:
     - `merged` → already in main, no action needed
     - `open` → delete local worktree, delete local branch (will be re-created on dispatch)
     - `blocked`/`failed` → delete local worktree and branch (salvage patches already in outputs/)
   - For open PRs on GitHub (live mode): close them with comment "Superseded by continuation run"
   
8. **Sync with remote**
   - `git fetch origin` to get latest remote state
   - `git merge origin/<systemBranch> --no-edit` on the system branch

### For Live GitHub Mode
- Verify PRs still exist on GitHub via Octokit
- Check if any were merged externally since the crash → update `pullRequests` array
- Close stale open PRs that will be re-dispatched

## Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|-----------|
| `state.json` not written before crash | Cannot reconstruct full state | Fallback to manifest + ledger + git (degraded mode) |
| Workspace deleted between crash and continue | Cannot continue | Detect early, fatal error with clear message |
| Git remote state diverged (external commits) | Merge conflicts on resume | Sync workspace with remote before resuming |
| LLM provider changed between runs | Model incompatibilities | Use current env config, not persisted model names |
| Token budget already exhausted | Run stops immediately again | Warn user, offer to increase budget for continuation |
| Development phase partially completed | Some branches done, others not | Leverage existing `selectPendingAssignments()` |
| Bugfix iteration counter | May re-run already-fixed bugs | Preserve iteration count and fixedBugIds |
| State schema evolution | Old state.json incompatible with new code | Versioned migration or best-effort field mapping |

## Summary

The "Continue Run" feature adds the ability to resume any stopped pipeline run from the last completed phase. It works by:

1. **Collecting** all artifacts from the stopped run's output directory
2. **Reconstructing** a valid `ProjectState` from `state.json` (primary) with secret rehydration from `.env`
3. **Resolving** the correct resume phase based on state evidence and ledger
4. **Reconciling** the workspace git state to ensure consistency
5. **Rehydrating** global singletons (logger, token tracker, ledger, etc.)
6. **Injecting** the state into a new LangGraph execution that skips completed phases
7. Providing both **CLI** and **REST API** interfaces for triggering continuation

The feature is divided into 10 sub-plans that can each be implemented in a fresh AI context to avoid context rot.
