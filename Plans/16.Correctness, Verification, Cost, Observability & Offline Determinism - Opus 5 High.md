# AgenticDevTeam — Plan 16: Correctness, Verification, Cost, Observability & Offline Determinism

Thirteen independently-runnable sub-plans that fix four proven correctness bugs the existing plans (01–15) never addressed, replace LLM self-reports with deterministic verification, cut prompt-context cost, add real observability and traceability, and make the whole pipeline testable offline without a gateway or a GitHub account.

---

## How to use this document

- This is **one plan file** split into **13 self-contained sub-plans (Sub-Plan 1 … Sub-Plan 13)**.
- **Each sub-plan can be executed in a brand-new chat/context.** Every sub-plan repeats the context it needs (file paths, current code, line numbers, why the change matters). Do not assume knowledge from other sub-plans.
- Execute in order **Sub-Plan 1 → Sub-Plan 13**. Sub-Plans 1–3 are correctness fixes and must land first. Sub-Plan 13 is last because it records a cassette of the *fixed* pipeline.
- After every sub-plan: run the checks in its **Verification** section and commit before starting the next one.
- Repo root: `/home/sio/Code/AgenticDevTeam`. All paths are relative to that root unless absolute.
- Stack: TypeScript, run with `tsx`, tested with `jest` (`npm test`). Type-check with `npx tsc --noEmit`.
- Code style in this repo: **4-space indent**, `// ─── Section ───` banner comments, JSDoc on exported functions, `getLogger('[Tag]', colorCode)` for logging, env-driven constants centralised in `src/config.ts` and mirrored (commented-out, with a one-line comment) in `.env.example`. Match it.
- **Verification policy for every sub-plan: unit tests + `npx tsc --noEmit` + `npm test` only.** No sub-plan requires a live LLM run to be considered done. `tests/greenfield.test.ts` and `tests/maintain.test.ts` hit the real gateway — do **not** run them as part of a sub-plan's verification; Sub-Plan 13 makes them replayable.

# PART A — Findings (evidence)

Everything below was verified by reading the current source, not inferred from the plan history. Plans 01–15 are already implemented (`src/utils/llm-throttle.ts`, `src/agents/_shared/tool-loop-guard.ts`, `src/conductor/review-policy.ts`, `src/utils/coding-conventions.ts` all exist).

## A1. The workspace QA and DevOps operate on never receives the merged developer code — **the biggest defect in the system**

- `executePRWorkflow` does all development inside an isolated git worktree at `<gitRoot>/.worktrees/<slug>` (`src/conductor/pr-workflow.ts:447-487`), pushes the feature branch, and squash-merges the PR **on the remote** via `octokit.pulls.merge` (`pr-workflow.ts:1246-1256`). The worktree and local branch are then deleted (`pr-workflow.ts:1301-1309`).
- Nothing ever fast-forwards the *main* checkout at `state.workspacePath`, which intake left sitting on the system branch (`src/conductor/nodes.ts:339-391`). A grep for `pull |fetch origin|reset --hard` across `src/` finds fetches only in intake and inside the worktree.
- Therefore `qaNode` (`nodes.ts:741`) hands `state.workspacePath` to `createQaUnitAgent` and `devopsNode` (`nodes.ts:920`) hands it to `createDevOpsAgent`, and **both see a tree containing only `docs/` artifacts and `.conventions/` — none of the merged application source.**
- This precisely explains the run 5/6 symptom that Plan 14 diagnosed as an *exploration budget* problem: `qa-unit` burned its whole budget on `list_dir .` → `list_dir tests` → `list_dir src` → `list_dir .` because **`src/` was empty**. Plan 14 raised the budget; the agent now has 25 tool calls to discover the same empty directory.
- Worse, `qaNode:846-857` and `devopsNode:970-981` then `git add . && commit && push` on that stale local branch. Because the remote system branch has advanced by N squash merges, those pushes are non-fast-forward and silently fail (`gitExec` swallows errors and returns an `Error:` string that is only checked for the branch-name lookup).
- Net effect: QA is theatre, DevOps writes a Dockerfile for a project it cannot see, and QA's generated test files are discarded.

## A2. The bug-fix loop re-runs every already-completed assignment

- `assignments` uses the **append** reducer (`src/conductor/state.ts:118-121`).
- `bugfixTriageNode` returns `assignments: output.assignments ?? []` (`nodes.ts:908`), which is appended to the existing list.
- `developmentNode` dispatches the whole list unconditionally: `dispatchDevelopers(apiKey, state.assignments, …)` (`nodes.ts:720`).
- So bug-fix iteration 1 re-dispatches all 26 original assignments **plus** the fixes; iteration 2 does it again. With `MAX_BUGFIX_ITERATIONS=3` the worst case is ~4× the intended development cost. Run 6's 5,115 LLM calls are consistent with this.
- Secondary issue: `developmentNode` also injects `JSON.stringify(state.fileChanges, null, 2)` into the context prompt for **every** dev agent (`nodes.ts:711`). `fileChanges` is append-reduced, so this blob grows monotonically across assignments and iterations.

## A3. QA E2E can never run

- The E2E block is gated on `state.devopsPlan?.serviceUrls?.length > 0` (`nodes.ts:815`).
- `devopsPlan` is only ever set by `devopsNode`, and the graph edges are `qa → (bugfix-triage | devops)` and `devops → finalize` (`src/conductor/graph.ts:93-105`).
- `devopsPlan` is therefore always `null` when `qaNode` runs, on the first pass and on every bug-fix pass. The Playwright MCP integration, the `qa-e2e` agent, `PLAYWRIGHT_MCP_*` config and the E2E section of the README are **unreachable code**.

## A4. Human-in-the-loop mode is broken three ways

1. **No checkpointer.** `graph.compile({ interruptBefore: HITL_PHASES })` (`graph.ts:110-115`) passes no `checkpointer`. LangGraph requires one for `interruptBefore` and for `getState`. `runHumanInTheLoop` calls `conductor.getState(...)` (`run.ts:117`) and both the CLI (`cli.ts:310`) and the server (`index.ts:137`) call it immediately after starting a run.
2. **Mode is read from the environment, not the request.** `buildConductorGraph` branches on the module-level `RUN_MODE` from `src/config.ts:96`. A CLI/API request for `mode: 'human'` while `.env` has `RUN_MODE=autonomous` compiles a graph with **no interrupts at all**, so the entire pipeline runs to completion on the first `invoke` and the "approve each phase" UX is a lie (and vice versa).
3. **"Enhance" is a no-op.** `cli.ts:354-362` collects feedback and calls `session.resume(true, feedback)`; `run.ts:132-144` packs it into an `Approval` and appends it to state. Grepping `approvals|feedback` in `src/conductor/nodes.ts` returns **no matches** — no node ever reads it. The menu says "provide feedback and re-run this phase"; the code approves and advances.
4. Related: `resume(false, …)` returns `null` and abandons the thread (`run.ts:124-128`) — the run never reaches `finalize`, so no reports or token summary are written for a denied run.

## A5. `docker-runner.ts` is dead code; deployment status is an LLM self-report

- `src/executor/docker-runner.ts` exports `buildImage`, `runContainer`, `healthCheck`, `stopContainer` (208 lines, dockerode-based). A grep for these names across `src/` finds **no importers**.
- `devopsPlan.buildStatus`, `runStatus`, `serviceUrls` and `healthChecks` come straight from the DevOps agent's JSON (`nodes.ts:950`, `985-992`). Nothing verifies that the image builds, the container starts, or the service answers. Plan 14 Sub-Plan 7 asked the *prompt* to self-verify — an unenforceable instruction.

## A6. The pre-PR quality gate is npm-only

- `ensureDepsAndRunTests` (`pr-workflow.ts:152-201`) returns `null` unless `package.json` exists with a real `scripts.test`.
- The system ships 11 developer agents covering C#/.NET, Java/Spring, Go and Python (`src/agents/developers/registry.ts`) and convention files for all of them. **Any non-Node project gets no build, no lint, no test gate whatsoever** — reviewers are the only line of defence, and Plan 14 taught them not to block on anything below `major`.
- Also: `afterQaRouter` (`graph.ts:41-47`) drives the bug-fix loop off `state.testReports[].status`, which is whatever `qa-unit` *claims*. A hallucinated `status: 'pass'` skips the loop entirely.

## A7. Agent output is never validated against its schema

- `buildAgent` accepts `cfg.responseFormat` (a Zod schema) but only stringifies it into the prompt (`src/agents/_shared/agent-factory.ts:79-82`); it is **not** passed to `createReactAgent` and never used to `parse`.
- `invokeAgent` (`nodes.ts:151-181`) JSON-parses with three fallbacks and returns whatever comes out. Every consumer is therefore written defensively (`output.architecture?.components ?? []`, `output.testReport?.passed ?? 0`, …), which converts *schema violations into silent zeros* rather than errors. A `testReport` missing `status` silently becomes a pass.
- The same 3-strategy parse is duplicated in `pr-workflow.ts` for dev and reviewer outputs.

## A8. Prompt context is built by dumping full state as pretty-printed JSON

Every pipeline node concatenates `JSON.stringify(state.X, null, 2)`:

| Node | Blobs injected | Location |
|---|---|---|
| architect | requirements + full `codebaseAnalysis` | `nodes.ts:482-487` |
| product-manager | architecture, techStack, epics, requirements, analysis | `nodes.ts:536-546` |
| dba | architecture, techStack, **all** userStories, **all** tasks, analysis | `nodes.ts:591-601` |
| team-leader | architecture, techStack, dbDesign, all stories, all tasks, analysis | `nodes.ts:648-660` |
| development | architecture, techStack, dbDesign, all stories, **all fileChanges**, analysis | `nodes.ts:706-717` |
| qa / devops | architecture, techStack, dbDesign, all stories / all fileChanges | `nodes.ts:760-765`, `937-947` |

`, null, 2` roughly doubles the character count versus compact JSON for no benefit to the model. Every developer agent receives *all* user stories when it needs one. `fileChanges` grows without bound. On top of that, `agent-factory.ts:80` appends the full JSON Schema of the response format to **every** system prompt.

## A9. Observability gaps

- `outputs/<run>/state.json` is documented in the README (line 754) and **never written** — grep for `state.json` in `src/` returns nothing.
- The WebSocket emits exactly four coarse events: `run:started`, `run:phase-complete`, `run:complete`, `run:error` (`src/index.ts:105-182`). Nothing is emitted between phases, so the dashboard's "live event feed" is empty for the multi-hour duration of a run. Transcript, PR states, tool calls and token counters are only visible after the run ends.
- There is no per-run manifest, so correlating a run's PRs / gate results / cost requires reading an 18,000-line log.
- There is **no cost or wall-clock ceiling**. A pathological run can consume the entire monthly quota; nothing degrades or aborts.

## A10. Requirements traceability is not computable

The state has epics → stories → tasks → assignments → PRs, but nothing links a *test* back to an *acceptance criterion*: `TestPlanSchema` items carry only `target`/`description`/`framework` (`src/agents/_shared/schemas/testing.schema.ts:5-27`) and `TestReportSchema` failures carry only `testName`. So "did we actually build and verify what was asked?" is unanswerable, and a story silently dropped by the Team Leader is undetectable.

## A11. Repo hygiene and a false sandbox claim

- `deployAllConventionsToWorkspace` copies **all 16** convention `.md` files (~150 KB, up to 34 KB each) into `<workspace>/.conventions/` (`src/utils/coding-conventions.ts:132-142`) and is called from `developmentNode`, `qaNode` and `devopsNode`. Pipeline nodes then run `git add .`. The root `.gitignore` ignores `.worktrees/` but **not** `.conventions/`, and in `new-repo`/`existing-repo` mode the generated repo has no inherited `.gitignore` at all — so scaffolding ships to the customer inside the delivered product.
- `generated-projects/calc4/.worktrees/calc4-chore-TASK-019-netlify-config/` still exists on disk with a full project tree: worktree cleanup (`pr-workflow.ts:1301-1309`) does not always run (it is skipped when `executePRWorkflow` throws before the `try`).
- `src/tools/shell/shell-tools.ts:1-7` documents itself as "Commands run inside a Docker container (via dockerode) against the generated project workspace — **never directly on the host**. Fallback: if `ALLOW_HOST_SHELL=true` (dev only), runs on host." The implementation is `child_process.exec` on the host, unconditionally (`shell-tools.ts:23-40`); `ALLOW_HOST_SHELL` is never read. LLM-authored shell commands run unsandboxed with no denylist and a caller-chosen timeout.

## A12. Nothing in the system can be tested without the gateway

`tests/greenfield.test.ts` and `tests/maintain.test.ts` call `runAutonomous` for real (`testTimeout: 900_000` in `jest.config.js`). Every pipeline-level regression therefore costs hours and quota, which is why all of Plans 01–15 verified with unit tests plus a manual smoke run. There is no seam for recording/replaying LLM traffic, and intake hard-throws unless the workspace sits inside a git repo with a GitHub remote (`nodes.ts:320-325`), so the system cannot run at all without a GitHub account.

## Sub-Plan 1 — Sync the workspace to the merged system branch (fixes A1)

**Priority: highest. Without this, QA and DevOps are operating on an empty tree and every downstream quality mechanism is measuring nothing.**

### Context you need

- `src/conductor/nodes.ts` holds a private `gitExec(workspacePath, args)` helper (lines 73-88) that **returns** `` `Error: …` `` instead of throwing, a `gitPush(workspacePath, branch, gitContext)` helper (lines 90-96) that pushes via an `https://x-access-token:<token>@github.com/...` URL, and `commitAndPushArtifacts(workspacePath, msg, gitContext, logger)` (lines 107-127).
- `state.workspacePath` is the project directory; in same-repo mode it is a **sub-directory** of the git root (`generated-projects/<name>`), in `new-repo`/`existing-repo` mode it **is** the git root. Intake finds the git root by walking up for `.git` (`nodes.ts:306-326`); `pr-workflow.ts:203-211` has the same logic as `findGitRoot`.
- `state.systemBranch` is `project/<slug>`. PRs are merged into it on the remote.
- Pipeline agents commit doc artifacts directly to the local system branch and push (`commitAndPushArtifacts` is called from the analyzer, architect, PM, DBA and TL nodes), so **local and remote are in sync before development starts**; after development the remote is strictly ahead. The normal reconciliation is therefore a fast-forward.

### Change 1 — new module `src/conductor/workspace-sync.ts`

Export one function plus two small pure helpers so the logic is unit-testable:

```ts
export interface SyncResult {
    ok: boolean;
    /** HEAD sha after the sync (empty on failure). */
    headSha: string;
    /** Human-readable description of what happened, for logs and the transcript. */
    details: string;
    /** Strategy that succeeded: 'already-current' | 'fast-forward' | 'rebase' | 'reset' | 'failed'. */
    strategy: string;
}

/**
 * Bring the local checkout of `branch` up to date with `origin/<branch>`.
 *
 * Developer work is done in throw-away worktrees and squash-merged into the
 * system branch ON THE REMOTE, so the main checkout that QA and DevOps agents
 * read is stale by N merges. Without this sync those agents see a tree with no
 * application source at all (see PART A1).
 *
 * Strategy ladder: already-current → merge --ff-only → rebase → hard reset
 * (the remote is authoritative after squash merges; local-only commits were
 * already pushed by commitAndPushArtifacts).
 */
export function syncWorkspaceToBranch(
    gitRoot: string,
    branch: string,
    gitContext?: GitContext | null,
    opts?: { allowReset?: boolean },
): SyncResult
```

Implementation notes (use the existing `gitExec` style — copy the helper into this module or export it from a shared place; **prefer moving `gitExec`/`gitPush` into `src/utils/git-exec.ts` and importing them in both `nodes.ts` and `workspace-sync.ts`**, since they are currently duplicated verbatim in `nodes.ts:73-96` and `pr-workflow.ts:73-101`):

1. `git worktree prune` — leftover worktrees can hold a lock on the branch.
2. If there are uncommitted changes (`status --porcelain` non-empty), commit them first (`add .`, `commit -m "[<slug>]-chore: pipeline artifacts"`) so nothing is lost by a later reset. Log at info.
3. `fetch origin <branch>` — if this fails, return `{ ok: false, strategy: 'failed' }` and log an **error** (do not throw).
4. If not on `branch`, `checkout <branch>` (create tracking branch from `origin/<branch>` if missing).
5. `rev-parse HEAD` and `rev-parse origin/<branch>`; if equal → `already-current`.
6. `merge --ff-only origin/<branch>` → `fast-forward`.
7. On failure, `rebase origin/<branch>` → `rebase`; abort the rebase on failure (`rebase --abort`).
8. On failure, if `opts.allowReset !== false`, `reset --hard origin/<branch>` → `reset`, logged at **warn** with the diverged shas.
9. Return the new `HEAD` sha and a `details` string like `` `fast-forward: 1a2b3c4 → 9f8e7d6 (37 files, +1204/-12)` `` using `diff --shortstat <old> <new>`.

Add two pure helpers with their own tests:

```ts
/** True when `git status --porcelain` output indicates a dirty tree. */
export function isDirty(porcelainOutput: string): boolean

/**
 * True when the synced workspace looks like it contains no application source
 * (only docs/, .conventions/, README and dotfiles) — a strong signal that
 * PR merges did not land and QA would be meaningless.
 */
export function looksSourceless(relativePaths: string[]): boolean
```

`looksSourceless` treats a path as source if it is not under `docs/`, `.conventions/`, `.worktrees/`, `.github/`, not a dotfile at the root, and not `README.md`/`LICENSE`.

### Change 2 — call it at the four places that matter (`src/conductor/nodes.ts`)

1. **End of `developmentNode`** (after `dispatchDevelopers`, before the `return` at line 724): sync, then run `looksSourceless` over `git ls-files` and log an **error** + push a transcript warning if it trips. Include the sync `details` in the returned transcript.
2. **Top of `qaNode`** (before `deployAllConventionsToWorkspace` at line 748) — idempotent, protects against a HITL resume in a fresh process.
3. **Top of `devopsNode`** (before line 925) — same.
4. **Inside `commitAndPushArtifacts`**: sync *before* committing, and if `gitPush` returns a non-fast-forward error, sync again and retry the push once. Today the failure is logged and forgotten.

Then replace the two hand-rolled commit blocks — `qaNode:846-857` ("QA unit test files") and `devopsNode:970-981` ("DevOps configuration files") — with `commitAndPushArtifacts(...)` calls so they inherit the sync-and-retry behaviour. Keep the existing commit messages verbatim.

Resolve `gitRoot` with the same upward `.git` walk already in `pr-workflow.ts:203-211` (`findGitRoot`); export it from `src/utils/git-exec.ts` and import it in both files rather than adding a third copy.

### Change 3 — config + `.env.example`

```ts

    (process.env.WORKSPACE_SYNC_ALLOW_RESET ?? 'true') === 'true';
```

## Sub-Plan 2 — Assignment lifecycle: never redo completed work (fixes A2)

### Context you need

- `src/conductor/state.ts:118-121` — `assignments` uses the **append** reducer. So does `fileChanges` (124-127) and `bugs` (138-141).
- `src/conductor/nodes.ts:720` — `developmentNode` calls `dispatchDevelopers(apiKey, state.assignments, …)` with the entire accumulated list.
- `src/conductor/nodes.ts:878-914` — `bugfixTriageNode` asks the Team Leader for brand-new assignments and appends them; the loop is bounded by `MAX_BUGFIX_ITERATIONS` (default 3) via `afterQaRouter` (`graph.ts:41-47`).
- `src/agents/developers/dispatcher.ts:151-262` — `dispatchDevelopers` returns `DispatchResult { fileChanges, artifacts, transcript, pullRequests, tokenUsage }`. Each `executePRWorkflow` result carries `pullRequest.assignmentIds` and `pullRequest.status` (`pr-workflow.ts:1278-1292`).
- `Assignment` shape: `src/agents/_shared/schemas/assignment.schema.ts` — `id`, `storyId`, `devAgentId`, `rank`, `priority`, `complexity`, `estimate`, `description`, `dependsOn`, optional `branchName`, `reviewerAgentIds`, `taskType`.

### Change 1 — new pure module `src/conductor/assignment-policy.ts`

```ts
/**
 * Which assignments still need to be dispatched.
 *
 * `assignments` is append-reduced, so after a bug-fix triage round the state
 * holds the original assignments AND the new fix assignments. Dispatching the
 * whole list re-ran every completed assignment on every bug-fix iteration
 * (PART A2) — up to 4x the intended development cost.
 *
 * Also de-duplicates by id (keeping the first occurrence), because a
 * re-prompted Team Leader frequently re-emits an existing assignment id.
 */
export function selectPendingAssignments(
    assignments: Assignment[],
    completedIds: string[],
): Assignment[]

/**
 * Assignment ids that a dispatch round finished. An assignment counts as
 * complete when its PR reached 'merged' or 'approved' — an 'open' or 'failed'
 * PR must be retried by the next iteration.
 */
export function completedIdsFromPullRequests(prs: PullRequest[]): string[]

/**
 * Namespace bug-fix assignment ids so an iteration can never collide with the
 * original assignments or a previous iteration.
 * `ASSIGN-003` + iteration 2 → `BUGFIX-2-ASSIGN-003`.
 */
export function namespaceBugfixAssignments(assignments: Assignment[], iteration: number): Assignment[]

/** De-duplicate bugs by id, keeping the first occurrence (bugs are append-reduced). */
export function dedupeBugs(bugs: Bug[]): Bug[]
```

`namespaceBugfixAssignments` must also rewrite `dependsOn` entries that point at other assignments in the same batch, so the dispatcher's `topoSort` (`dispatcher.ts:28-50`) still resolves. Entries that are not in the batch are left alone (they refer to already-completed work, which `topoSort` treats as never-satisfied — see Change 4).

### Change 2 — new state field (`src/conductor/state.ts`)


Pass `pending` to `dispatchDevelopers` and return `completedAssignmentIds: result.completedAssignmentIds`.

Also fix `topoSort` (`dispatcher.ts:28-50`): it currently loops `while (completed.size < assignments.length)` and treats any unsatisfiable `dependsOn` as a cycle, dumping the remainder into one layer. Seed `completed` with the ids of assignments **not present in the input list** so dependencies on already-merged work are pre-satisfied:

```ts
function topoSort(assignments: Assignment[], preSatisfied: Set<string> = new Set()): Assignment[][]
```

and pass `new Set(completedAssignmentIds)` through from `dispatchDevelopers`.

### Change 5 — bug-fix triage hygiene (`src/conductor/nodes.ts:878-914`)

Filter them out of `openBugs`. If the filtered list is empty, route to `devops` (the existing early-exit at lines 883-890 already does this).

### Change 3 — real phase re-run, via a conditional self-edge

**Design note — read this before implementing.** The obvious approach is `conductor.updateState(config, values, asNode)` to rewind the next node. That API's exact semantics vary across LangGraph versions and it is awkward to unit-test. Use a **version-independent, testable** mechanism instead:

- New state field `pendingRerun: Annotation<PhaseName | null>` (replace reducer, default `null`).
- New state field `phaseFeedback: Annotation<Record<string, string[]>>` with a **merge** reducer (`{ ...existing, ...incoming }`, concatenating arrays per key) so feedback accumulates across enhance rounds.
- For each HITL phase, replace its outgoing `addEdge` with an `addConditionalEdges(phase, rerunRouter(phase), { [phase]: phase, [next]: next })` where:

```ts
/**
 * Route a phase back to itself when the user asked to enhance it.
 *
 * `pendingRerun` is cleared by the node itself at the start of its next
 * execution, so a phase can only re-run once per request. This replaces the
 * previous no-op "enhance" path, which stored feedback in `approvals` that no
 * node ever read (PART A4.3).
 */
function rerunRouter(phase: PhaseName) {
    return (state: ProjectStateType) => (state.pendingRerun === phase ? phase : nextOf(phase));
}
```

- Every HITL node, at its top: if `state.pendingRerun === <its phase>`, log `Re-running <phase> with user feedback` and return `pendingRerun: null` in its update.
- Every HITL node builds its user message with an extra highest-priority section when `state.phaseFeedback[<phase>]` is non-empty:

```
## Reviewer Feedback — you MUST address this
<numbered feedback lines, newest last>
```

Wire this through `buildContext` (Sub-Plan 6) at priority 1 so it is never clipped. **This is the change that makes "enhance" real** — everything else is plumbing.

### Context you need

### Change 1 — new module `src/conductor/security-gates.ts`

```ts
export interface SecurityFinding {
    kind: 'secret' | 'vulnerability' | 'licence';
    severity: 'critical' | 'major' | 'minor';
    file?: string; line?: number;
    detail: string;
    /** Stable id for de-duplication across bug-fix iterations. */
    id: string;
}

/**
 * Regex sweep for hard-coded credentials over git-tracked text files.
 *
 * Offline and dependency-free by design: no scanner binary is assumed. Skips
 * .env.example, .conventions/, .worktrees/, node_modules/, lock files, and
 * anything git does not track.
 */
export function scanForSecrets(workspacePath: string): SecurityFinding[]

/** Per-stack dependency audit. Every command is optional; a missing tool yields no findings. */
export function auditDependencies(workspacePath: string): SecurityFinding[]

/** Flag dependency licences matching LICENCE_DENYLIST (npm `license` fields only, for now). */
export function checkLicences(workspacePath: string): SecurityFinding[]

export function runSecurityGates(workspacePath: string): { findings: SecurityFinding[]; passed: boolean }
```

Secret patterns (keep them in an exported `SECRET_PATTERNS` array so they are testable and extensible):
- `AKIA[0-9A-Z]{16}` (AWS access key id)
- `-----BEGIN (RSA |EC |OPENSSH |DSA )?PRIVATE KEY-----`
- `gh[pousr]_[A-Za-z0-9]{36}` (GitHub tokens)
- `xox[baprs]-[A-Za-z0-9-]{10,}` (Slack)
- `eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}` (JWT)
- generic: `(api[_-]?key|secret|password|passwd|token)\s*[:=]\s*['"][^'"\s]{12,}['"]` — but **not** when the value is an obvious placeholder (`changeme`, `xxx`, `<...>`, `${...}`, `your-...`, `example`).

Audit commands by stack (all soft — missing tool ⇒ skip, never fail):
- node: `npm audit --json --audit-level=high`
- python: `pip-audit -f json` (if on `PATH`)
- go: `govulncheck ./...` (if on `PATH`)
- dotnet: `dotnet list package --vulnerable --include-transitive`
- maven: `mvn -B -q org.owasp:dependency-check-maven:check` **only** when `SECURITY_DEEP_AUDIT=true` (it downloads a large CVE database)

Severity mapping: any secret → `critical`; vulnerability `critical`/`high` → `critical`, `moderate` → `major`, else `minor`; denied licence → `major`.

### Change 1 — new module `src/utils/llm-cassette.ts`

```ts
export type CassetteMode = 'off' | 'record' | 'replay';

/**
 * Record/replay wrapper for LLM HTTP traffic.
 *
 * Sits INSIDE throttledFetch (i.e. wraps oauthFetch) so recordings capture
 * real gateway responses and replays skip the throttle's cooldowns entirely.
 * Enables deterministic, offline, seconds-long pipeline tests where the only
 * option today is an hours-long run against a rate-limited gateway (PART A12).
 */
export function cassetteFetch(inner: typeof globalThis.fetch): typeof globalThis.fetch

export function getCassetteStats(): { mode: CassetteMode; recorded: number; replayed: number; misses: number };
export function _resetCassette(): void
```

- **Key**: `sha256(JSON.stringify({ url, method, body }))` where `body` is the request JSON with volatile fields removed — at minimum any `thread_id`-like value; keep `messages`, `model`, `tools` and `temperature`, since those are what determine the response.
- **Sequence**: keep a per-key counter. Identical requests do occur (an agent re-asked after a tool error), and they must replay in the original order. Store `{ key, seq }`.
- **Storage**: `tests/cassettes/<CASSETTE_NAME>.jsonl`, one JSON object per line (`{ key, seq, status, headers, body }`). JSONL so a crashed recording is still usable, and so diffs are reviewable.
- **Redaction on write**: drop `Authorization` and any header or body field matching `/token|secret|key/i` **before** writing. A cassette is committed to the repo — this is mandatory, not optional. Assert it in the tests.
- **`record`**: pass through, buffer the response body (`response.clone().text()`), append the line, return the original response.
- **`replay`**: return a synthesised `Response` from the stored entry. On a miss, honour `LLM_CASSETTE_ON_MISS`: `strict` (default) throws an error naming the missing key, the request's model and the first 200 chars of the last user message — enough to diagnose which agent drifted; `passthrough` calls `inner` (useful while extending a cassette).
- **Size**: warn when a cassette exceeds `CASSETTE_MAX_MB` (default `25`), and support transparent gzip when the filename ends in `.jsonl.gz`.

### Change 2 — wire the seam (`src/agents/_shared/agent-factory.ts`)

```ts
const base = LLM_CASSETTE_MODE === 'off' ? oauthFetch : cassetteFetch(oauthFetch);

```

In `replay` mode also short-circuit `getAccessToken()` (`src/utils/oauth-auth.util.ts`) to a constant — a replay must not need OAuth credentials. Add a `LLM_CASSETTE_MODE === 'replay'` early return there.

# PART D — Risks and trade-offs

| Change | Risk | Mitigation |
|---|---|---|
| Workspace hard reset (SP1) | Discards local-only commits | Uncommitted work is committed first; ff-only and rebase are tried before reset; gated by `WORKSPACE_SYNC_ALLOW_RESET` |
| QA/DevOps suddenly see real code (SP1) | They will do far more work and cost more tokens than the current no-op | This is the point. `TOOL_PIPELINE_MAX_TOOL_CALLS` (25) still bounds them; SP7 caps total spend |
| Filtering completed assignments (SP2) | A partially-merged branch could be skipped | Only `merged`/`approved` PRs mark completion; `open`/`failed` are retried |
| Real docker build/run (SP3) | Slow; needs a Docker daemon; can leave containers running | `DEVOPS_VERIFY_ENABLED`, hard timeout, all-`skipped` fallback, teardown in `finalize` |
| Deterministic gate overrides `qa-unit` (SP4) | A broken toolchain could fail an otherwise-good run | Missing tools yield `skipped` unless `QUALITY_GATE_STRICT_TOOLCHAIN=true`; both the agent report and the gate report are kept |
| Schema validation (SP5) | A too-strict schema could turn a usable response into a repair loop | Exactly one repair attempt, then the raw object is returned as today; failures are logged, not thrown |
| Context summarisation (SP6) | Removing detail could starve an agent | `CONTEXT_COMPACT=false` restores the old behaviour at runtime; DBA keeps full schema detail; feedback and assignments are priority 1 (never clipped) |
| Degradation ladder (SP7) | Quietly shipping less-reviewed code | Every transition is logged; the manifest records the final level and what was skipped; all limits default to disabled |
| Event bus (SP8) | A chatty run could flood the WebSocket | Ring buffer of 500; `tokens:update` inherits the tracker's 3 s debounce; listeners are try/catch-wrapped |
| Conditional self-edge for HITL re-run (SP9) | An extra conditional edge per phase adds graph complexity | Chosen deliberately over `updateState(asNode)` because it is version-independent and directly unit-testable; `pendingRerun` is cleared by the node so re-runs cannot loop |
| Cassettes (SP13) | Go stale on any prompt change; add repo weight | That staleness *is* the signal — a prompt edit that breaks parsing now fails in seconds. Size warning + gzip; JSONL keeps diffs reviewable |
| `GITHUB_MODE=local` (SP13) | A second code path through PR handling | Confined to `getOctokit`/`gitPush`/intake; the local implementation performs real git merges so behaviour matches |

# PART F — Ideas considered and deliberately not planned

Recorded so they are not re-litigated:

- **Replacing LangGraph / rewriting the orchestrator.** The state machine is not the problem; the data flowing through it is.
- **Multi-agent debate or a critic agent for design phases.** Adds LLM calls to phases that are not currently the cost or quality bottleneck. Revisit after SP10 shows where requirements are actually lost.
- **RAG / embedding index over the generated codebase.** SP6's per-assignment story filtering and the existing `search_code` tool address the same need for projects of this size at a fraction of the complexity.
- **Per-story parallel QA agents.** Pointless until SP1 makes QA see real code and SP4 makes its verdict deterministic; then measure before parallelising.
- **Auto-tuning model selection per agent by observed success rate.** Attractive, but needs the SP8 event stream and several recorded runs as a baseline first.
- **Making `MODEL_PRICING` authoritative.** The current values are documented guesses; SP7 only needs them to be *proportional*. Wire real gateway pricing when it is available rather than inventing more precise fictions.
