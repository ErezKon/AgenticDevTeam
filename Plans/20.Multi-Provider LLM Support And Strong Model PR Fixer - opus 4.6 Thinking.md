# Multi-Provider LLM Support & Strong Model PR Fixer

Add support for Anthropic (`ChatAnthropic`) and Google Gemini (`ChatGoogleGenerativeAI`) alongside the existing OpenAI-compatible provider, with automatic provider detection from model names, plus a "strong model fixer" agent that takes over PRs that exhaust their review iterations.

---

## Current State

- **Agent Factory** (`src/agents/_shared/agent-factory.ts`): All agents are built via `buildAgent()` which always creates a `ChatOpenAI` instance. The `apiKey` is an OAuth bearer token from `getAccessToken()`.
- **Auth Chain**: `oauthFetch` -> `cassetteFetch` -> `throttledFetch` — hardwired to OpenAI-compatible endpoints via `LLM_BASE_URL`.
- **Dependencies**: `@langchain/anthropic` (^0.3.34) and `@langchain/google-genai` (^0.2.18) are already in `package.json` but never used.
- **Per-Agent Models**: Each agent role has its own model env var (e.g., `ARCHITECT_MODEL`, `PRINCIPAL_DEV_MODEL`), all defaulting to `gpt-oss-*`.
- **PR Escalation**: When max review iterations are reached with unresolved CRITICALs, the system escalates to a higher-rank dev agent using the same model tier. No "strong model" override exists.
- **Token Callback**: `TokenUsageCallbackHandler` already handles multiple token usage formats (`promptTokens`, `input_tokens`, etc.) — compatible with all providers.

---

## Sub-Plan 1: Multi-Provider LLM Abstraction Layer

**Goal**: Modify the agent factory to detect the LLM provider from the model name and create the appropriate LangChain chat model class (`ChatOpenAI`, `ChatAnthropic`, or `ChatGoogleGenerativeAI`).

**Scope**: This sub-plan is self-contained and touches configuration + the agent factory. No pipeline logic changes.

### Files to Modify

1. **`src/config.ts`** — Add new env vars:
   - `OPENAI_API_KEY`: API key for OpenAI models (when set, used directly instead of OAuth; falls back to OAuth if empty)
   - `ANTHROPIC_API_KEY`: API key for Anthropic models
   - `GOOGLE_API_KEY`: API key for Google Gemini models
   - `ANTHROPIC_BASE_URL`: Optional base URL override for Anthropic (for proxies)
   - `GOOGLE_BASE_URL`: Optional base URL override for Google (for proxies)
   - `LLM_PROVIDER_DETECTION`: `'auto'` (default) | `'openai'` — force all models through OpenAI-compatible endpoint (escape hatch)

2. **`src/agents/_shared/llm-provider.ts`** — New file: Provider detection & LLM factory:
   - `type LLMProvider = 'openai' | 'anthropic' | 'google'`
   - `detectProvider(modelName: string): LLMProvider` — Pattern matching:
     - `/claude|anthropic/i` -> `'anthropic'`
     - `/gemini|google/i` -> `'google'`
     - Everything else -> `'openai'` (covers `gpt-*`, `o1-*`, `llama-*`, `mistral-*`, and any OpenAI-compatible model)

     - **OpenAI**: `ChatOpenAI` with `OPENAI_API_KEY` (direct) or OAuth fetch chain (fallback), `LLM_BASE_URL`, etc.

   - For OpenAI: JSON mode support (`response_format`) as today
   - For Anthropic/Google: no custom fetch chain (they have their own HTTP handling), no OAuth

   - The `apiKey` parameter remains (used as OAuth fallback for OpenAI provider)

### Implementation Details

```typescript
// src/agents/_shared/llm-provider.ts

import { ChatOpenAI } from '@langchain/openai';
import { ChatAnthropic } from '@langchain/anthropic';
import { ChatGoogleGenerativeAI } from '@langchain/google-genai';
import type { BaseChatModel } from '@langchain/core/language_models/chat_models';

export type LLMProvider = 'openai' | 'anthropic' | 'google';

export function detectProvider(modelName: string): LLMProvider {
    const lower = modelName.toLowerCase();
    if (/claude|anthropic/.test(lower)) return 'anthropic';
    if (/gemini/.test(lower)) return 'google';
    return 'openai';
}

export interface CreateModelOpts {
    modelName: string;
    temperature: number;
    maxTokens?: number;
    timeout?: number;
    callbacks: any[];
    // OpenAI-specific
    apiKey?: string;         // OAuth token
    baseURL?: string;
    customFetch?: typeof fetch;
    jsonMode?: boolean;
}

export function createChatModel(opts: CreateModelOpts): BaseChatModel {
    const provider = detectProvider(opts.modelName);
    
    switch (provider) {
        case 'anthropic':
            return new ChatAnthropic({
                model: opts.modelName,
                temperature: opts.temperature,
                maxTokens: opts.maxTokens,
                anthropicApiKey: ANTHROPIC_API_KEY,
                ...(ANTHROPIC_BASE_URL && { clientOptions: { baseURL: ANTHROPIC_BASE_URL } }),
                maxRetries: 0,
                callbacks: opts.callbacks,
            });
            
        case 'google':
            return new ChatGoogleGenerativeAI({
                model: opts.modelName,
                temperature: opts.temperature,
                maxOutputTokens: opts.maxTokens,
                apiKey: GOOGLE_API_KEY,
                maxRetries: 0,
                callbacks: opts.callbacks,
            });
            
        case 'openai':
        default:
            return new ChatOpenAI({
                model: opts.modelName,
                temperature: opts.temperature,
                maxRetries: 0,
                maxTokens: opts.maxTokens,
                timeout: opts.timeout,
                openAIApiKey: opts.apiKey,
                apiKey: opts.apiKey,
                configuration: {
                    baseURL: opts.baseURL,
                    fetch: opts.customFetch,
                },
                callbacks: opts.callbacks,
                ...(opts.jsonMode && {
                    modelKwargs: { response_format: { type: 'json_object' } },
                }),
            });
    }
}
```

### Key Design Decisions

- **Auto-detect only (no explicit provider config)**: Provider is inferred from the model name. Setting `ARCHITECT_MODEL=claude-sonnet-4-20250514` in `.env` automatically routes to `ChatAnthropic`. No per-agent `_PROVIDER` env vars.
- **OpenAI is the fallback**: Any model name that doesn't match Anthropic/Google patterns goes through `ChatOpenAI`. This preserves backward compatibility for all existing models (`gpt-oss-*`, `llama-*`, `mistral-*`, `gemma-*`).
- **Direct API keys for all providers**: OpenAI uses `OPENAI_API_KEY`, Anthropic uses `ANTHROPIC_API_KEY`, Google uses `GOOGLE_API_KEY`. All three support direct API key authentication for consistency.
- **OpenAI API key priority over OAuth**: When `OPENAI_API_KEY` is set, it is used directly and the OAuth fetch chain is skipped. When empty, the existing OAuth client-credentials flow is used as a fallback. This makes the system work out-of-the-box with a standard OpenAI API key while preserving backward compatibility for enterprise OAuth setups.
- **Throttle/Cassette only for OpenAI OAuth path**: The custom fetch chain (cassette recording, throttle) only applies when using OAuth for OpenAI models. Direct API key and Anthropic/Google paths rely on `retryWithBackoff` at the invocation level.
- **`LLM_PROVIDER_DETECTION=openai`**: Escape hatch to force all models through OpenAI-compatible endpoint (useful if running Anthropic/Google models through an OpenAI-compatible proxy).

- **JSON mode differences**: Anthropic doesn't have `response_format: { type: 'json_object' }`. The schema instruction in the prompt is the primary mechanism (already used), so this should work. Anthropic supports structured output via tool_use or prompt-based JSON.
- **Token usage reporting**: `TokenUsageCallbackHandler` already handles multiple formats. Verify Anthropic/Google report usage in callbacks.

## Sub-Plan 2: Strong Model PR Fixer

**Goal**: When a dev agent's PR exhausts max review iterations, create a new "strong fixer" agent using a dedicated powerful model that reviews the full context (task, code, review comments) and fixes the issues.

**Scope**: Modifies PR workflow and config. Depends on Sub-Plan 1's multi-provider abstraction (the strong model could be from any provider).

### Files to Modify

1. **`src/config.ts`** — Add new env vars:
   - `STRONG_FIXER_MODEL`: Model to use for the strong fixer agent (e.g., `claude-opus-4.6`, `gpt-4o`). Default: empty (uses `PRINCIPAL_DEV_MODEL`)
   - `STRONG_FIXER_ENABLED`: `'true'` | `'false'` (default: `'true'`) — enable/disable the strong fixer
   - `STRONG_FIXER_MAX_TOOL_CALLS`: Max tool calls for the fixer agent (default: 40)
   - `PR_EXHAUSTION_STRATEGY`: `'escalate-then-fix'` (default) | `'fix-only'` | `'escalate-only'` — controls whether the existing rank-based escalation, the strong fixer, or both run when max review iterations are hit

2. **`src/conductor/pr-workflow.ts`** — Refactor escalation + add strong fixer step:
   - Wrap the existing escalation check (section 3b, ~line 1644) in a `PR_EXHAUSTION_STRATEGY` guard:
     - `'escalate-only'` or `'escalate-then-fix'`: run existing escalation logic
     - `'fix-only'`: skip escalation
   - After escalation (or instead of it for `'fix-only'`), add new section "3c. Strong Model Fixer":
     - Triggers when: `STRONG_FIXER_ENABLED === true` AND `prStatus` is still `'open'` or `'escalated_open'`
     - Also respects run budget (`getEffectiveLimits()`)
     - Creates a new dev agent using `STRONG_FIXER_MODEL` (or defaults to `PRINCIPAL_DEV_MODEL`)
     - The fixer gets comprehensive context:
       - Original task/assignment description
       - All review comments (from all iterations, all reviewers)
       - The current code diff against the base branch
       - The PR description and title
       - Quality gate results (if available)
       - Integrity findings (if available)
     - The fixer agent writes code, commits
     - After the fix, runs quality gates
     - Then runs a final review with a reviewer using the same strong model tier
     - If approved: proceed to merge
     - If still not approved: PR remains in its current state (blocked/open)

3. **`src/agents/developers/dev-agent.builder.ts`** — Add `buildStrongFixerAgent()`:
   - New function that creates a dev agent with the strong fixer model
   - Uses `principal` rank persona (highest capability)
   - Gets workspace (fs) + shell tools (same as regular dev agents)
   - Higher tool call budget (`STRONG_FIXER_MAX_TOOL_CALLS`)

4. **`.env.example`** — Add documentation for new env vars

5. **`AI_Context.md`** — Update PR Workflow section

### Implementation Details

The strong fixer step in `pr-workflow.ts`:

```typescript
// ── 3c. Strong Model Fixer ──────────────────────────────────────
// When the PR is still open after regular escalation and STRONG_FIXER_ENABLED,
// invoke a powerful model to do a comprehensive fix pass.
if (STRONG_FIXER_ENABLED && (prStatus === 'open' || prStatus === 'escalated_open')) {
    log.info(`Invoking strong model fixer for PR #${ghPr.number}...`);
    
    // Collect ALL review comments from all iterations
    const allComments = allReviews.flatMap(r => r.comments);
    
    // Get the current full diff
    const fullDiff = gitExec(worktreeWorkspace, `diff ${baseRef}...HEAD -- . ${DIFF_EXCLUDE_SPECS}`);
    
    // Build the strong fixer agent
    const fixerAgent = buildStrongFixerAgent(apiKey, worktreeWorkspace, gitContext, baseBranch, conventionFiles, isMaintainMode);
    
    const fixerMsg = [
        `## STRONG FIXER — PR #${ghPr.number}: ${prTitle}`,
        `\nYou are a SENIOR EXPERT developer taking over a PR that has exhausted its review iterations.`,
        `Your job: read the task, understand the review feedback, and fix ALL issues to get this PR merged.`,
        `\n## Original Task\n${contextPrompt}`,
        `\n## PR Description\n${prBody}`,
        `\n## All Review Comments (${allComments.length} total)\n${JSON.stringify(allComments, null, 2)}`,
        `\n## Current Diff\n\`\`\`diff\n${truncate(fullDiff, 30000)}\n\`\`\``,
        gateReport ? `\n## Quality Gate Results\n${gateReportToMarkdown(gateReport)}` : '',
        `\n## Instructions`,
        `1. Read and understand ALL review comments.`,
        `2. Fix every issue raised by reviewers.`,
        `3. Ensure quality gates will pass (build, lint, test).`,
        `4. Do NOT weaken tests or build configuration.`,
    ].join('\n');
    
    try {
        const { output, tokenUsage } = await invokeDevAgent(fixerAgent, fixerMsg, ...);
        // Commit, run quality gates, then do a final review
    } finally {
        commitWorktree(...);
    }
    
    // Final review with strong model reviewer
    // If approved -> merge
}
```

### Key Design Decisions

- **Configurable strategy (`PR_EXHAUSTION_STRATEGY`)**: Three modes:
  - `'escalate-then-fix'` (default): Run the existing rank-based escalation first. If still unresolved, run the strong fixer.
  - `'fix-only'`: Skip rank-based escalation entirely. Go straight to the strong fixer.
  - `'escalate-only'`: Keep existing behavior only. No strong fixer (backward-compatible).
- **Comprehensive context**: Unlike the regular fix step (which only gets the latest reviewer comments), the strong fixer gets ALL comments from all iterations, the full diff, and the original task.
- **Uses configurable model**: `STRONG_FIXER_MODEL` can be set to any model (e.g., `claude-opus-4.6`). Combined with Sub-Plan 1, this automatically uses the right provider.
- **Budget-aware**: The strong fixer respects the run budget. If the budget is exhausted, it won't run.
- **Single pass**: The fixer gets one attempt. It doesn't enter a new review loop — it does one fix pass and one review.

### Risks

- **Cost**: Strong models are expensive. A single fixer invocation with full context could cost significantly more than regular dev agents. Mitigation: the run budget (`MAX_RUN_COST_USD`) caps total spend.
- **Context size**: Dumping all review comments + full diff + task could exceed context windows. Mitigation: truncate the diff, summarize older review comments.
- **Infinite cost spiral**: If the fixer itself produces poor code, it won't loop. One attempt, one review, done.
