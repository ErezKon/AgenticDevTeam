# AgenticDevTeam Resilience Overhaul — Budget-Aware Task Decomposition and Failure Containment

Fix 7 bugs identified in the pacmanclaude3 run, plus restructure task sizing and budget allocation to prevent the cascading failures caused by oversized scaffold assignments.

---

## Root Cause Chain

The run's failures form a causal chain:
1. **Oversized scaffold assignment** (ASSIGN-001: complex/3d estimate, ~20 files) exhausted principal-frontend's turn budget (28/28), requiring a respawn
2. Respawn wasted budget re-reading files, but eventually finished scaffold; meanwhile **senior-frontend crashed** repeatedly due to Bug 1 (`cache_control` on thinking blocks)
3. Combined time pressure caused **branch wall-time budget to exceed 900s** before review, so scaffold PR was never reviewed (Bug 3)
4. Quality gates failed, repair attempt also crashed (Bug 1 again), and **PR was opened despite failures** (Bug 4)
5. Feature branches were created from pre-scaffold state, missing scaffold code (Bug 5)

## Part A: Bug Fixes (Code Defects)

### A1 (P0): Fix `blocksWithTrailingBreakpoint()` — skip thinking blocks

**File:** `src/agents/_shared/prompt-cache.ts` (lines 107-118)

**Root cause:** `blocksWithTrailingBreakpoint()` adds `cache_control: { type: 'ephemeral' }` to the LAST content block. When `sanitizeStreamingContentBlocks()` (which runs earlier in `wrapModelCall`) strips tool_use blocks that are redundant with `tool_calls`, content can become `[thinking_block]` only. The function then puts `cache_control` on the thinking block. `@langchain/anthropic@1.5.4` faithfully forwards `cache_control` from thinking blocks to the API (confirmed in `node_modules/@langchain/anthropic/dist/utils/message_inputs.cjs` line 133), and the Anthropic API rejects it.

**Evidence:** All 3 occurrences hit the same path — `messages.X.content.0.thinking.cache_control: Extra inputs are not permitted`. The team leader response (full-response 004) confirms models produce thinking blocks (`type: "thinking"` with `signature`).

**Fix:** Scan backwards from the end of the blocks array for the last block whose `type` is NOT `thinking` or `redacted_thinking`. Place `cache_control` on that block. If all blocks are thinking blocks, return `null` to skip breakpoint placement.

```typescript
// In blocksWithTrailingBreakpoint(), replace the last-block selection:
const THINKING_TYPES = new Set(['thinking', 'redacted_thinking']);
let targetIdx = -1;
for (let i = blocks.length - 1; i >= 0; i--) {
    const b = blocks[i];
    if (b !== null && typeof b === 'object' && !THINKING_TYPES.has(b.type)) {
        targetIdx = i;
        break;
    }
}
if (targetIdx < 0) return null; // all blocks are thinking — skip breakpoint
blocks[targetIdx].cache_control = EPHEMERAL;
```

### A2 (P0): Track dev agent failures — distinguish crash from completion

**File:** `src/conductor/pr/orchestrator.ts` (lines 198-304)

**Root cause:** The dev agent loop's `catch` block at line 282-289 logs the error but doesn't track it. After the loop, line 304 unconditionally says `"All N assignment(s) complete"`. Partial work from crashed agents is committed (line 291-292) and proceeds through quality gates and PR creation.

**Fix:**
1. Add a `failedAgentIds: Set<string>` before the dev loop (line 197).
2. In the non-budget catch block (line 286-289), add the devId to `failedAgentIds`.
3. After the loop (line 304), if `failedAgentIds.size > 0`:
   - Log `"N of M assignment(s) completed (K agent(s) crashed: [ids])"` instead of `"All N complete"`.
   - Emit a `branch:partial-failure` event.
   - Set a `hasDevFailures` flag used later in A4.

### A3 (P1): Guarantee minimum 1 review iteration

**File:** `src/conductor/pr/review-loop.ts` (lines 102-110)

**Root cause:** The budget check at line 104 is the first thing inside the review loop. When branch wall time exceeds `MAX_BRANCH_WALL_MS` before the first review iteration, the loop breaks immediately — the PR is opened but never reviewed.

**Fix:** Allow iteration 1 to run regardless of budget:
```typescript
const reviewBudgetReason = checkBranchBudget(`before review iteration ${iteration}`);
if (reviewBudgetReason) {
    if (iteration > 1) {
        log.warn(`Branch ${branchName} budget exceeded: ${reviewBudgetReason} — ending review loop`);
        // ... existing break logic ...
        break;
    }
    log.warn(`Branch ${branchName} budget exceeded: ${reviewBudgetReason} — proceeding with mandatory first review`);
}
```

### A4 (P1): Block PR creation when critical quality gates fail

**File:** `src/conductor/pr/orchestrator.ts` (between lines 375 and 377)

**Root cause:** After the quality gate repair loop, the orchestrator proceeds to PR creation regardless of gate status. PRs are opened with known typecheck/build failures.

**Fix:** After the gate repair section (around line 375), before the "check for actual commits" section (line 377):
```typescript
if (gateReport && !gateReport.passed) {
    const criticalSteps = ['typecheck', 'build'];
    const criticalFailures = gateReport.results
        .filter(r => !r.passed && !r.skipped && criticalSteps.includes(r.step));
    if (criticalFailures.length > 0) {
        const failedSteps = criticalFailures.map(f => f.step).join(', ');
        log.error(`Critical gates still failing on ${branchName}: ${failedSteps} — skipping PR`);
        allTranscript.push(msg('conductor', `BLOCKED: ${failedSteps} still failing after repair`));
        emitRunEvent('branch:gates-blocked', { branchName, failedSteps });
        // Salvage the worktree for debugging
        if (outputPath) salvageWorktree(worktreeWorkspace, gitRoot, baseRef, branchName, 'critical-gates-failed', outputPath);
        return { pullRequest: { /* ...gates-failed status... */ }, ... };
    }
}
```

Also: when `hasDevFailures` is true (from A2), append a warning section to the PR body indicating which agents crashed and that some work may be incomplete.

### A5 (P1): Propagate scaffold work to feature branches on merge failure

**File:** `src/agents/developers/dispatcher.ts` (around line 670)

**Root cause:** When the scaffold branch fails to merge, the dispatcher logs an error but continues creating feature branches from the pre-scaffold base. Feature branches then lack scaffold code, causing typecheck/build failures.

**Fix:** When scaffold fails to merge, record the scaffold branch ref as a fallback base:
```typescript
let scaffoldFallbackRef: string | undefined;

// After scaffold merge check (line 667):
if (scaffoldPR?.status === 'merged') {
    syncWorkspaceToBranch(gitRoot, baseBranch);
} else {
    log.error(`Scaffold branch ${scaffoldBranch} failed to merge — using scaffold tip as fallback base`);
    scaffoldFallbackRef = scaffoldBranch;
    // Sync workspace to the scaffold branch tip instead of base
    syncWorkspaceToBranch(gitRoot, scaffoldBranch);
}
```

Then when creating worktrees for feature branches later, if `scaffoldFallbackRef` is set, create them from the scaffold branch tip rather than from `baseBranch`.

## Part B: Task Decomposition + Budget Scaling

### B1: Update TL prompt to split scaffold into smaller assignments

**File:** `src/agents/team-leader/team-leader.prompt.ts` (lines 129-141)

**Current problem:** Lines 129-134 explicitly tell the TL to pack ALL scaffolding into one assignment: project config, type definitions, data files, and module stubs. This created ASSIGN-001 (complex/3d) which exhausted the principal-frontend's budget.

**Fix:** Replace the `<integration_check>` scaffold instructions (lines 129-134) with guidance to split scaffold into 2-3 focused assignments:

```
The SCAFFOLD should be split into MULTIPLE assignments on the same branch to prevent budget exhaustion:
  a. **Config & Entry Points** (principal): package.json with scripts, tsconfig, bundler config,
     index.html, main entry (e.g. main.tsx, server.ts). This assignment creates the build pipeline.
  b. **Type Definitions & Frozen Data** (senior): All shared type files (types.ts, interfaces),
     frozen data files (layout data, constants, palettes), and the service worker registration.
  c. **Module Stubs** (junior or senior): Interface stub files (throw new Error('not implemented'))
     for every remaining module path in the contract. These stubs exist ONLY so parallel branches
     compile; they will be replaced by real implementations in feature branches.
     IMPORTANT: Tag the assignment description with "[STUBS]" so reviewers know these are intentional.

Each scaffold assignment MUST depend on the previous one (b depends on a, c depends on b).
All scaffold assignments share the same branch: "{project-slug}/chore/scaffold".
```

### B2: Add scope feasibility validation in plan-coverage.ts

**File:** `src/conductor/plan-coverage.ts` (add checks in `validateAssignmentPlan()`)

Add new violation checks after the existing coverage validation:

```typescript
// Scope feasibility: flag oversized assignments
const COMPLEXITY_CONCERN_THRESHOLD = new Set(['complex', 'very-complex']);
const ESTIMATE_CONCERN_RE = /^[3-9]d$|^\d{2,}d$/; // 3d+ or 10d+

for (const a of state.assignments ?? []) {
    // Flag assignments that are both complex AND have high estimates
    if (COMPLEXITY_CONCERN_THRESHOLD.has(a.complexity) && ESTIMATE_CONCERN_RE.test(a.estimate)) {
        violations.push({
            kind: 'oversized-assignment',
            severity: 'major',
            id: a.id,
            detail: `Assignment ${a.id} is ${a.complexity} with estimate ${a.estimate} — consider splitting into smaller assignments`,
        });
    }

    // Flag agents with too many tasks on one branch
    const agentAssignmentsOnBranch = (state.assignments ?? [])
        .filter(other => other.devAgentId === a.devAgentId && other.branchName === a.branchName);
    const totalTasks = agentAssignmentsOnBranch.reduce((sum, o) => sum + (o.taskIds?.length ?? 0), 0);
    if (totalTasks > 6) {
        violations.push({
            kind: 'agent-overloaded',
            severity: 'major',
            id: a.devAgentId,
            detail: `Agent ${a.devAgentId} has ${totalTasks} tasks on branch ${a.branchName} — risk of budget exhaustion`,
        });
    }
}
```

This triggers the existing repair loop (lines 370-395 of `planning.ts`) which re-invokes the TL with a gap prompt to fix the violations.

### B3: Per-assignment invocations in orchestrator

**File:** `src/conductor/pr/orchestrator.ts` (lines 190-294)

**Current problem:** All of an agent's assignments on a branch are batched into ONE invocation message. The agent gets one tool budget for all assignments combined. A crash on one assignment kills all remaining assignments for that agent.

**Fix:** Change the dev agent loop to invoke per-assignment instead of per-agent:

```typescript
// BEFORE (lines 190-294):
const byDev = new Map<string, Assignment[]>();
for (const a of assignments) { ... }
for (const [devId, devAssignments] of byDev) {
    // ONE invocation with ALL assignments for this agent
    const message = `... ${assignmentText} ...`;
    const result = await invokeDevAgent(agent, message, ...);
}

// AFTER:
// Sort assignments by dependsOn order
const sortedAssignments = topologicalSort(assignments);
for (const assignment of sortedAssignments) {
    const devId = assignment.devAgentId;
    const entry = getDevAgent(devId);
    // Build a fresh agent per assignment (fresh budget)
    const agent = buildAgentFn(entry, assignment.complexity);
    const assignmentText = `Assignment ${assignment.id} [${assignment.priority}/${assignment.complexity}]: ${assignment.description}`;
    const message = [contextPrompt, snapshotSection, storySection, ...].join('\n');
    
    try {
        const result = await invokeDevAgent(agent, message, ...);
        // Commit after each assignment
        commitWorktree(worktreeWorkspace, branchName, ...);
    } catch (err) {
        // Track failure but continue with next assignment
        failedAssignments.push(assignment.id);
        commitWorktree(worktreeWorkspace, branchName, ...);
    }
}
```

Key changes:
- Each assignment gets its own invocation with a fresh tool budget
- A crash on one assignment doesn't block others
- Commits happen after each assignment, not just on failure
- Later assignments see the files created by earlier ones
- The `buildAgentFn` accepts complexity for budget scaling (see B4)

### B4: Complexity-aware budget scaling

**Files:**
- `src/agents/_shared/tool-loop-guard.ts` — modify `resolveToolBudgets()` signature and logic
- `src/agents/developers/dev-agent.builder.ts` — pass complexity through to budget resolution
- `src/conductor/pr/orchestrator.ts` — pass complexity when building agents

Add complexity multipliers to `resolveToolBudgets`:

```typescript
const COMPLEXITY_MULTIPLIERS: Record<string, number> = {
    'trivial': 0.75,
    'simple': 0.75,
    'moderate': 1.0,
    'complex': 1.5,
    'very-complex': 2.0,
};

export function resolveToolBudgets(
    rank: string,
    jsonOverride?: string,
    complexity?: string, // NEW parameter
): Required<ToolBudgets> {
    const base = DEFAULT_BUDGETS[rank] ?? DEFAULT_BUDGETS.default;
    let resolved = { ...base };
    
    // Apply JSON override
    if (jsonOverride) { /* existing logic */ }
    
    // Apply complexity scaling (primarily to turns, the binding constraint)
    const multiplier = COMPLEXITY_MULTIPLIERS[complexity ?? 'moderate'] ?? 1.0;
    if (multiplier !== 1.0) {
        resolved.turns = Math.round(resolved.turns * multiplier);
        resolved.writes = Math.round(resolved.writes * multiplier);
        // reads and shell stay at base — they're rarely the bottleneck
    }
    
    return resolved;
}
```

Budget effect for principal rank:
| Complexity | Turns (base 28) | Writes (base 30) |
|-----------|-----------------|-------------------|
| trivial/simple | 21 | 22 |
| moderate | 28 | 30 |
| complex | 42 | 45 |
| very-complex | 56 | 60 |

## Risks / Considerations

- **B3 (per-assignment invocations):** Most significant structural change. The current batched approach was intentional — it lets the agent see all its assignments at once and plan holistically. With per-assignment invocations, the agent can't coordinate across assignments. Mitigation: include a "Previously completed assignments on this branch" section in the message so the agent knows what already exists.

- **B4 (complexity scaling):** `very-complex` assignments getting 56 turns could be expensive (more LLM calls). But this is still cheaper than the current behavior (28 turns + respawn + 28 turns = 56 turns anyway, with the overhead of re-reading everything).

- **B2 (scope validation):** The `major` severity means the TL gets re-invoked with a gap prompt. If the TL doesn't know HOW to split, it might produce the same plan. The TL prompt changes in B1 are needed for this to work reliably.

- **A4 (block PR on gate failures):** Could prevent PRs from being opened for debugging. Mitigation: the salvaged worktree preserves the branch state for manual inspection.

- **A5 (scaffold fallback):** Creating feature branches from the scaffold tip changes the merge base. The PR diff will show scaffold changes + feature changes. Mitigation: this is better than the current behavior where features fail to compile at all.

- **Plan 25 compatibility:** None of these changes conflict with Plan 25's structural refactoring (module splits, async migration, RunContext). Plan 25 didn't modify `blocksWithTrailingBreakpoint()`, the dev loop error handling, the review budget check, or the TL prompt.
