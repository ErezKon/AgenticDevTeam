# Plan 23 — Continue Run: Implementation Report

## Sub-Plan 01: State Collector

**Status:** Implemented  
**File:** `src/conductor/continue/state-collector.ts`

### What Was Built

A read-only artifact collector that scans a stopped run's output directory and workspace, producing a structured `CollectedRunState` object. This is the foundation that all downstream sub-plans depend on.

### Exported API

| Function | Purpose |
|----------|---------|
| `collectRunState(outputPath)` | Main entry — reads all artifacts into a `CollectedRunState` |
| `findRunOutputs(identifier)` | Locates a run's output directory by absolute path, relative path, name, or timestamp prefix |
| `listStoppedRuns()` | Scans `outputs/` for runs with status != 'completed' (for CLI menu) |

### CollectedRunState Shape

```typescript
interface CollectedRunState {
    stateSnapshot: Record<string, any> | null;  // from state.json
    manifest: RunManifest | null;                // from run-manifest.json
    ledgerEntries: LedgerEntry[];                // from ledger.jsonl
    responseIndex: ResponseLogEntry[];           // from full-responses/index.jsonl
    agentArtifacts: AgentArtifact[];             // from docs/agents/*.md
    gitBranches: { local: string[]; remote: string[] };
    gitLog: GitLogEntry[];
    workspaceFiles: string[];
    prBranchStatus: BranchStatus[];
    outputPath: string;
    workspacePath: string;
    workspaceExists: boolean;
    workspaceIsGitRepo: boolean;
    salvagePatches: string[];
    tokenUsageRecords: Record<string, any>[];
}
```

### Key Design Decisions

1. **Read-only** — No files are modified, no git commands mutate state. Safe to call repeatedly.
2. **Never throws** — Individual artifact collection failures are logged as warnings; the corresponding field gets its empty/null default.
3. **Workspace resolution** — Tries three strategies: `state.json → workspacePath`, `state.json → input.existingProjectPath` (maintain mode), and inferred from `systemName` slug (greenfield convention).
4. **PR branch status inference** — Derives status from `pullRequests` array in state.json, cross-referenced with `salvageBranches` and local git branches.
5. **Reuses existing utilities** — `readLedger()` from `run-ledger.ts`, `readResponseLogIndex()` from `response-log.ts`, `gitExec()` from `git-exec.ts`.

## Sub-Plan 02: State Reconstructor (+ Sub-Plan 03: Phase Resolver)

**Status:** Implemented  
**File:** `src/conductor/continue/state-reconstructor.ts`

### What Was Built

A state reconstructor that builds a valid `ProjectState` from the collected artifacts and determines the correct pipeline phase to resume from. Sub-Plan 03 (Phase Resolver) is integrated into this file as the `resolveResumePhase()` function since the two are tightly coupled.

### Exported API

| Function | Purpose |
|----------|---------|
| `reconstructState(collected)` | Main entry — returns `ReconstructedState` with state, resumePhase, confidence, and warnings |

### ReconstructedState Shape

```typescript
interface ReconstructedState {
    state: Record<string, any>;           // ready to inject into the graph
    resumePhase: PhaseName;               // first incomplete phase
    confidence: 'full' | 'partial' | 'minimal';
    warnings: string[];
}
```

### Three Reconstruction Paths

| Path | Trigger | Confidence |
|------|---------|-----------|
| **Primary** | `state.json` exists | `full` |
| **Fallback** | Only `run-manifest.json` exists | `partial` |
| **Degraded** | Only `ledger.jsonl` exists | `minimal` |

### Secret Rehydration

Secrets redacted by `writeStateSnapshot()` are restored from the current `.env`:

| Field | Source |
|-------|--------|
| `gitContext.token` | `GITHUB_PROJECT_TOKEN` or `GITHUB_TOKEN` |
| `gitContext.owner` | From state (preserved) or `GITHUB_PROJECT_OWNER` / `GITHUB_OWNER` |
| `gitContext.repo` | From state (preserved) or `GITHUB_REPO` |
| `gitContext.defaultBranch` | From state (preserved) or `GIT_DEFAULT_BRANCH` |

A deep-walk of the state tree warns about any remaining `***REDACTED***` values that couldn't be rehydrated.

### Phase Resolution Algorithm

1. Read `state.phase` — the phase active when the run stopped
2. Extract completed phases from ledger (`kind='phase'`, `event='end'`)
3. Walk through phases in pipeline order, checking both ledger evidence and state contents
4. Resume from the first phase whose evidence is incomplete

**Phase-specific evidence checks:**

| Phase | Complete When |
|-------|-------------|
| `intake` | `workspacePath` + `outputPath` set (always skip on continue) |
| `codebase-analyzer` | `codebaseAnalysis` not null (maintain only) |
| `architect` | `architecture` not null + `epics.length > 0` |
| `product-manager` | `userStories.length > 0` + `tasks.length > 0` |
| `dba` | Ledger says complete (dbDesign may legitimately be null) |
| `team-leader` | `assignments.length > 0` |
| `development` | `fileChanges.length > 0` or `pullRequests.length > 0` |
| `qa` | `testReports.length > 0` |
| `bugfix-triage` | Ledger says complete |
| `devops` | `devopsPlan` not null |
| `e2e` | `e2eStatus !== 'not-run'` |
| `acceptance-gate` | `acceptance` not null |
| `finalize` | Always re-run |

**Development phase special handling:** Counts pending assignments (same dedup + filter logic as `selectPendingAssignments` in `assignment-policy.ts`). If all assignments are completed but the phase didn't finish cleanly, advances past development.

### Field Validation

Best-effort validation of key state fields (never fails, logs warnings):
- Arrays are verified to be arrays (reset to `[]` if not)
- Objects are verified to be objects (reset to defaults if not)
- `phase` is validated against the `PhaseName` enum
- `iteration.bugfix` is verified to be a number
- `e2eStatus` is validated against the allowed enum values

## Sub-Plan 03: Phase Resolver

**Status:** Implemented (integrated into Sub-Plan 02)  
**File:** `src/conductor/continue/state-reconstructor.ts`

### What Was Built

The Phase Resolver determines which pipeline phase to resume from based on state evidence and ledger data. It is integrated into the State Reconstructor file since the two are tightly coupled — the resolver needs the reconstructed state to inspect, and the reconstructor calls the resolver as its final step.

### Internal Functions

| Function | Purpose |
|----------|---------|
| `resolveResumePhase(state, collected, warnings)` | Main resolver — cross-validates ledger + state evidence |
| `resolveResumePhaseFromLedger(entries, state, warnings)` | Degraded fallback for ledger-only reconstruction |
| `getCompletedPhases(entries)` | Extract completed phases set from ledger `kind='phase'` + `event='end'` |
| `isPhaseComplete(phase, state, completed, runType)` | Per-phase evidence check |
| `countPendingAssignments(state)` | Development-phase special handling |
| `detectSystemBranch(collected)` | Git branch detection for degraded mode |

### Algorithm

1. Read `state.phase` — the phase active when the run stopped
2. Extract completed phases from ledger entries (`kind='phase'`, `event='end'`)
3. Walk through phases in pipeline order, checking both ledger evidence and state contents
4. Resume from the first phase whose evidence is incomplete

### Special Cases

- **Development phase:** Counts pending assignments using the same dedup + filter logic as `selectPendingAssignments()` in `assignment-policy.ts`. If all assignments completed but the phase didn't finish cleanly, advances past development.
- **Bugfix loop:** Preserved via `iteration.bugfix` counter and `fixedBugIds` — the resolver doesn't reset these.
- **Greenfield vs. Maintain:** `codebase-analyzer` phase is skipped for greenfield runs.
- **Finalize:** Always re-run (writes final reports).

## Sub-Plan 04: Graph Entry Point

**Status:** Implemented  
**Files Modified:** `src/conductor/state.ts`, `src/conductor/nodes.ts`, `src/conductor/run.ts`, `src/utils/token-tracker.ts`  
**Test Files Updated:** 6 test files (added new state fields to mock objects)

### What Was Built

The core mechanism that allows the LangGraph graph to resume execution from any phase by injecting reconstructed state with continuation flags. All completed pipeline nodes skip execution via idempotency guards.

### Approach: State Injection + Node-Level Idempotency

Rather than modifying the graph topology or creating synthetic checkpoints, the implementation uses a simpler approach:

1. Pass the full reconstructed state as the initial input to `conductor.invoke()`
2. Each node checks `shouldSkipOnContinue()` and returns immediately if its phase index is before the resume phase
3. The graph flows through all edges but completed nodes return `{}` (no-op)
4. The `intakeNode` already had its own idempotency guard (`if (state.outputPath && state.workspacePath)`)

### Changes by File

#### `src/conductor/state.ts`

Added two new internal state fields:

| Field | Type | Default | Purpose |
|-------|------|---------|---------|
| `_isContinuation` | `boolean` | `false` | When true, nodes before `_resumePhase` skip execution |
| `_resumePhase` | `PhaseName \| null` | `null` | The phase to resume from (set by `continueRun()`) |

#### `src/conductor/nodes.ts`

**New helper function:**

```typescript
function shouldSkipOnContinue(
    state: ProjectStateType,
    currentPhase: PhaseName,
    logger: ReturnType<typeof getLogger>,
): boolean
```

Returns `true` when: `_isContinuation` is true AND `_resumePhase` is set AND the current phase's index is strictly before the resume phase's index. Nodes at or after the resume phase execute normally. Conservative — returns `false` if indices cannot be resolved.

Uses `CONTINUE_PHASE_ORDER` and `CONTINUE_PHASE_INDEX` (a `Map<PhaseName, number>`) defined at module level.

## Sub-Plan 05: Singleton Rehydration

**Status:** Implemented  
**File Created:** `src/conductor/continue/singleton-rehydration.ts`  
**Files Modified:** `src/conductor/run.ts`, `src/conductor/continue/index.ts`

### What Was Built

A dedicated module that reinitialises all global singletons that `intakeNode` normally sets up. Since intake is skipped on continuation (its idempotency guard fires because `outputPath` and `workspacePath` are already set), this module replicates the singleton setup so downstream nodes have a fully initialised run infrastructure.

This replaces the inline `rehydrateSingletons()` function that was previously embedded in `run.ts` as part of SP-04.

### Exported API

| Function | Purpose |
|----------|---------|
| `rehydrateSingletons(collected, state)` | Main entry — reinitialises all global singletons for a continued run |

### Singletons Rehydrated

| Singleton | Function Called | Behavior |
|-----------|----------------|----------|
| **Run log** | `setRunLogPath()` | Points to `<outputPath>/run.log` — new entries are appended, preserving the original run's log |
| **Ledger** | `initLedger()` | Sets the output path for `appendLedger()` — existing `ledger.jsonl` entries are preserved |
| **Response log** | `initResponseLog()` | Resets the sequence counter and creates `full-responses/` if needed — `index.jsonl` is append-only |
| **Token tracker** | `tokenTracker.enablePersistence()` | Points persistence at `outputPath`, creates the initial JSON snapshot |
| **Token history** | `tokenTracker.recordFromPreviousRun()` | Restores all previous token usage records so budget calculations are accurate |
| **Token report** | `refreshTokenReport()` | Writes the initial HTML report skeleton |
| **Run budget** | `startRunBudget()` | Resets wall-clock origin; token/cost budgets carry forward from previous run |
| **Local bare repo** | `setLocalBareRepoPath()` | (Local GitHub mode only) Detects from `<outputPath>/origin.git` or workspace remote URL |

### Token Budget Handling

The previous run may have consumed significant tokens. On continuation:
- Token usage records from `token-usage.json` are loaded into the tracker via `recordFromPreviousRun()`
- `startRunBudget()` reads from the tracker, which already has cumulative totals — so token and cost limits account for the carry-forward spend
- Only the wall-clock budget resets — the continued run gets a fresh time window

The inline `rehydrateSingletons()` function (72 lines) was removed from `run.ts` and replaced with an import from the new module:

```typescript

```

Unused imports were also cleaned up: `path`, `fs`, `setRunLogPath`, `initLedger`, `initResponseLog`, `startRunBudget`, `GITHUB_MODE`, `setLocalBareRepoPath`, `RunInput`, and `ConductorOptions` were removed from `run.ts`.

## Sub-Plan 06: CLI Integration

**Status:** Implemented  
**File Modified:** `src/cli.ts`

### What Was Built

A "Continue a stopped run" option added to the CLI main menu, allowing users to select a previously stopped run, view a reconstruction summary, choose a run mode, and resume execution.

### Menu Change

The main menu was updated from 5 to 6 options:

```
Commands:
  1) Start new run (autonomous)
  2) Start new run (human-in-the-loop)
  3) Maintain existing project
  4) Continue a stopped run        <-- NEW
  5) Show agent roster             (was 4)
  6) Exit                          (was 5)
```

### New Function: `startContinueRun()`

The function implements the full continuation flow as a 5-step interactive process:

**Step 1 — List stopped runs:**
- Calls `listStoppedRuns()` to scan `outputs/` for runs with status `crashed`, `failed`, or `cancelled`
- Displays each run with color-coded status, system name, final phase, timestamp, and workspace path
- Offers a "p) Enter output path manually" option for runs not in the standard outputs directory
- Shows "b) Back to main menu" for easy navigation

**Step 2 — Resolve output path:**
- Accepts numeric selection from the list or manual path entry
- Validates the selected path exists on disk

**Step 3 — Collect and reconstruct with summary:**
- Calls `collectRunState(outputPath)` to gather all artifacts
- Validates workspace exists (fatal error with clear message if not)
- Calls `reconstructState(collected)` to build state and determine resume phase
- Displays a detailed reconstruction summary:
  - System name, run type, resume phase (in green)
  - Confidence level (green/orange/red based on full/partial/minimal)
  - Workspace and output paths
  - List of completed phases and remaining phases
  - Any warnings (in orange)

**Step 4 — Choose run mode:**
- Autonomous or human-in-the-loop
- "b) Back to main menu" option

**Step 5 — Confirm and continue:**
- Shows final summary (system name, resume phase, mode)
- Asks for Y/n confirmation
- Calls `continueRun({ outputPath, mode })`
- For autonomous mode: displays final state summary on completion
- For HITL mode: enters the standard HITL approval loop (approve/deny/enhance/show reports/show state) — same interaction pattern as the existing HITL run flow

### New Imports

```typescript

```

### Error Handling

- Missing workspace → clear error message directing user to restore the workspace
- State collection failure → error with message, return to main menu
- State reconstruction failure → error with message, return to main menu
- Run continuation failure → error with stack trace and partial token report path

## Sub-Plan 07: REST API Integration

**Status:** Implemented  
**File Modified:** `src/index.ts`

### What Was Built

Two new REST endpoints for continuing stopped runs, following the same patterns as the existing `POST /api/run` and `GET /api/runs` endpoints.

### New Endpoints

#### `GET /api/runs/stoppable`

Lists all runs in the `outputs/` directory that are candidates for continuation (status != 'completed'). Returns an array sorted by timestamp descending (newest first).

**Response:**
```json
[
  {
    "outputPath": "/path/to/outputs/run-name-2026-...",
    "systemName": "my-app",
    "timestamp": "2026-08-16T...",
    "status": "crashed",
    "finalPhase": "development",
    "workspacePath": "/path/to/generated-projects/my-app"
  }
]
```

#### `POST /api/run/continue`

Continues a previously stopped run from the last completed phase.

**Request body:**
```json
{
  "outputPath": "/path/to/outputs/run-name",
  "mode": "autonomous",
  "threadId": "optional-thread-id"
}
```

**Response (autonomous):**
```json
{
  "status": "continuing",
  "threadId": "continue-1723...",
  "systemName": "my-app",
  "resumePhase": "qa",
  "confidence": "full",
  "warnings": [],
  "mode": "autonomous"
}
```

**Response (HITL):**
```json
{
  "status": "continuing",
  "threadId": "continue-1723...",
  "systemName": "my-app",
  "resumePhase": "qa",
  "confidence": "full",
  "warnings": [],
  "mode": "human",
  "phase": "qa"
}
```

### Design Decisions

1. **Autonomous mode is fire-and-forget** — same pattern as `POST /api/run`. The response is returned immediately with the reconstruction summary. Results arrive via WebSocket events (`run:complete`, `run:error`).

2. **HITL mode returns a session** — same as `POST /api/run`. The session is stored in the in-memory `sessions` Map and can be driven via the existing `POST /api/run/:id/approve` endpoint.

3. **Validation before invocation** — the endpoint pre-validates `outputPath` existence, collects and reconstructs state, and validates workspace existence before calling `continueRun()`. This provides meaningful 400 errors rather than 500s from deep in the pipeline.

4. **WebSocket events include `continuing: true`** — the `run:started` broadcast includes a `continuing` flag and `resumePhase` so the dashboard can distinguish continuation from fresh runs.


## Sub-Plan 08: Git State Reconciliation

**Status:** Implemented  
**File Created:** `src/conductor/continue/git-reconciliation.ts`  
**Files Modified:** `src/conductor/run.ts`, `src/conductor/continue/index.ts`, `src/config.ts`

### What Was Built

A comprehensive git workspace reconciliation module that verifies and fixes the workspace git state before resuming a continued run. This prevents git-related failures that would otherwise occur when the pipeline tries to create worktrees, branches, or commits on a workspace left in an inconsistent state by a crash.

### Exported API

| Function | Purpose |
|----------|---------|
| `reconcileGitState(collected, state)` | Main entry — runs all checks and fixes, returns a `ReconciliationResult` |

### ReconciliationResult Shape

```typescript
interface ReconciliationResult {
    ok: boolean;
    checks: CheckResult[];
    warnings: string[];
    systemBranch: string;
}
```

Each `CheckResult` contains: `check` (name), `ok` (pass/fail), `details` (human-readable), and optional `action` (what was done to fix it).

### Reconciliation Checks (8 steps)

| # | Check | Fatal? | What It Does |
|---|-------|--------|-------------|
| 1 | `workspace-is-git-repo` | Yes | Verifies workspace exists and contains `.git` |
| 2 | `stale-lock-files` | No | Removes `.git/*.lock` and `.git/worktrees/*/locked` files left by killed processes |
| 3 | `worktree-cleanup` | No | Removes `.worktrees/` and `.worktrees-failed/` directories, runs `git worktree prune` |
| 4 | `system-branch` | No | Detects and checks out the system branch (`project/<slug>`). Falls back to creating a tracking branch from remote or checking out `main` |
| 5 | `clean-working-tree` | No | Auto-commits uncommitted changes with `chore: auto-commit pre-continuation` |
| 6 | `remote-reachable` | No | (Live mode only) Tests `git ls-remote origin` to verify network connectivity |
| 7 | `branch-cleanup` | No | Deletes local branches for merged, open, and failed-salvaged PRs. `unknown` branches are left untouched (conservative) |
| 8 | `remote-sync` | No | Fetches from remote and merges/rebases to sync the system branch. Falls back from merge to rebase if merge fails |

### System Branch Detection

The system branch is detected from multiple sources (in priority order):
1. `state.systemBranch` — set by intakeNode
2. Derived from `input.systemName` via slug convention (`project/<slug>`)
3. Current git branch if it matches `project/*` pattern
4. Fallback to `main`

### Configuration

Three new environment variables added to `src/config.ts`:

| Variable | Default | Description |
|----------|---------|-------------|
| `CONTINUE_TOKEN_CARRY_FORWARD` | `true` | Include previous run's token usage in budget calculations |
| `CONTINUE_GIT_RECONCILE` | `true` | Auto-fix git state issues (worktree cleanup, branch sync) before resuming |
| `CONTINUE_CLOSE_STALE_PRS` | `true` | Close open GitHub PRs from previous run that will be re-dispatched |

When `CONTINUE_GIT_RECONCILE=false`, the entire reconciliation is skipped (returns an immediate success).

### Integration into `continueRun()`

Git reconciliation is called in `run.ts` as step 3b, between singleton rehydration (step 3) and graph invocation (step 4):

```typescript
// ── 3b. Git state reconciliation ─────────────────────────────────────
if (collected.workspaceIsGitRepo) {
    const reconciliation = reconcileGitState(collected, reconstructedState);
    if (reconciliation.warnings.length > 0) {
        for (const w of reconciliation.warnings) continueLog.warn(`  Git: ${w}`);
    }
    if (!reconciliation.ok) {
        continueLog.warn('Git reconciliation completed with issues...');
    }
}
```

The reconciliation is non-blocking: even if some checks fail (except the fatal `workspace-is-git-repo` check), the run continues. Warnings are logged so the user can investigate if issues arise.

### Ledger Integration

A ledger entry of kind `'invariant'` is appended after reconciliation:
```json
{ "kind": "invariant", "id": "git-reconciliation", "phase": "intake", "detail": "git-reconciliation: 7/8 checks passed" }
```

### Stale PR Handling

For live GitHub mode with `CONTINUE_CLOSE_STALE_PRS=true`, the module logs the intent to supersede open PRs but does not directly close them via Octokit — that requires `gitContext` which is only available at the PR workflow level. The PR workflow handles re-creation naturally when development re-dispatches.
