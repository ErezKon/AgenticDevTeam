## Changes Implemented

### Part A: Bug Fixes

#### A1 (P0): Fix `blocksWithTrailingBreakpoint()` — skip thinking blocks

**File:** `src/agents/_shared/prompt-cache.ts`

**What changed:** The function now scans backwards from the end of the blocks array for the last block whose `type` is NOT `thinking` or `redacted_thinking`. Places `cache_control` on that block instead of unconditionally on the last block. Returns `null` when all blocks are thinking blocks, preventing Anthropic API rejection (`Extra inputs are not permitted`).

**Key additions:**
- `THINKING_TYPES` set (`'thinking'`, `'redacted_thinking'`)
- Backward scan loop to find the last non-thinking block
- Function exported for direct unit testing

#### A2 (P0): Track dev agent failures — distinguish crash from completion

**File:** `src/conductor/pr/orchestrator.ts`

**What changed:** Added `failedAgentIds: Set<string>` and `failedAssignmentIds: string[]` tracking. Non-budget catch blocks now add the devId to `failedAgentIds`. After the assignment loop, partial failures are reported with accurate counts instead of the unconditional "All N complete" message. A `branch:partial-failure` event is emitted.

**Also added `hasDevFailures` flag** used by A4 to append a warning section to the PR body listing which agents crashed and which assignments may be incomplete.

#### A3 (P1): Guarantee minimum 1 review iteration

**File:** `src/conductor/pr/review-loop.ts`

**What changed:** The budget check at the start of the review loop now allows iteration 1 to proceed regardless of budget status. Only iteration > 1 breaks on budget exhaustion. This ensures every PR gets at least one review pass before budget-based early termination.

#### A4 (P1): Block PR creation when critical quality gates fail

**File:** `src/conductor/pr/orchestrator.ts`

**What changed:** After the gate repair loop and integrity gate, a new check examines whether critical gates (`typecheck`, `build`) are still failing. If so, PR creation is skipped entirely — the worktree is salvaged and a `PR-GATES-FAILED` placeholder is returned. A `branch:gates-blocked` event is emitted.

Additionally, when `hasDevFailures` is true (from A2), a "Dev Agent Failures" warning section is appended to the PR body listing which agents crashed and which assignments failed.

#### A5 (P1): Propagate scaffold work to feature branches on merge failure

**File:** `src/agents/developers/dispatcher.ts`

**What changed:** When the scaffold branch fails to merge, instead of just logging an error and continuing with `baseBranch`, the dispatcher now:
1. Records `scaffoldFallbackRef = scaffoldBranch`
2. Syncs the workspace to the scaffold branch tip (not `baseBranch`)
3. Uses `scaffoldFallbackRef` as the `baseBranch` for all subsequent non-scaffold `executePRWorkflow` calls

This ensures feature branches are created from the scaffold code even when the scaffold PR doesn't merge cleanly.

### Part B: Task Decomposition + Budget Scaling

#### B1: Update TL prompt to split scaffold into smaller assignments

**File:** `src/agents/team-leader/team-leader.prompt.ts`

**What changed:** Replaced the `<integration_check>` scaffold instructions that told the TL to pack ALL scaffolding into one assignment. The new prompt guides the TL to split scaffold into 2-3 focused assignments:
- **Config & Entry Points** (principal, moderate)
- **Type Definitions & Frozen Data** (senior, simple/moderate)
- **Module Stubs** (junior/senior, moderate, tagged `[STUBS]`)

Each assignment depends on the previous one, all sharing the same scaffold branch.

#### B2: Scope feasibility validation in plan-coverage.ts

**File:** `src/conductor/plan-coverage.ts`

**What changed:** Added two new violation kinds to `CoverageViolation`:
- `oversized-assignment` (major): Flags assignments that are both `complex`/`very-complex` AND have `3d+` estimates
- `agent-overloaded` (major): Flags agents with >6 tasks on a single branch

These trigger the existing TL re-invocation repair loop. The gap prompt builder was also updated to include feedback about oversized and overloaded violations.

#### B3: Per-assignment invocations in orchestrator

**File:** `src/conductor/pr/orchestrator.ts`

**What changed:** The dev agent loop was restructured from per-agent batching to per-assignment invocations:
- Each assignment gets its own invocation with a fresh tool budget
- A crash on one assignment doesn't block others on the same branch
- Commits happen after each assignment (not just on failure)
- Later assignments see files created by earlier ones via refreshed workspace snapshot
- A "Previously Completed Assignments on This Branch" section provides context

Added `topologicalSortAssignments()` helper to respect `dependsOn` ordering within a branch.

#### B4: Complexity-aware budget scaling

**Files:**
- `src/agents/_shared/tool-loop-guard.ts`
- `src/agents/developers/dev-agent.builder.ts`
- `src/conductor/pr/orchestrator.ts`

**What changed:** `resolveToolBudgets()` now accepts an optional `complexity` parameter. Budget multipliers:

| Complexity | Multiplier | Principal turns | Principal writes |
|-----------|-----------|----------------|-----------------|
| trivial/simple | 0.75x | 21 | 23 |
| moderate | 1.0x | 28 | 30 |
| complex | 1.5x | 42 | 45 |
| very-complex | 2.0x | 56 | 60 |

Only `turns` and `writes` are scaled — reads and shell stay at base (rarely the bottleneck). `buildDevAgent()` accepts and forwards complexity. The orchestrator passes each assignment's complexity when building agents.

#### B5: Stub awareness in PR description + reviewer context

**Files:**
- `src/conductor/pr/pr-body.ts`
- `src/agents/_shared/persona.ts`

**What changed:**
- `buildPRDescription()` now detects assignments with `[STUBS]` in the description or chore assignments mentioning "stub", and adds an "Intentional Scaffold Stubs" section to the PR body
- The reviewer persona's `<severity_rubric>` exception was strengthened to reference the PR description's stub section
