## 30-01: Dispatch planning correctness (primary root cause)

### 30-01.1 Outcome

All five goals of the sub-plan are implemented:

- **Only the scaffold branch name makes a branch the scaffold.** `taskType: 'chore'` and the `.some()` fallback are gone.
- **The Team Leader's explicit branches are honoured.** An assignment without a `branchName` follows the first non-scaffold branch of its story. Nothing is moved onto or off the scaffold.
- **Barrier injection never creates cycles.**
  - Every injected edge is checked with `wouldCreateCycle` at assignment and branch level.
  - Wiring work that depends on feature work is a `finalizer`, so no edges are injected for it.
  - Cycles the Team Leader wrote are broken deterministically with Tarjan SCC and reported.
- **Branches dispatch in cross-branch dependency order.** The dispatcher runs a branch DAG layer by layer. A branch starts only after every branch it depends on has finished.
- **A failed branch blocks only its dependents.** This is the new default, `DISPATCH_HALT_POLICY=dependents`. A failed scaffold still blocks everything, because every branch depends on it.

### 30-01.4 Decisions and deviations (please review)

1. **The bootstrap and scaffold injectors are no longer exported.** `isBootstrapAssignment`, `isBootstrapBranch`, `injectScaffoldDependencies` and `injectBootstrapDependencies` are folded into `buildDispatchPlan()`.
   - The new bootstrap-or-finalizer decision needs the dependency graph, and every barrier edge needs the cycle check, so standalone array → array helpers could not stay correct.
   - The tests that used them now assert the same behaviour through the planner.
   - `findOverlappingBranches`, `primaryTaskType` and `collectReviewers` moved as internal helpers. The plan now carries `taskType`, `reviewerAgentIds` and `overlaps` per branch.
2. **`topoSort` is pure.** It returns `{ layers, brokenEdges, warnings }` instead of `Assignment[][]` and does not log. The planner also runs inside `validateAssignmentPlan`, which would otherwise log `[Dispatcher]` errors during the Team Leader phase. The dispatcher logs the plan's broken edges (ERROR for assignment-level, WARN for branch-level) and its warnings.
   - **Cycle-breaking rule.** Every cycle contains a "forward" edge: an assignment waiting for one listed after it. In each strongly connected component, the forward edge whose dependent is listed earliest is removed, then the components are recomputed. This keeps the Team Leader's listing order.
3. **The graph algorithms live in `src/utils/dependency-graph.ts`** because the planner was 654 LOC (over the ~600 limit). Reachability reuses `source-graph.ts`'s `transitiveReachable` rather than adding a copy.
4. **Plan 26 A5 fallback (`off` only).**
   - The plan says to pass `origin/<scaffold>` as the base ref. I pass the scaffold **branch name** as `baseBranch`; `createBranchWorktree` already turns it into `origin/<scaffold>` (`fetch origin <base>`, then `worktree add -b <branch> origin/<base>`).
   - A literal `origin/…` value would break the base fetch and PR creation, which needs a branch name as `base`.
   - The removed part is the `checkout <scaffold>` in the main checkout, as required. `orchestrator.ts` is not in this sub-plan's file list, so no separate start-point parameter was added.
5. **A crashed branch workflow now counts as "did not merge" for the halt policy.** This covers a rejected promise that is not a provider-level failure. The old code applied `strict` only to fulfilled results, so a crash never halted even under `strict`; with `dependents`, a crash must skip the dependents too.
6. **Branches that never really ran also skip their dependents, under `dependents` only.** These are branches deferred by wall-clock admission and branches whose provider failure recovered; they never trigger a halt, as before.
7. **An invalid explicit `branchName` falls back to the story branch, with a warning, instead of throwing.** `assertValidRef` still guards every name. Before, a single bad name (e.g. containing `..`) crashed the whole dispatch, and continue-run would crash again on the same persisted plan. This also means the validator can never crash the Team Leader node.
8. **`mergeGapRepair()` and the one-line change to `planning.ts`.** `planning.ts` is outside the listed files.
   - A `dependency-cycle` repair cannot work by appending assignments: `concat` would add same-id duplicates, and `selectPendingAssignments` keeps the first (cyclic) copy.
   - Only assignments named in a violation's `assignmentIds` (the cycle members) may be replaced. Everything else is still appended, so an accidental id collision cannot overwrite unrelated work.
9. **Finalizer branches.**
   - A finalizer gets only the scaffold barrier edge. No bootstrap edges are injected for it, and nothing waits for it.
   - In layering, a finalizer branch is held back while any non-finalizer branch is ready, which implements "simply runs last".
   - A branch with any finalizer on it has kind `finalizer`. If other work shares that branch, plan coverage reports `finalizer-on-shared-branch` (major), as with us-027.
10. **The bootstrap rule is literal.** Any transitive dependency on non-scaffold work makes wiring a finalizer, including a dependency on another bootstrap assignment.
11. **Overlap detection is limited to same-layer branches.** Branches in different layers already run one after another. Same-layer overlaps produce a warning naming the shared modules.
12. **Smaller fixes made while rewriting the dispatcher:**
    - With concurrency > 1, the old halt `break` dropped later results of the same batch (their PRs were never recorded). All results are now absorbed.
    - The git root comes from `findGitRoot()`. The old `gitExec('rev-parse --show-toplevel')` could return an `Error: …` string that was then used as a path (Rule 19).
    - The high-branch-count warning uses `MAX_BRANCHES` instead of a hard-coded 8.
    - `storyId: ''` (an id dropped by sanitising) is treated as missing, so such assignments no longer all collapse onto one branch.
13. **`dispatch:plan` and `dispatch:skipped-dependents` are priority events** (never evicted), alongside `plan:coverage`.

### 30-01.5 Behaviour changes to be aware of

- **The default policy changed from `strict` to `dependents`** (approved). Runs that relied on `strict` must set `DISPATCH_HALT_POLICY=strict`.
- **Barrier branches block their dependents.** Under `dependents`, a failed bootstrap branch skips every feature branch, as a failed scaffold skips everything, because they wait for it through the barrier. Previously a failed bootstrap only logged a warning when the policy was not `strict`. Nothing waits for a finalizer, so a failed finalizer skips nothing.
- **Branches now wait for their dependencies.** With `SEQUENTIAL_DISPATCH=true` this only reorders the work; with parallel dispatch the critical path gets longer. Both effects were accepted as risks in the plan.
- **Explicit branch names can raise the branch count when the Team Leader splits a story.** `MAX_BRANCHES` in the prompt, `consolidateBranches` and the new `story-branch-split` finding cover this.

## 30-02: Honest branch lifecycle and resumable re-dispatch

### 30-02.1 Outcome

All five goals are implemented:

- **A PR claims only the assignments that actually ran.** `PullRequest.assignmentIds` lists the executed assignments (this round's plus, on a resumed branch, those its commits show as done). Assignments the branch budget never started are returned as `deferredAssignmentIds` and stay pending. ASSIGN-027 can no longer be "completed" without running.
- **No valid output is discarded.** An invocation that crosses `MAX_INVOCATION_INPUT_TOKENS` after a generation produced valid output returns that output with `budgetCapped: true` and does not respawn. `InvocationBudgetExceededError` is thrown only when no generation produced valid output. ASSIGN-021's 134/134-passing output would now have been kept.
- **The merge decision uses fresh evidence.**
  - Gates and the integrity gate re-run when HEAD moved after they last ran.
  - `decideMerge()` gets the review iterations that actually ran.
  - A merge guard blocks the merge unless the PR head GitHub would merge is the local HEAD ("remote head stale").
- **Blocked, open and deferred branches resume from their remote head.**
  - The worktree is created from `origin/<branch>`. The old code reset it to the base.
  - Assignments that already ran are read from the durable-commit subjects and skipped.
  - The latest base is merged in before any dev work, and the open PR is reused.
  - Rounds 2 and 3 of the claudeopus5 run would have pushed fast-forward instead of being rejected.
- **Push failures are never silent.**
  - A non-fast-forward rejection is integrated (rebase, merge as fallback) and retried once.
  - A push that still fails returns `pushed: false`, logs an ERROR and emits `branch:push-failed`. "Branch pushed" is logged only after a successful push.
  - A branch that cannot be pushed before the PR gets no PR, review or merge.

On the claudeopus5 run, the us-027 branch would now behave as follows:
- **Round 1:** ASSIGN-021 keeps its output (budget-capped). The 15-minute flat cap becomes 15 + 6 × 6 = 51 minutes for its 7 assignments. Anything the cap still cuts off is deferred, not marked complete.
- **Round 2:** the branch resumes from `origin/…us-027…` with 021 already done, merges the system branch in, and pushes fast-forward. PR #2 is reused, and it can only merge at the reviewed HEAD.

### 30-02.4 Decisions and deviations (please review)

1. **A failed run is marked in its durable commit and runs again on resume.** The plan says to skip "already-executed" assignments. A run that crashed or hit the ceiling without output is committed as `… (durable commit, failed)`. The parser ignores that subject, so a resumed branch runs those assignments again on top of their partial work, and skips only the successful ones. Without this, a crashed assignment's partial work would be claimed by the resumed PR and never retried. Commits from before this change keep the plain subject and count as executed.
2. **The runner appends to the orchestrator's accumulators** (`BranchAccumulators`) rather than returning its own arrays. The branch cost cap reads `tokenUsage` while the loop runs. With separate arrays, the cost cap would not have seen the loop's spend.
3. **Merge-time blockers now set status `blocked`.** These are: branch not on remote, critical secrets, critical integrity findings, PR identity mismatch and stale remote head. Each one also emits `pr:blocked` and posts a `[BLOCKED]` comment. They used to leave the PR `open`. **Unresolvable base conflicts still leave `open`**, because `detectUnrecoverable()` rule 2 counts open PRs with merge-conflict transcripts (30-05 rewrites that rule). *30-05 rewrote the rule, and these PRs are now `blocked` too (30-05 decision 5).*
4. **`resolveBaseRef()` prefers `origin/<base>`.** This was not a listed step, but resume needs it. The main checkout's local system branch is synced only at the end of a round or after a scaffold merge. Diffs, `executedAssignmentIds`, salvage patches and completion evidence taken against the stale local ref would include other branches' merged work. On a resumed branch that has merged the base in, they would credit it with everything.
5. **A respawned generation whose output does not parse falls back to the last valid generation's output.** This extends "never discard valid output" to the case below the token ceiling.
6. **`runBranchGates()` runs product verification after the quality gates and on every gate run.** Before, it ran before the build, and only on the first run, so a repair or re-run silently dropped the product-verification blocker from `decideMerge`.
7. **The strong fixer commits before running its gates.** Its report then belongs to a known HEAD, and the merge stage reuses it when HEAD has not moved, instead of running the gates a second time.
8. **A gate re-run that throws before the merge decision is a blocker** (`refreshError`). Before, a `null` report passed `decideMerge`. Under `legacy` policy it does not block.
9. **Completion-evidence `filesChanged` uses `git diff --relative`.** The `docs/`/`.agent/` filter compared repo-root paths, so in same-repo projects (`generated-projects/<slug>/docs/…`) it never applied.
10. **`settleCompletion()` counts attempts from merged PR claims** across rounds, including this one. It ignores evidence for assignments that no merged PR claimed, so an assignment that never ran cannot receive an `INCOMPLETE` bug.
11. **A conflict while resuming gives a `blocked` record** (the open PR's number when one is found) plus a salvage export, and no dev work, gates or review for that round.
12. **`deferred` maps to the traceability status `planned-only`, not `blocked`.** The work is unfinished, not blocked. QA's AC-coverage gate (`qa.ts` L412/425 reads the traceability status, not the PR status) therefore raises no AC bug for work that is still pending and will be re-dispatched. `qa.ts` is unchanged.
13. **A deferred branch is not salvaged.** Its executed work is on the remote, and the next round resumes from it.
14. **Transcript wording:** "PR #N created" → "PR #N open for review" (the PR may be reused). The development summary now says "M of N PR record(s) merged"; it used to report every record as merged.
15. **`agent:budget-exhausted` is emitted from `agent-invoke.ts`** whenever any invocation crosses the ceiling: dev, repair, review fix, escalation and strong fixer. The payload has `outputKept`, which tells a budget-capped invocation from an exhausted one. Run diagnosis counts this event, but nothing in `src/` emitted it.

### 30-02.5 Behaviour changes to be aware of

- **Branches get more wall time:** 15 minutes for one assignment, plus 6 minutes for each additional assignment. Set `MAX_BRANCH_WALL_PER_ASSIGNMENT_MS=0` to restore the flat cap.
- **Re-dispatched branches keep their history.** The next round builds on top of the earlier round's commits, reviewed or not. Before, it started again from the base.
- **The manifest's `branchesDeferred` now means "latest PR record is `deferred`".** It used to count zero-output dispatch rounds. The dispatcher's wall-time admission counter keeps its field name (`DispatchResult.branchesDeferred`) but is logged as "not admitted".
- **Merges can now be refused for a stale remote head or a failed gate re-run.** These merges used to go through.
- **More merged work can return to pending** (`INCOMPLETE-*` bugs), bounded by `ASSIGNMENT_MAX_ATTEMPTS`.

### 30-02.6 Follow-ups noticed, not changed

Its `git add .` stages the files that still have conflict markers, which marks them resolved and completes the merge. `listConflictedFiles()` is then empty and the conflict is reported as resolved. This is pre-existing. Resumed branches now call `integrateBase()` before dev work, so this path runs more often. ## 30-03: QA signal integrity

### 30-03.1 Outcome

All five goals are implemented:

- **Karma/Jasmine results are parsed.** A Karma project (`ng test`, `karma` in the script, a `karma.conf.*` file, or a Karma test builder) runs through a wrapper config. The wrapper is written to the run's test-report directory and registers an inline JSON reporter. When that report is missing, the totals and the failed specs are read from the rendered output. Jest is chosen only when the project really has Jest; otherwise the runner is `unknown`.
- **Dependencies are installed before the tests run.** This happens when `node_modules` is missing or stale. Exit 127 reads `command not found: <bin> — dependencies not installed?`.
- **Salvage directories are never treated as product.** `.worktrees-failed` is in `PRUNE_DIRS`, and the secret scan skips it. 30-04's `.worktrees/_failed/` is already covered by `.worktrees`.
- **The smoke test serves the right directory.** It uses angular.json's `outputPath` (`dist/<project>/browser`), else the shallowest directory with an `index.html`. Readiness is any HTTP response, and `GET /` gets an explicit reason.
- **No derived or not-yet-delivered "bugs":**
  - A runner problem is one `QA-runner-error` bug, with each command and its rendered output.
  - `story-untested` applies only to stories with merged work, and only when case names are known.
  - The AC gate is `inconclusive` with no bugs when it cannot measure.
  - `planned-only` criteria raise nothing.
  - A blocked PR is one bug, with its real blockers.

### 30-05.4 Decisions and deviations (please review)

1. **The bug window is a cursor in NEW `state.triageRounds`.** The old filter (`state.bugs` minus `fixedBugIds`) brought back every bug a triage had dropped or absorbed once the absorbing bug was fixed. It also hid regressions, because `fixedBugIds` never forgets. Each round records `{ iteration, bugCursor, bugIds }`. Adding a state channel meant adding `triageRounds: []` to the typed test fixtures.
2. **"Undelivered" requires an assignment.** A story-scoped bug is dropped only while its story has assignments and none of them merged. A story no assignment covers keeps its bugs (AC `missing`), because nothing else would deliver it.
3. **Branch bugs come from the PR history**, not only from the AC gate. The Team Leader sees a blocked PR even when the AC gate did not run or did not fail. The AC gate's `PR-BLOCKED-*` bug wins when both exist, since the ids are the same. A `PR-GATES-FAILED-*` placeholder counts: its executed assignments are skipped on resume, so without a fix assignment it would fail the same way every round. A skipped or push-rejected placeholder does not count, because its assignments simply run again.
4. **Absorption also covers the acceptance gate's restatements** (`ACCEPT-BUILD` while a `GATE-*-build` bug is open, and so on), under the plan's "deduplicate by root cause".
5. **The old rule 2 is replaced, and unresolvable conflicts are now `blocked`.** It matched open PRs against "merge conflicts" transcript lines. Abandonment reads the PR history instead. With rule 2 gone, `merge-decision.ts` treats unresolvable base conflicts like every other merge blocker: status `blocked`, `pr:blocked`, a `[BLOCKED]` comment (30-02 decision 3).
6. **"Open" for rules 4 and 5 means "selected by `selectTriageBugs()`"**, so a bug that the latest evaluation no longer raises is not open. Rule 5 keeps its thresholds (3 bugs, 2 attempts); rule 4 is skipped when the last dispatch round deferred work. At the acceptance gate the window does not yet hold that gate's own `ACCEPT-*` bugs, so rules 4 and 5 normally fire at the next triage.
7. **`bugAttempts` counts first executions** (`newlyExecutedIds()`: claimed this round, never before). A failed assignment that runs again on a resumed branch is therefore not counted a second time, which slightly undercounts.
8. **`Assignment.bugIds` is optional.** When the Team Leader omits it, the open bug ids named in the description are used.
9. **`PullRequest.failedGate` is new (optional)**, since the PR record had no gate output. It holds the first failing step of the last gate run, rendered and summarised, and only on a PR that did not merge.
10. **SCOPE reads `completedAssignmentIds`** (30-03.6's suggested fix), the same mapping QA uses. Two existing tests had been written around the broken SCOPE (`'returns "accepted"…'` expected `rejected`). They now expect `accepted` and `partial`, with executed tests and a merged assignment in the fixture.
11. **QA stamps `state.iteration.bugfix`** on the executed, claimed, gate and invariant reports (30-03.6), and the AC gate gets the same value.
12. **`DispatchResult.providerFailureKind` is gone; `stopReason` carries the provider stop.** A provider stop replaces an earlier stop reason of the same round, so a `pr-creation-failed` stop in a parallel batch cannot hide it.
13. **The PR-creation retry duplicated every PR record** (not a listed step). It returned `[...otherPRs, ...retriedPRs]` to an append reducer. It now returns only the retried records. Abandonment and first executions read this history.
14. **The triage context budget is unchanged** (`CONTEXT_MAX_CHARS`). The source-file list and the assignment list are clipped first.
15. **`blockedPrBug()`'s title** reads "Branch <b> blocked before a PR" when the PR number is 0. The test of the bug id and detail is unchanged.

### 30-05.5 Behaviour changes to be aware of

- **Runs end sooner under `RUN_FAIL_POLICY=halt`.** That happens after two rounds that merged nothing, even with file changes; when an abandoned branch blocks the rest; when a bug-fix round changes none of the open bugs; or when three bugs worked on twice remain.
- **A branch that stayed unmerged for two rounds is not dispatched again in that run.** Neither is any branch that waits for it.
- **The Team Leader gets far fewer bugs** and no bugs about stories whose work is still pending. Its assignments carry `bugIds`.
- **`accepted` is reachable.** SCOPE used to fail for every run with stories.
- **From the first bug-fix round on, executed test failures route QA back to triage again,** and traceability counts executed tests.
- **Unresolvable base conflicts give a `blocked` PR** with a `[BLOCKED]` comment, instead of `open`.
- **The development node logs an ERROR for every round without a merged PR** (a WARN when work was deferred). It used to log only rounds without file changes.

### 30-05.6 Follow-ups noticed, not changed

The triage node's `phase:end` event still says `nextPhase: 'devops'`. A rule for "nothing actionable and nothing pending" would end such runs.
- **The Team Leader can still create work on an abandoned branch.** The dispatcher skips it, so it stays pending, and rule 2 then ends the run.

## 30-06: Tokens A — prompt caching, invocation economics, cost accounting

### 30-06.1 Outcome

All three goals are implemented:

- **The conversation is cached, not just the static prefix.**
  - Anthropic requests use **automatic caching**: a top-level `cache_control`, which moves the history breakpoint forward every turn. It is on by default unless `ANTHROPIC_BASE_URL` is set.
  - The explicit breakpoints on the system message and the task message stay. They are no longer gated on the length of the block they end. The rolling history breakpoint is gone.
  - Behind a proxy, an explicit breakpoint on the last message replaces automatic caching.
  - History compaction is cache-stable (`epoch` mode): every request extends the previous one byte for byte until a recompaction.
- **Invocations are limited by effective tokens, with a soft landing.**
  - Effective input = uncached + 1.25 × cache write + 0.1 × cache read.
  - Once an invocation has spent 350k effective tokens, its next model call can use no tool. The agent returns its JSON, the output is kept as budget-capped, and nothing respawns.
  - `MAX_INVOCATION_INPUT_TOKENS` is now a raw backstop of 1.5M, checked before every call. The strong fixer lands at `STRONG_FIXER_MAX_INPUT_TOKENS` (250k), which is now enforced.
- **Costs are reported correctly.**
  - `claude-opus-5-5` is priced by its longest priced prefix (`claude-opus-5`). A model with no price costs $0, with one warning per run, and is named in the report.
  - Billed cost uses each row's own cache tokens; nothing is spread proportionally. "List price" is the list price, and savings = list − billed.
  - New report cards and counters: effective input, median uncached input per call, tokens on unmerged branches, budget-capped invocations. New tables attribute tokens by development round and by branch.

Expected effect (from the plan, to be measured in 30-08): the junior agents' uncached input per call falls from 8.2k to about 2–3k. Raw "Input Tokens" may rise slightly, because they are now cache reads.

### 30-06.4 Decisions and deviations (please review)

1. **"Withhold tools" depends on the provider.** Anthropic and Google keep the tool definitions and get `tool_choice: 'none'`. OpenAI-compatible models get no tools and no `tool_choice`; before, every provider got an empty tool list together with `tool_choice: 'none'`. On Anthropic the tool schemas head the cached prefix, so dropping them would turn the landing call into a full cache write. OpenAI rejects a `tool_choice` without tools, and not every compatible backend honours `none`. This also changes Plan 22 A4's forced termination, which uses the same helper.
2. **The raw backstop also lands softly.** The plan says `MAX_INVOCATION_INPUT_TOKENS` is "checked on every call". The factory checks it before each call and lands exactly as for effective tokens. `invokeDevAgent`'s post-generation check is unchanged: keep valid output as budget-capped, or throw without it.
3. **An epoch also restarts when the history no longer extends the frozen one** (the anchor message moved), not only when the first message changes. Example: the same agent instance invoked on a fresh thread. Without this, a frozen view could be spliced onto an unrelated history.
4. **The fake fetch is a spy on the global `fetch`**, not `clientOptions.fetch`. `createChatModel()` has no seam for a custom Anthropic fetch, and both SDKs resolve the global `fetch` when the client is built. The spy records only model endpoints; anything else (e.g. tracing) gets an empty 200.
5. **Summary rows are per agent and model** (`byAgent`), so `estimateRunCost()` prices each row exactly. This equals the sum over call records, which a test asserts. The report totals sum per record.
6. **"Budget-capped invocations" counts dev invocations whose output was kept** (`markBudgetCapped` from `invokeDevAgent`). Reviewer and pipeline agents can land too (the event is emitted), but they have no budget-capped outcome, so they are not counted.
7. **`not-attempted` branch outcomes are recorded** (wall-clock admission, recovered provider failure), so tokens a branch spent before a provider failure count as unmerged.
8. **`STRONG_FIXER_MAX_INPUT_TOKENS` already existed** in config and `.env.example` (Plan 24 B2, logged only). It is now enforced as the fixer's soft-landing threshold in effective tokens. No new variable was added.
9. **The rolling breakpoint is deleted, not repaired.** With epochs, automatic caching covers the history, and a rolling explicit breakpoint would only use up the breakpoint budget.

### 30-06.5 Behaviour changes to be aware of

- **Anthropic requests carry a top-level `cache_control`** unless `ANTHROPIC_BASE_URL` is set. If your proxy forwards it, set `ANTHROPIC_AUTO_CACHE=true` explicitly.
- **Invocations end earlier, but without losing work.** A dev invocation lands at 350k effective tokens and returns its JSON, instead of running on to the old 600k raw ceiling and having its output discarded. The raw ceiling is now 1.5M.
- **A landed dev invocation is never respawned**, even when its tool budget is also exhausted.
- **Reported costs drop for cached runs and list prices rise to the real list price.** This affects the HTML report, finalize's usage report, the run diagnosis and the branch cost cap. Heavily cached branches therefore get more headroom under `MAX_BRANCH_COST_USD`.
- **Unpriced models log one WARN per run** and appear in a report banner. They still cost $0.
- **`getRunSummary().byAgent` has one row per agent and model.**
- **The history is no longer rewritten every call**, so a turn can see a few stub-free older results that the sliding window would have stubbed, until the next recompaction.

### 30-06.6 Follow-ups noticed, not changed

- **Invocations and branch outcomes are not persisted.** After a continue-run, the report attributes only the new session's tokens to rounds and branches; the earlier records carry `prev:` invocation ids.
- **Google's `tool_choice: 'none'` path is untested against the real API.** The OpenAI and Anthropic request bodies are covered by the fake-fetch test.
- **Cache TTL.** The 5-minute ephemeral cache expires during a long tool call (e.g. a full test run), and the next call writes again. A 1-hour TTL costs 2× per write; measure in 30-08 before changing.

## 30-07: Tokens B — tool-output hygiene and agent-turn efficiency

### 30-07.1 Outcome

Steps 1–8 and 10 are implemented. Optional step 9 is not, because the plan says to measure first.

- **Clean tool output.** `run_command` output is rendered as a terminal shows it: the 16 kB Karma run is under 2 kB. Long test and build output is cut to its failure blocks and summary lines, then truncated. Commands run with a non-interactive environment.
- **Honest exit codes.** Commands run in `bash -o pipefail -c` when bash exists, and the tool description says so.
- **Gate output.** Gate results store rendered, summarised output. The repair prompt, PR body, strong fixer, gate bugs and gate test report use `summariseTestOutput()`.
- **No read-cache deadlocks.**
  - The read cache belongs to one agent instance, so a fresh agent is never told "unchanged" about a file it never read.
  - A repeat of a read still visible in the history gets a one-line pointer.
  - A read the compactor stubbed runs again and returns its content, never `BLOCKED` and never a `CACHED` stub.
- **Dependencies already installed.** The conductor installs once per worktree. The snapshot says `Dependencies: installed`, and the persona says not to run `npm install` unless a package is added.
- **Batched reads, finish when done.** The persona asks for one turn of independent reads and an immediate final JSON once the tests pass and every AC has a tagged test. The stale layout-linter sentence is gone.
- **Conventions digest.** It keeps only imperative rule lines; with none, only the pointer line remains.

### 30-07.4 Decisions and deviations (please review)

1. **Only test, build and lint commands are summarised**, and not commands that only read files. `cat src/app.test.ts` must keep its head; summarising it would leave only "failure-like" lines and the last five lines.
2. **stdout and stderr are summarised separately**, each with half the budget. Jest reports on stderr and Karma on stdout, and the stream labels stay.
3. **The host's `NODE_ENV` is no longer passed to agent commands.** A production host would otherwise make the agent's `npm install` skip devDependencies. `CI`, `NO_COLOR` and `FORCE_COLOR` are now fixed values, not the host's.
4. **`markFresh()` touches `node_modules/.package-lock.json`** after a successful install. `shouldSkipInstall()` compares mtimes strictly, and `npm install` can write `package-lock.json` after the hidden lockfile. Without the touch, the snapshot would say "not installed" and the gates would install again.
5. **The cache is per agent instance by construction.** The plan asks for "a unique ID per `buildAgent` plus the worktree, scoped per run". A closure owned by the instance gives all three without a registry, and it needs no RunContext scoping because there is no shared state.
6. **The compact-persona length budget in `persona.test.ts` moved from 4100 to 4200 characters.** By hand count, the principal persona is about 4050 after the change (+~140 net), which is too close to the old limit. The "with conventions" budget (5100) is unchanged, because the digest shrank.
7. **The snapshot's package lines are relabelled** `Packages:` / `Dev packages:`, so that "Dependencies:" appears only on the status line. No code parses them.
8. **Pre-install runs for every branch whose worktree has a `package.json`.** That includes resumed branches (after base integration, so a base that changed `package.json` is installed) and maintain mode. Python, Go and other stacks are not pre-installed.

### 30-07.5 Behaviour changes to be aware of

- **Pipelines report failures.** `npm test | tail -20` now exits non-zero when the tests fail, so agents see more honest non-zero exits.
- **Agent commands run in CI mode without colour**, without npm notices, and without the host's `NODE_ENV`.
- **Each branch worktree with a `package.json` gets one install before the first agent runs.** This adds install time per branch but removes the agents' install turns. The gates' install step is then usually skipped as up to date.
- **PR bodies, gate bugs and gate test reports carry summarised failures** rather than head or tail slices.
- **Repeated reads cost one line** while the earlier result is visible, and a stubbed read is served again instead of `BLOCKED`.
- **The conventions digest is shorter.** Files without rule lines (e.g. `TypeScript.md`) contribute nothing.
