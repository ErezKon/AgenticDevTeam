## Sub-Plan A: PR Identity, Worktree Re-entrancy, Fatal Provider Errors (N1, N2, N3)

### A1 — Fix `findExistingPR` bare-head fallback + merge-site guard (N1)

**Status:** Implemented
**File:** `src/conductor/pr-workflow.ts`, `src/utils/github-local.ts`

**Root cause:** `findExistingPR()` had a bare-branch fallback (`pulls.list({ head: branchName })`) that in live GitHub mode returns the full open-PR list unfiltered. `data[0]` silently returned whatever PR was opened first. This attached nine branches to the wrong PR in the pacmanclaude run.

**Changes:**
1. **Head validation loop:** Both the `owner:head` and bare-ref code paths now iterate all candidates and validate `pr.head?.ref === head` before accepting. Mismatches are logged as warnings.
2. **Bare-ref fallback gated on local mode:** The unqualified `pulls.list({ head })` call only runs when `GITHUB_MODE === 'local'` — live GitHub mode never makes this ambiguous call.
3. **`PrIdentityMismatchError` class:** New error thrown when a PR's head doesn't match the expected branch, preventing merge/deleteRef of the wrong branch.
4. **Merge-site guard:** Before `pulls.merge()` and `git.deleteRef()`, asserts `ghPr.head?.ref === branchName`. On mismatch, logs error and sets `prStatus = 'open'` without merging.
5. **Local stand-in extended:** `github-local.ts` `pulls.list` now exposes `head: { ref: pr.head }` on each result, matching the GitHub API shape.
6. **`ghPr` type widened:** The local `ghPr` variable's type now includes `head?: { ref: string }`.

### A2 — Make worktree creation re-entrant (N2)

**Status:** Implemented
**File:** `src/conductor/pr-workflow.ts`

**Root cause:** After a failed branch attempt, the salvage worktree held the branch checked out. On re-dispatch, `git branch -D` failed (branch is checked out elsewhere), then `git worktree add -b` failed ("branch already exists").

**Changes:**
1. **Pre-cleanup scan:** Before pruning, runs `git worktree list --porcelain` and removes ANY existing worktree (including `.worktrees-failed/` salvage) whose branch matches `branchName`.
2. **Branch reuse path:** If `git rev-parse --verify` shows the branch still exists despite deletion attempt, reuses it via `git worktree add <dir> <branch>` (without `-b`) followed by `git reset --hard origin/<baseBranch>` to discard stale commits.
3. **Original path preserved:** When the branch doesn't exist (normal case), the original `-b` creation path runs unchanged.

### A3 — Classify fatal provider failures and stop the run gracefully (N3)

**Status:** Implemented
**Files:** `src/conductor/provider-failure.ts` (new), `src/utils/llm-throttle.ts`, `src/agents/developers/dispatcher.ts`, `src/utils/event-bus.ts`, `src/conductor/nodes.ts`

**Root cause:** A 50-second Anthropic "credit balance is too low" outage produced 22 errors that were swallowed as per-branch failures, destroying 13 of 15 branches in 50 seconds. Provider outages should not consume branch attempts.

**Changes:**
1. **`classifyProviderFailure()`:** New function classifies errors into 6 kinds: `billing`, `auth`, `quota`, `model-not-found`, `transient`, `unknown`. Each kind has `pauseable` and `fatal` flags.
2. **`isProviderLevelFailure()`:** Returns true for billing/auth/quota — these errors should not consume the branch's attempt.
3. **`ProviderRecoveryFailedError`:** New error class for unrecoverable provider failures.
4. **`awaitProviderRecovery()`:** Added to `llm-throttle.ts`. Pauses all LLM traffic with exponential backoff probing (10s initial, 2min max per probe, 15min total ceiling). All concurrent callers block on the same gate.
5. **`createProviderProbe()`:** New function in `llm-throttle.ts` that creates a lightweight probe hitting the provider's `/models` endpoint — replaces the dummy probe callback with a real API reachability check.
6. **Dispatcher integration:** In `runBranches()`, rejected promises are classified. Provider-level failures log a different message ("branch assignments remain pending"), emit `run:paused` event, and trigger `awaitProviderRecovery(createProviderProbe())` for pauseable failures. Fatal errors (`auth`, `model-not-found`) set `providerFailureKind` immediately and stop dispatch. If `awaitProviderRecovery` fails, `providerFailureKind` is set and remaining branches are skipped.
7. **`DispatchResult.providerFailureKind`:** New optional field on `DispatchResult`. `developmentNode` checks it after dispatch completes, and if set, writes a periodic snapshot and returns `{ cancelled: true, _stopReason: 'provider-<kind>' }`. This bridges provider failures to the graph's cancel routing.
8. **New event types:** `run:paused`, `run:budget-stop`, and `run:provider-stop` added to `RunEventType` union. The latter two are classified as priority events for observability.

### D5 — Periodic state snapshots

**Status:** Implemented
**Files:** `src/utils/run-snapshot.ts`, `src/conductor/nodes.ts`

**Root cause:** When budget exhaustion stopped the run before `finalizeNode`, there was no recent `state.json` — the only snapshot was written at finalize time. A mid-phase crash or budget stop left continue-run with stale or missing state.

**Changes:**
1. **`writePeriodicSnapshot(outputPath, state, phase)`:** New function in `run-snapshot.ts`. Writes the full accumulated state to `state.json` and a `latest-phase.json` marker file containing the current phase name.
2. **Node integration:** Every node (except `intakeNode` and `finalizeNode`) calls `writePeriodicSnapshot()` immediately after `emitRunEvent('phase:start', ...)`. This captures the complete state from all previous phases before any new work begins.
3. **Budget-stop snapshot:** `checkBudgetStop()` also writes a periodic snapshot before returning its cancellation update, ensuring the snapshot includes the `_stopReason`.

### D6 — Budget-stop-to-cancellation bridge

**Status:** Implemented
**Files:** `src/utils/run-budget.ts`, `src/conductor/nodes.ts`, `src/conductor/state.ts`

**Root cause:** When the run budget reached the `'stop'` level, `developmentNode` stopped dispatching new work (`allowNewBranchWorkflows = false`) but planning nodes continued executing and consumed additional budget. No mechanism existed to route planning nodes to `finalizeNode` when budget was exhausted.

**Changes:**
1. **`shouldStopRun()`:** New function in `run-budget.ts` that returns `true` when `getBudgetStatus().level === 'stop'`.
2. **`_stopReason` state field:** New `Annotation<string | null>` on `ProjectState` (replace reducer, default `null`). Records why the run was stopped gracefully — e.g. `'budget-exhausted:cost'`, `'budget-exhausted:wall'`, `'provider-billing'`.
3. **`checkBudgetStop(state, phase, logger)`:** New helper in `nodes.ts`. Called at the top of every node (except `intakeNode`, `finalizeNode`, and `acceptanceNode`). If `shouldStopRun()` returns `true`, logs the binding budget limit, emits `run:budget-stop`, writes a periodic snapshot, and returns `{ cancelled: true, _stopReason: 'budget-exhausted:<binding>', phase }`. The graph's existing cancel routing sends this to `finalizeNode`.
4. **Test fixture updates:** All test files with `ProjectState` fixtures updated to include `_stopReason: null` — `acceptance-gate.test.ts`, `e2e-node.test.ts`, `graph-routing.test.ts`, `hitl-graph.test.ts`, `qa-node-resilience.test.ts`, `run-invariants.test.ts`, `architect-node-content-blocks.test.ts`.

### D7 — `budget-exhausted` manifest status and continue-run awareness

**Status:** Implemented
**Files:** `src/utils/run-snapshot.ts`, `src/utils/token-tracker.ts`, `src/conductor/nodes.ts`, `src/conductor/continue/state-collector.ts`, `src/conductor/run.ts`

**Root cause:** `listStoppedRuns()` showed all stopped runs identically — no indication of *why* they stopped. A user continuing a budget-exhausted run didn't know to increase budget limits first. The manifest status was either `'completed'`, `'failed'`, `'cancelled'`, or `'crashed'` — no distinct status for budget exhaustion.

**Changes:**
1. **`ManifestStatus` extended:** `'budget-exhausted'` added to the status union in `run-snapshot.ts`.
2. **`RunStatus` extended:** `'budget-exhausted'` added to the `RunStatus` type in `token-tracker.ts`.
3. **`finalizeNode` logic:** Checks `state._stopReason`. If it starts with `'budget-exhausted'` or `'provider-'`, writes the manifest with status `'budget-exhausted'` instead of `'cancelled'`.
4. **`listStoppedRuns()` updated:** Now reads `_stopReason` from saved `state.json` and includes it as `stopReason` in the returned run information. The CLI and REST API surface this to users.
5. **`continueRun()` updated:** Clears both `cancelled: false` and `_stopReason: null` when resuming a stopped run. Without this, the reconstructed state would have `cancelled: true` and the resumed run would immediately route to `finalizeNode` again.
