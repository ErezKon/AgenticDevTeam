# Product Manager & DBA Tool Loop Guard, Diagram Sanitization, and Doc Auto-Commit Plan

Introduce robust protections against tool-call loops in planning agents, ensure Mermaid diagrams render correctly, and automatically commit/push all non-PR agent mission reports to the system branch.

---

## Context & Current State

Two autonomous CLI runs exposed issues in the planning phases and diagram handling:

1. **Product Manager infinite loop (first run)**
   - PM agent (`product-manager`, model `llama-3-3-70b-instruct`) repeatedly called the `emit_mermaid` tool despite its prompt never requesting diagram generation.
   - Logs showed thousands of input tokens consumed with the same `"System Architecture"` diagram output, until hitting the LangGraph recursion limit.
   - Root causes:
     - PM was wired with the `emitMermaidTool` even though its job is to emit structured stories/tasks, not diagrams.
     - No hard stop when the model ignored loop-guard hints and kept calling the same tool.

2. **DBA infinite loop (second run)**
   - After fixing PM, a similar loop appeared in the DBA phase: `llama-3-3-70b-instruct` repeatedly called `emit_mermaid` with identical arguments for the ERD.
   - The new loop guard logged warnings, but the model ignored the returned error payload and continued the same tool call until recursion-limit.
   - The DB design schema already contains an `erdMermaid` field, so the tool was redundant here as well.

3. **Architect & PM mission reports not committed to project repo**
   - For a new project (`mybasiccalc` / `MyBasicCalc`), architect and PM wrote markdown artifacts under:
     - `generated-projects/<system>/docs/agents/architect-mission.md`
     - `generated-projects/<system>/docs/agents/product-manager-mission.md`
   - These artifacts were not staged/committed/pushed to the GitHub project system branch, despite being important planning outputs and not requiring a PR workflow.

4. **Mermaid diagram rendering issues**
   - The architect’s Mermaid diagram used bracket labels with parentheses:
     - `UI[UI Component (React)]`, etc.
   - Mermaid requires such labels to be quoted: `UI["UI Component (React)"]`, otherwise rendering fails.
   - Similar patterns can appear in codebase analyzer and DBA ERD diagrams.

---

## Design Decisions

| # | Decision | Choice | Rationale |
|---|----------|--------|-----------|
| 1 | PM/DBA diagram generation path | Use structured output fields only (`architecture.mermaidDiagram`, `dbDesign.erdMermaid`); remove `emit_mermaid` from PM & DBA | Simplifies behavior; avoids giving planning agents unnecessary tools that trigger loops |
| 2 | Loop detection behavior | Warn after N identical calls, then hard-fail after a tolerance window | Allows the model a couple of chances to recover before terminating to protect tokens/time |
| 3 | Loop detection scope | Implement in shared agent factory and apply to all tools for all agents | Centralized protection; covers future tools/agents without per-agent changes |
| 4 | Mermaid label safety | Sanitize labels in diagrams at write-time with a small utility | Keeps agent prompts simpler while guaranteeing diagrams render in markdown and docs |
| 5 | Artifact persistence for planning agents | Auto-commit/push architect and PM mission reports directly to the system branch | These docs are authoritative planning artifacts but don’t go through PR; committing them automatically ensures they live alongside code |

### Step 3: Strengthen tool loop guard in agent factory

**File:** `src/agents/_shared/agent-factory.ts`

Changes:
1. Add a shared loop guard around all tools:
   - New helper `withLoopGuard(tools, agentId)` that wraps each `StructuredToolInterface` in a LangChain `tool()` wrapper.
   - Internally tracks recent argument signatures per tool and counts consecutive identical calls.

2. Introduce thresholds:
   - `MAX_REPEATED_TOOL_CALLS = 3` – number of identical calls allowed before returning an error payload.
   - `LOOP_TOLERANCE = 2` – number of additional identical calls allowed after the first warning before hard-failing.

3. Behavior:
   - On each tool call:
     - Compute `argSig = JSON.stringify(args)`.
     - Count how many consecutive history entries match `argSig`.
   - If `repeats >= MAX_REPEATED_TOOL_CALLS + LOOP_TOLERANCE`:
     - Log `factoryLog.error` stating the agent is stuck.
     - Throw an `Error` to terminate the agent invocation, causing the surrounding retry/backoff logic (if any) or conductor node to fail fast instead of burning more tokens.
   - Else if `repeats >= MAX_REPEATED_TOOL_CALLS`:
     - Log `factoryLog.warn` about a loop.
     - Append the signature to history.
     - Return a JSON string:
       - `{ error: "Tool \"<name>\" has been called N times with the same arguments. This indicates a loop. STOP calling tools and produce your final JSON response now." }`
   - Otherwise:
     - Append signature and delegate to `originalTool.invoke(args)`.

4. Integrate into `buildAgent`:
   - Replace direct `tools: cfg.tools` with `tools: guardedTools` where:
     - `const guardedTools = withLoopGuard(cfg.tools, cfg.id);`

Outcome:
- All agents are now protected from pathological tool loops.
- Planning agents with no tools (PM, DBA) incur no overhead.

### Step 4: Add Mermaid label sanitization utility

```ts
export function sanitizeMermaidLabels(source: string): string {
    return source.replace(
        /(\w+)\[([^\]"]*[(){},:;][^\]"]*)\]/g,
        (_match, id, label) => `${id}["${label}"]`,
```

```ts
function commitAndPushArtifacts(
    workspacePath: string,
    commitMessage: string,
    gitContext?: GitContext | null,
    logger?: ReturnType<typeof getLogger>,
): void {
    gitExec(workspacePath, 'add .');
    const status = gitExec(workspacePath, 'status --short');
    if (!status || status.includes('nothing to commit')) return;

    gitExec(workspacePath, `commit -m "${commitMessage}"`);
    const currentBranch = gitExec(workspacePath, 'rev-parse --abbrev-ref HEAD');
    if (currentBranch && !currentBranch.startsWith('Error:')) {
        const pushResult = gitPush(workspacePath, currentBranch, gitContext);
        if (pushResult.startsWith('Error:')) {
            logger?.error?.(`Failed to push artifacts: ${pushResult}`);
        } else {
            logger?.info?.(`Committed and pushed artifacts on ${currentBranch}`);
        }
    }
}
```



## Session 2: Loop Guard Hardening, Reviewer Tool Cleanup, and Full Doc Auto-Commit (2026-08-04)

### Requirements

From analysis of run log `outputs/mybasiccalculator-2026-08-04T12-59-32-138Z/run.log`:

1. **Loop guard `throw` does not terminate agents** — The `throw new Error(...)` in `withLoopGuard` is caught by LangGraph's `ToolNode` and converted to an error `ToolMessage`. The model ignores the error and retries the same tool call, continuing until the recursion limit (150) is reached.
2. **Review all agents for unused/missing tools** — Identify agents that have tools they shouldn't, which contribute to tool loops.
3. **Extend doc auto-commit to all non-PR agents** — DBA, Team Leader, and Codebase Analyzer should commit/push their mission reports to the project's system branch, same as Architect and PM already do.

### Root Cause Analysis

#### Issue 1: Loop guard throw is ineffective (CRITICAL)

LangGraph's `createReactAgent` uses a `ToolNode` that catches ALL errors thrown during tool execution and converts them to error `ToolMessage`s with `status: 'error'`. The model sees this error message, interprets it as a transient failure, and retries the same tool call. This creates an infinite loop:

1. Model calls tool with args X
2. Loop guard detects repeat >= threshold → throws Error
3. LangGraph ToolNode catches Error → creates error ToolMessage
4. Model sees error → calls same tool with args X again
5. Goto 2

Each iteration burns ~229 input tokens + ~171 output tokens. Over 60+ iterations before hitting recursion limit, this wastes 12,000+ tokens per loop occurrence.

**Evidence:** Lines 310–445 of run.log show `principal-frontend-reviewer` looping on `github_post_pr_review` with ERROR logged 60+ times, each time the log says "terminating agent" but the agent continues. Same pattern for `principal-backend-reviewer` (lines 573–707).

#### Issue 2: Reviewer agents have mutating GitHub tools they shouldn't use

Reviewer agents were built with `createGitHubTools(...)` which gives them 6 GitHub API tools including `github_post_pr_review`, `github_create_pr`, `github_merge_pr`, etc. But the PR workflow itself handles posting reviews to GitHub via Octokit. This creates:

- **Duplicate review postings:** The agent posts reviews via its tool, AND the PR workflow posts reviews via its own code
- **Tool loops:** The agent calls `github_post_pr_review`, gets a success response, then calls it again with the same args

The reviewer should only inspect diffs (read-only git tools) and produce structured JSON output. The PR workflow orchestrates all GitHub mutations.

#### Issue 3: QA Lead has `emitMermaidTool` unnecessarily

The QA Lead agent had `tools: [emitMermaidTool]` despite its job being to create a test plan, not diagrams. This is the same class of bug that caused PM and DBA loops — giving planning agents tool access they don't need.

#### Issue 4: DBA, Team Leader, Codebase Analyzer don't commit/push artifacts

While Architect and PM were fixed in Session 1, three other non-PR agents still didn't commit their mission reports to the project system branch:
- **DBA** — writes `dba-mission.md` but doesn't commit
- **Team Leader** — writes `team-leader-mission.md` but doesn't commit
- **Codebase Analyzer** — writes `codebase-analyzer-mission.md` but doesn't commit

#### Issue 5: Dev agent JSON parse failures (noted, not loop-related)

`senior-backend` and `senior-frontend` (model `mistral-small-3-1-24b-instruct-2503`) returned non-JSON output causing "Unexpected token s in JSON at position 0/1" errors. These are model quality issues, not loop bugs.

| # | Decision | Choice | Rationale |

| 6 | Loop guard hard-fail mechanism | Replace `throw` with a "poisoned" flag that blocks ALL subsequent tool calls | LangGraph catches thrown errors; poison flag prevents tool side-effects and minimises token waste |
| 7 | Reviewer tool scope | Remove ALL GitHub tools and mutating git tools; keep only read-only git tools (`git_diff`, `git_merge_base_diff`, `git_log`, `git_current_branch`, `git_status`) | Reviewers produce JSON output only; PR workflow handles GitHub mutations; eliminates the primary source of reviewer tool loops |
| 8 | QA Lead tools | Remove `emitMermaidTool`; set `tools: []` | Same reasoning as PM/DBA — planning agents that produce structured JSON don't need diagram tools |

## Session 3: Per-Type Recursion Limits, Reviewer & Dev Tool Cleanup, Worktree Robustness (2026-08-04)

### Requirements

From analysis of run log `outputs/mybasiccalc-2026-08-04T13-42-05-530Z/run.log`:

1. **Recursion limit of 150 wastes tokens after poison** — After the loop guard poisons all tools at tool call 6, `principal-backend` continued for 144 more iterations (each burning ~215 tokens = 18K+ wasted). `principal-frontend-reviewer` showed the same pattern with `git_diff`.
2. **Reviewer `git_diff` tool is useless** — By the time reviewers run, all code is committed. `git_diff` (unstaged changes) always returns "(no diff)", causing the reviewer to loop calling `git_diff` → `git_merge_base_diff(master)` → `git_merge_base_diff(main)` in cycles.
3. **Dev agents have `emitMermaidTool` unnecessarily** — The `DeveloperOutputSchema` already has a `mermaidDiagram` field; the tool is redundant and creates loop risk.
4. **No `git worktree prune`** — Stale worktree tracking can cause "already checked out" errors when creating new worktrees.
5. **"400 Already borrowed" error not handled** — This non-retriable error (likely LangGraph MemorySaver or LLM API issue) caused fix attempts to fail and waste review iterations.

### Root Cause Analysis

#### Issue 1: Recursion limit too high (CRITICAL)

The single `AGENT_RECURSION_LIMIT = 150` applied to ALL agents. Actual tool usage by agent type:
- Pipeline agents (architect, PM, DBA, TL, QA): 1-5 tool calls
- Developer agents: 10-25 tool calls (write files, git add, commit)
- Reviewer agents: 2-5 tool calls (diff, produce JSON)

With the poison flag kicking in at tool call 6, agents had up to 144 wasted iterations. Each iteration costs ~105-215 tokens (model input/output for the tool call + poison response).

**Evidence:** `principal-backend` poisoned at line 67, continued to line 149 (recursion limit hit at iteration 150). `principal-frontend-reviewer` poisoned at line 211, continued to line 227+ (log truncated).

#### Issue 2: Reviewer `git_diff` causes tool call loops

The `git_diff` tool shows unstaged working-tree changes. Since the PR workflow commits and pushes all code before running reviewers, `git_diff` always returns "(no diff)". The reviewer model (`llama-3-3-70b-instruct`) then cycles through different diff approaches:

1. `git_diff -- src/evaluator/index.js` → "(no diff)"
2. `git_merge_base_diff` with baseBranch="master" → error (no "master" branch)
3. `git_merge_base_diff` with default (main) → returns actual diff
4. Back to step 1 (loop)

The reviewer gets the diff on step 3 but doesn't recognize it has enough information and loops back. The loop guard eventually catches it, but 3-4 wasted cycles per loop is costly.

#### Issue 3: Dev agents with `emitMermaidTool`

Same class of bug as PM/DBA in Session 1. The `DeveloperOutputSchema` already has `mermaidDiagram: z.string().optional()`, so devs can include diagrams in their structured output without a separate tool.

#### Issue 4: Stale worktree tracking

`gitExec` swallows errors (returns `"Error: ..."` string). If `worktree remove` fails silently but the directory is deleted, git's internal worktree list still references it. Subsequent `worktree add -b` fails with "already checked out". No `git worktree prune` was called anywhere in the runtime code.

#### Issue 5: "Already borrowed" non-retriable error

The fix attempt at line 195 failed with `400 Already borrowed`, likely from LangGraph's MemorySaver state management or the LLM API. This error is not a rate limit, so `retryWithBackoff` doesn't retry it, but the review loop continued trying further iterations that would also fail.

### Design Decisions (Session 3)

| # | Decision | Choice | Rationale |
|---|----------|--------|-----------|
| 10 | Recursion limit granularity | Per-type limits: pipeline=15, dev=30, reviewer=15 | Matches actual tool usage patterns; caps token waste after poison to 9-24 iterations instead of 144 |
| 11 | Reviewer `git_diff` tool | Remove from reviewer tool set | Useless for committed code; primary source of reviewer loops |
| 12 | Dev agent `emitMermaidTool` | Remove from dev agents | `DeveloperOutputSchema.mermaidDiagram` field covers this; tool creates loop risk |
| 13 | Worktree robustness | Add `git worktree prune` before worktree creation | Cleans stale tracking entries that cause "already checked out" errors |
| 14 | Non-retriable error handling | Break out of review loop on "Already borrowed" or "recursion limit" errors | Prevents wasting review iterations on errors that won't resolve by retrying |
| 15 | Loop guard total call ceiling | Add `MAX_TOTAL_CALLS = 50` across all tools per agent | Catches cross-tool loops (e.g. cycling between `git_diff` and `git_merge_base_diff`) that evade per-tool consecutive detection |
| 16 | Reviewer tool usage guidance | Add `<tool_usage>` section to reviewer persona prompt | Models (especially llama-3-3-70b-instruct) need explicit instruction to use the inline diff rather than looping on tools |

### Risks & Considerations (Session 3)

- **Recursion limits may be too low for complex tasks:** If a dev agent legitimately needs 30+ tool calls for a large feature (e.g., scaffolding 15+ files), the limit will terminate it prematurely. The env override (`DEV_RECURSION_LIMIT`) provides an escape hatch. Monitor logs and adjust if needed.
- **Removing `git_diff` from reviewers:** If a future workflow has reviewers checking uncommitted changes (e.g., mid-development review), `git_diff` would be needed. Current architecture always commits before review, so this is safe.
- **Total call ceiling (50) is fixed:** The `MAX_TOTAL_CALLS = 50` ceiling in the loop guard is not configurable. If a legitimate agent workflow needs 50+ distinct tool calls, it will be poisoned. This ceiling should be raised if needed (or made configurable via `AgentConfig`).
