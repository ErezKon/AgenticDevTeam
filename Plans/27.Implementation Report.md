## Sub-Plan 27-B: Sequential Branch Dispatch with Halt-on-Failure

### Problem
Dispatcher ran branches concurrently via `MAX_CONCURRENT_DEVS=2`. When the scaffold branch failed, all feature branches ran anyway on a broken base, wasting ~$80 in tokens on doomed branches. The dispatcher only stopped on `pr-creation-failed` status, not on any other failure.

### Changes

| File | Change |
|------|--------|
| `src/config.ts` | Added `SEQUENTIAL_DISPATCH` (bool, default `true`) and `DISPATCH_HALT_POLICY` (enum: `strict`/`scaffold-only`/`off`, default `strict`) |
| `src/utils/event-bus.ts` | Added `dispatch:halted` event type to `RunEventType` |
| `src/agents/developers/dispatcher.ts` | Imported new config vars; added `effectiveConcurrency` (forced to 1 when `SEQUENTIAL_DISPATCH=true`); replaced 3 `MAX_CONCURRENT_DEVS` references with `effectiveConcurrency`; added halt-on-failure check after each branch result that emits `dispatch:halted` and stops dispatch when any non-merged branch is detected (under `strict` policy) or only when scaffold fails (under `scaffold-only` policy) |
| `.env.example` | Documented both new variables with usage examples |
| `AI_Context.md` | Updated event-bus type count (16 -> 17); updated dispatcher description; updated development phase description |

### Design Decisions
- **Reuses `prCreationFailed` flag** to stop dispatch, rather than adding a new flag. This is safe because both paths want the same behaviour: stop dispatching and report what was skipped.
- **`dispatch:halted` event** carries `branchName`, `status`, and `policy` for observability.
- **`scaffold-only` option** is a middle ground for teams that want parallel dispatch for features but still want scaffold failure to stop everything.

## Sub-Plan 27-D: Planning Integrity — TL Truncation & Gap-Repair Context

### Problem
Two interrelated failures:
1. **TL output truncated** at 64,005 tokens (limit: 64,000). Only 8 of 46 assignments survived.
2. **Gap-repair called blind** — `buildCoverageGapPrompt()` sent only violations, no project slug, tech stack, repo contract, or existing assignments. The 38 gap-repair assignments had wrong branch prefixes, wrong agent assignments, oversized branches.

### Changes

| File | Change |
|------|--------|
| `src/config.ts` | Raised `PLANNING_MAX_OUTPUT_TOKENS` from 64000 to 128000 |
| `src/conductor/plan-coverage.ts` | Added `GapRepairContext` interface; updated `buildCoverageGapPrompt` to accept `GapRepairContext` (with backward-compatible legacy signature); enriched gap prompt with project slug, tech stack, repo contract, existing assignments, and existing branches |
| `src/conductor/nodes/planning.ts` | Imported `GapRepairContext`; gap-repair loop now prepares context summaries (project slug, tech stack, repo contract) and passes enriched `GapRepairContext` to `buildCoverageGapPrompt` instead of raw violations |
| `.env.example` | Updated `PLANNING_MAX_OUTPUT_TOKENS` documentation (default 128000) |
| `AI_Context.md` | Updated plan-coverage section; updated planning token ceiling note |

### Design Decisions
- **Backward-compatible signature**: `buildCoverageGapPrompt` accepts both `(violations, nextId)` (legacy) and `(GapRepairContext)` (enriched). This avoids breaking any other callers.
- **Context reuse**: Project slug, tech stack, and repo contract summaries are computed once before the gap-repair loop, then reused across attempts. Existing assignments and branches are recomputed each attempt (they change as gap-repair adds more).
- **128K output token ceiling**: Claude Sonnet 5 supports 128K output. This handles up to ~80-story projects (at ~1500 tokens/assignment).

## Sub-Plan 27-E: Off-Stack Agent Assignment Guard

### Problem
`junior-python` (backend/Python specialist) was assigned to write TypeScript/React code on a frontend-only project. The gap-repair call had no tech-stack context (fixed in 27-D), but the system also lacked a runtime validation guard.

### Changes

| File | Change |
|------|--------|
| `src/conductor/plan-coverage.ts` | Added `off-stack-agent` to `CoverageViolation.kind` union; imported `getDevAgent` from developer registry; added off-stack detection logic in `validateAssignmentPlan` that checks tech stack layers and choices to determine frontend-only vs backend-only projects, then flags junior agents assigned outside their domain; added `off-stack-agent` section to `buildCoverageGapPrompt` output |

### How It Works
1. Collects all tech stack `choice` values and `layer` values from `state.techStack`
2. Determines `hasFrontend` (layer contains 'frontend'/'styling', or choice matches frontend frameworks) and `hasBackend` (layer contains 'backend', or choice matches backend frameworks)
3. For each assignment, looks up the dev agent in the registry:
   - **Backend junior on frontend-only project** (`hasFrontend && !hasBackend`): flagged as `off-stack-agent` (major severity)
   - **Frontend junior on backend-only project** (`hasBackend && !hasFrontend`): flagged as `off-stack-agent` (major severity)
   - **Seniors/principals**: never flagged (cross-domain capable)
   - **Fullstack projects** (`hasFrontend && hasBackend`): no flags (any junior can contribute)

## Sub-Plan 27-F: Comprehensive Ledger & State Saving

### Problem
The ledger had exactly ONE entry (`intake start`) after a 2-hour run. `state.json` was stuck at `phase: team-leader` with `0 PRs, 0 fileChanges`. Middle phases (architect through devops) never called `appendLedger`, and the development phase ran for 2+ hours in a single node execution with only the initial entry-point snapshot.

### Changes

| File | Change |
|------|--------|
| `src/conductor/nodes/_guards.ts` | Added `appendLedger` import; added phase start/end ledger entries in the `phaseNode` decorator — automatically instruments ALL phase nodes (architect, PM, DBA, TL, development, QA, devops, e2e, acceptance-gate) with `kind: 'phase'` entries including `durationMs` on end |
| `src/conductor/pr/orchestrator.ts` | Added `appendLedger` import; added `kind: 'agent'` ledger entries after each assignment completion (outcome: `ok`), budget exhaustion (outcome: `budget-exhausted`), and failure (outcome: `failed`) — records `agentId`, `invocation` index, `filesWritten`, `filesClaimed`, and `error` |
| `src/agents/developers/dispatcher.ts` | Added `writePeriodicSnapshot` import; added periodic state snapshot write after each branch batch result — captures `pullRequests`, `fileChanges`, and `completedAssignmentIds` so `state.json` stays current during long dispatch phases |
| `src/conductor/nodes/planning.ts` | Added `appendLedger` import; added `kind: 'plan-funnel'` ledger entry after `logPlanFunnel()` — records `epics`, `stories`, `criteria`, `tasks`, `assignments`, `unassignedStories`, `unassignedTasks` |

### Design Decisions
- **Automatic instrumentation via `phaseNode` decorator**: All phase nodes get ledger entries without touching each individual file. This is zero-maintenance — new phases automatically get instrumented.
- **Three-outcome agent entries**: `ok`, `budget-exhausted`, and `failed` map directly to the three code paths in the orchestrator's try/catch.
- **Periodic snapshot debouncing**: Uses existing `writePeriodicSnapshot` (30s debounce) so rapid branch completions don't cause excessive disk writes.
- **Plan-funnel entry after validation**: Captures the post-validation state so the ledger shows the actual coverage including gap-repair additions.

## Sub-Plan 27-G: SIGINT-Aware Graceful Shutdown

### Problem
When the user killed the process (`Ctrl+C` / `kill -INT`), the SIGINT handler immediately called `process.exit(130)` after flushing only the token report. It did NOT write `state.json`, flush the ledger, set `_stopReason`, or support continue-run recovery.

### Changes

| File | Change |
|------|--------|
| `src/utils/crash-handlers.ts` | Replaced simple signal handlers with `gracefulShutdown()` function — runs registered hooks, saves state from `RunContext.lastKnownState` with `_stopReason: 'manual-kill'`, writes `invariant` ledger entry, flushes token report. Added `onGracefulShutdown()` hook registration API, `_resetShutdown()` test helper, and double-shutdown prevention flag |
| `src/utils/run-context.ts` | Added `lastKnownState: Record<string, any> | null` field to `RunContext` class; added `setLastKnownState()` exported function that updates the active RunContext |
| `src/conductor/nodes/_guards.ts` | Added `setLastKnownState` import; calls `setLastKnownState(state)` in `phaseNode` decorator before the body executes — keeps the state reference current at each phase entry |
| `src/conductor/run.ts` | Added `getRunContext` and `onGracefulShutdown` imports; registered shutdown hooks in `runAutonomous()`, `runHumanInTheLoop()`, and `continueRun()` that save state with `_stopReason: 'manual-kill'` on SIGINT/SIGTERM |

### Design Decisions
- **Hook-based architecture**: `onGracefulShutdown()` allows any module to register cleanup work without coupling to the signal handler. This is extensible for future needs (e.g., closing database connections, cleaning up worktrees).
- **RunContext-based state access**: `lastKnownState` is stored on the per-run `RunContext` via `setLastKnownState()`. This is safe for concurrent server runs and avoids global mutable state.
- **Double-shutdown prevention**: The `_shuttingDown` flag prevents re-entrant shutdown when multiple signals arrive in quick succession.
- **Best-effort everywhere**: All shutdown operations are wrapped in try/catch to ensure the process exits even if state serialization fails.
- **Three shutdown hooks**: One per run entry point (autonomous, HITL, continue-run). Each hook reads from `RunContext.lastKnownState` which is updated by `phaseNode` at every phase entry.
- **Ledger entry type**: Uses `kind: 'invariant'` (existing type) with `id: 'graceful-shutdown'` rather than adding a new ledger entry kind, keeping the `LedgerEntry` union stable.

### Shutdown Flow

```
SIGINT/SIGTERM received
  -> _shuttingDown = true (prevent re-entry)
  -> Run registered shutdown hooks
  -> Save state from RunContext.lastKnownState with _stopReason: 'manual-kill'
  -> Write 'invariant' ledger entry
  -> Flush token report
  -> process.exit(130 for SIGINT, 143 for SIGTERM, 1 for exceptions)
```

## Risks & Considerations (Plan 27 — Complete)

1. **Sequential dispatch is slower** — A 7-branch run that previously took ~2h with parallel dispatch will take longer sequentially. However, the current parallel approach wastes tokens when early branches fail. Net token spend should decrease.

2. **128K output tokens is expensive** — The TL call with 128K output ceiling will cost more per-token. But it avoids the truncation-gap-repair cascade that wastes a second TL call plus produces lower-quality assignments.

3. **Raised budgets increase per-agent cost** — 45 turns vs 28 turns means ~60% more LLM calls per agent. But this is cheaper than the current pattern of budget exhaustion -> respawn -> re-read everything -> respawn again (which was observed to consume 3-4x the budget of a single well-resourced run).

4. **SIGINT handler may not fire on forced kill** — `kill -9` bypasses all handlers. Users should use `Ctrl+C` or `kill -INT` for graceful shutdown. This is documented in README.md.

5. **Graceful shutdown assumes serializable state** — If the state contains non-serializable objects (functions, circular refs), the snapshot will fail silently (best-effort). This is acceptable because `writeStateSnapshot` already uses `JSON.stringify` with redaction, which handles this case.

6. **`lastKnownState` holds a reference to potentially large state objects** — This is acceptable because only one state exists per run, and the reference is updated (not accumulated) at each phase entry.
