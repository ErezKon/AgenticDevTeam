# Plan 18 — Implementation Report

## Sub-Plan A: Server-Side HITL Event & API Improvements

**Goal:** Make the backend emit the right events and expose the right endpoints so the dashboard can drive HITL sessions.

---

## Changes Made

### 1. Added `hitl:waiting` event type (`src/utils/event-bus.ts`)

Added `'hitl:waiting'` to the `RunEventType` union so it is a recognized, typed event that downstream consumers (event bus listeners, WebSocket bridge) can filter for.

```typescript
export type RunEventType =
    | 'phase:start' | 'phase:end'
    | 'agent:start' | 'agent:end' | 'agent:respawn'
    | 'tool:call'
    | 'pr:opened' | 'pr:reviewed' | 'pr:merged'
    | 'gate:result'
    | 'tokens:update'
    | 'budget:level'
    | 'transcript'
    | 'hitl:waiting';   // <-- NEW
```

### 2. Emit `hitl:waiting` after HITL run start (`src/index.ts`)

After `runHumanInTheLoop()` returns and the session is stored, a `hitl:waiting` event is broadcast via WebSocket immediately after the `run:started` event. This tells the dashboard that a HITL approval is needed for the first phase.

```typescript
broadcast('run:started', { systemName, threadId: session.threadId, mode: 'human' });
// NEW: notify dashboard that HITL approval is needed
broadcast('hitl:waiting', {
    threadId: session.threadId,
    phase: state.phase,
    systemName,
});
```

**Payload shape:**
| Field | Type | Description |
|-------|------|-------------|
| `threadId` | `string` | The run session thread ID |
| `phase` | `string` | The phase awaiting HITL approval (e.g. `'architect'`) |
| `systemName` | `string` | The system name for the run |

### 3. Emit `hitl:waiting` after resume in approve handler (`src/index.ts`)

After `session.resume()` completes in the `POST /api/run/:id/approve` handler, if the pipeline has not reached `'finalize'`, a `hitl:waiting` event is broadcast to notify the dashboard that the next phase needs approval.

```typescript
broadcast('run:phase-complete', { threadId, phase, decision });
// NEW: if not finalized, notify that next HITL approval is needed
if (state.phase !== 'finalize') {
    broadcast('hitl:waiting', {
        threadId: req.params.id,
        phase: state.phase,
    });
}
```

### 4. Added `GET /api/runs` endpoint (`src/index.ts`)

New endpoint that lists all active HITL sessions with their current phase, enabling the dashboard to show an "Active Runs" section.

```typescript
app.get('/api/runs', async (_req, res) => {
    const runs: any[] = [];
    for (const [threadId, session] of sessions.entries()) {
        try {
            const state = await session.getState();
            runs.push({
                threadId,
                systemName: state.input?.systemName,
                phase: state.phase,
                mode: state.input?.mode,
                runType: state.input?.runType,
                cancelled: state.cancelled,
            });
        } catch { /* session may be stale */ }
    }
    res.json(runs);
});
```

**Response shape:** `Array<RunSummary>` where each entry has:

| Field | Type | Description |
|-------|------|-------------|
| `threadId` | `string` | Session thread ID |
| `systemName` | `string` | System name |
| `phase` | `string` | Current pipeline phase |
| `mode` | `string` | Run mode (`'human'`) |
| `runType` | `string` | `'greenfield'` or `'maintain'` |
| `cancelled` | `boolean` | Whether the run was denied/cancelled |

Stale sessions (where `getState()` throws) are silently skipped.

### 5. Updated approve endpoint response with `waiting` flag (`src/index.ts`)

The `POST /api/run/:id/approve` response now includes a `waiting: boolean` field so the dashboard knows whether to show HITL controls for the next phase or a completion summary.

**Before:**
```typescript
res.json({ phase: state.phase, decision: hitlDecision, state });
```

**After:**
```typescript
res.json({ phase: state.phase, decision: hitlDecision, state, waiting: state.phase !== 'finalize' });
```

Added `GET /api/runs` to the file-level JSDoc endpoint list.

## Changes Made

### 1. Created `run-session.component.ts`

The core TypeScript component with full HITL state management and WebSocket integration.

**Key state properties:**
```typescript
threadId: string;           // from route param :id
phase: string;              // current phase waiting for HITL
state: any;                 // full ProjectState from GET /api/run/:id
loading: boolean;           // while approve/resume is in progress
events: WsMessage[];        // live WebSocket events for this run
feedbackText: string;       // textarea for enhance feedback
error: string;              // error message display
completed: boolean;         // true when phase === 'finalize'
activeTab: string;          // which output tab is shown
totalTokens: number;        // derived token stats
totalCalls: number;         // derived LLM call count
budgetLevel: string;        // budget status from WebSocket
budgetUtilisation: number;  // budget percentage
```

**Key behaviors:**

- **`ngOnInit()`**: Reads `threadId` from the route params, calls `refreshState()` to load initial state, subscribes to WebSocket events filtered by `threadId`. Auto-refreshes on `hitl:waiting` and `run:phase-complete` events. Tracks `tokens:update` and `budget:level` events for the stats bar.

- **`refreshState()`**: Calls `GET /api/run/:id`, updates all state properties, derives token stats from `state.tokenUsage`, and auto-selects the best tab for the current phase.

- **`approve()`**: Sends `POST /api/run/:id/approve` with `approved: true`, then refreshes state.

- **`deny()`**: Sends `POST /api/run/:id/approve` with `approved: false` and optional feedback, then refreshes state.

- **`enhance()`**: Validates feedback is non-empty, sends `POST /api/run/:id/approve` with `approved: true` and feedback to trigger a phase re-run, then refreshes state.

- **`visiblePhases`** getter: Returns the pipeline phase list, filtering out `codebase-analyzer` for greenfield runs.

- **`phaseStatus(step)`**: Returns `'completed'`, `'current'`, or `'pending'` based on the step's position relative to the current phase.

- **`availableTabs`** getter: Dynamically builds the tab list based on which state fields have data (architecture, techStack, epics, stories, tasks, assignments, dbDesign, fileChanges, testReports, bugs, pullRequests, devops, raw JSON).

- **`autoSelectTab()`**: Maps the current phase to the most relevant tab (e.g., `architect` → `architecture`, `qa` → `testReports`).

- **`transcriptMessages`** getter: Returns the last 20 transcript messages from `state.transcript`.

## Sub-Plan C: Dashboard API Service & Navigation Wiring

**Goal:** Update the API service to support new endpoints and decision format, wire up navigation so users flow naturally from new-run to run-session, and show active runs on the dashboard home.

## Changes Made

### 1. Updated `api.service.ts` — Decision-based `approvePhase()` + `getActiveRuns()`

Replaced the legacy `approved: boolean` parameter with the decision-based format that matches the server's `{ decision, feedback }` payload. Added the `getActiveRuns()` method to fetch active HITL sessions from the new `GET /api/runs` endpoint (added in Sub-Plan A).

**Before:**
```typescript
approvePhase(id: string, approved: boolean, feedback?: string): Observable<any> {
    return this.http.post(`/api/run/${id}/approve`, { approved, feedback });
}
```

**After:**
```typescript
approvePhase(id: string, decision: 'approve' | 'deny' | 'enhance', feedback?: string): Observable<any> {
    return this.http.post(`/api/run/${id}/approve`, { decision, feedback });
}

getActiveRuns(): Observable<any[]> {
    return this.http.get<any[]>('/api/runs');
}
```

The server's approve endpoint (`POST /api/run/:id/approve`) accepts both formats for backward compatibility, but the dashboard now sends the canonical `decision` format directly, eliminating the ambiguity of mapping `approved: true + feedback` to the `enhance` decision.

### 2. Updated `run-session.component.ts` — Decision-based approve/deny/enhance calls

Updated all three HITL action methods to use the new decision-based `approvePhase()` signature:

| Method | Old Call | New Call |
|--------|----------|----------|
| `approve()` | `approvePhase(id, true)` | `approvePhase(id, 'approve')` |
| `deny()` | `approvePhase(id, false, feedback)` | `approvePhase(id, 'deny', feedback)` |
| `enhance()` | `approvePhase(id, true, feedback)` | `approvePhase(id, 'enhance', feedback)` |

This is semantically clearer — previously `enhance` was indistinguishable from `approve` at the API call level (both sent `approved: true`), and the server had to infer intent from the presence of feedback. Now the intent is explicit.

### 3. Updated `new-run.component.ts` — Post-start navigation to run session

Added automatic navigation to the run session page after successfully starting a HITL run. When the server responds with `mode: 'human'` and a `threadId`, the user is redirected to `/run/:threadId` instead of staying on the new-run form.

```typescript
next: (res) => {
    this.loading = false;
    this.success = true;
    this.threadId = res.threadId ?? '';
    // Navigate to run session page for HITL runs
    if (res.mode === 'human' && res.threadId) {
        this.router.navigate(['/run', res.threadId]);
    }
},
```

**Behavior:**
- HITL runs (`mode: 'human'`): automatically redirects to `/run/:threadId`
- Autonomous runs (`mode: 'autonomous'`): stays on the new-run page showing the success message (no HITL controls needed)
- The `Router` was already injected (used in the constructor) but not used for post-start navigation

### 4. Updated `dashboard.component.ts` — Active runs loading + WebSocket refresh

Added `activeRuns` array property and two data-fetching behaviors:

1. **On init:** Calls `getActiveRuns()` alongside the existing `getAgents()` call to load any active HITL sessions on page load.

2. **On WebSocket events:** When a `hitl:waiting` or `run:started` event is received, refreshes the active runs list. This ensures the dashboard updates in real-time when:
   - A new HITL run is started (from this or another browser tab)
   - A phase is approved and the next phase becomes active
   - A phase completes and the pipeline advances

```typescript
activeRuns: any[] = [];

ngOnInit() {
    this.api.getAgents().subscribe(agents => this.agents = agents);
    this.api.getActiveRuns().subscribe(runs => this.activeRuns = runs);

    this.sub = this.api.connectWebSocket().subscribe(msg => {
        // ... existing event handling ...
        // Refresh active runs on HITL events
        if (msg.event === 'hitl:waiting' || msg.event === 'run:started') {
            this.api.getActiveRuns().subscribe(runs => this.activeRuns = runs);
        }
    });
}
```

## Full User Flow (A + B + C combined)

1. User opens dashboard at `/` → sees Agent Roster, Live Events, and **Active Runs** (if any)
2. User clicks "+ New Run" → navigates to `/new-run`
3. User fills in system name, requirements, selects "Human-in-the-Loop", clicks "Start Run"
4. Server starts HITL session, returns `{ threadId, mode: 'human' }`
5. **Dashboard auto-redirects to `/run/:threadId`** (new navigation wiring)
6. Server broadcasts `hitl:waiting` → run session page auto-refreshes state
7. User sees phase timeline, output viewer, and HITL controls
8. User clicks **Approve** → sends `{ decision: 'approve' }` (new decision format)
9. Phase executes, server broadcasts `run:phase-complete` + `hitl:waiting`
10. Run session auto-refreshes, shows next phase for review
11. User can **Enhance** (with feedback) or **Deny** at any point
12. If user navigates back to `/`, the **Active Runs** section shows the run with a "Review" link
13. On finalize, completion summary is shown with final stats

## Sub-Plan E: Fix HITL Resume (Log Splitting) — Backend Core

**Goal:** Fix the fundamental HITL resume mechanism so the graph properly resumes from checkpoints instead of re-running from `__start__`, and make `intakeNode` idempotent.

---

## Changes Made

### E1. Fixed `resume()` in `run.ts` to use `updateState` + `invoke(null)`

Changed the invocation pattern in both `runHumanInTheLoop` and `resumeRun` inner `resume()` functions across all three decision branches (approve, deny, enhance).

**Before (wrong — re-starts from `__start__`):**
```typescript
const result = await conductor.invoke(
    { approvals: [approval] },
    { configurable: { thread_id: threadId } },
);
```

**After (correct — merges state then resumes from checkpoint):**
```typescript
const config = { configurable: { thread_id: threadId } };
await conductor.updateState(config, { approvals: [approval] });
const result = await conductor.invoke(null, config);
```

**Why this matters:** `conductor.invoke(stateUpdates, config)` is interpreted by LangGraph as a new invocation from `__start__`, which re-runs `intakeNode` from scratch. The correct LangGraph resume pattern is:
1. `conductor.updateState(config, stateUpdates)` — merge approvals/feedback into the checkpoint state
2. `conductor.invoke(null, config)` — resume from the checkpoint without re-starting from `__start__`

**Decision-specific state updates:**

| Decision | State Updates Merged via `updateState` |
|----------|---------------------------------------|
| `approve` | `{ approvals: [approval] }` |
| `deny` | `{ approvals: [approval], cancelled: true }` |
| `enhance` | `{ approvals: [approval], pendingRerun: phase, phaseFeedback: { [phase]: [feedback] } }` |

Applied in both functions:
- `runHumanInTheLoop()` inner `resume()` (with full error handling and crash snapshot logic preserved)
- `resumeRun()` inner `resume()` (the checkpoint-based resume variant)

### E2. Made `intakeNode` idempotent (`nodes.ts`)

Added an early-return guard at the top of `intakeNode` that checks whether the node has already completed. If `state.outputPath` and `state.workspacePath` are both set, intake skips execution entirely.

```typescript
export async function intakeNode(state: ProjectStateType): Promise<Partial<ProjectStateType>> {
    // Idempotency guard: skip if already initialized (prevents re-creation on graph replay)
    if (state.outputPath && state.workspacePath) {
        intakeLog.info('Intake already completed — skipping (idempotent guard).');
        return {};
    }
    // ... rest of intake logic ...
}
```

**Why this matters:** Even though E1 fixes the root cause (resume no longer re-starts from `__start__`), the idempotency guard provides defense-in-depth. If the graph ever replays `intakeNode` for any reason (e.g., a checkpointer edge case), it won't create a new output directory, re-create the GitHub repo, or re-push the system branch.

### E3. Guarded `tokenTracker.reset()` in `intakeNode`

The `tokenTracker.reset()` call at the top of `intakeNode` is now naturally guarded by the idempotency check from E2. Since the guard returns `{}` early when intake has already completed, `tokenTracker.reset()` only executes once — on the first intake invocation. This prevents accumulated token data from being wiped on graph replays.

## Changes Made

### G1. Added `GET /api/run/:id/artifact/:agentId` endpoint (`src/index.ts`)

New endpoint that retrieves a single artifact's content by agent ID. Reads the artifact file from disk using the `filePath` stored in `state.artifacts` and the `workspacePath` as the base directory.

```typescript
app.get('/api/run/:id/artifact/:agentId', async (req, res) => {
    const session = sessions.get(req.params.id);
    const state = session ? await session.getState() : states.get(req.params.id);
    if (!state) { res.status(404).json({ error: 'Run not found' }); return; }

    const artifact = (state.artifacts ?? []).find(
        (a: any) => a.agentId === req.params.agentId
    );
    if (!artifact) { res.status(404).json({ error: 'Artifact not found' }); return; }

    const filePath = path.join(state.workspacePath, artifact.filePath);
    if (!fs.existsSync(filePath)) {
        res.status(404).json({ error: 'Artifact file not found on disk' });
        return;
    }

    const content = fs.readFileSync(filePath, 'utf-8');
    res.json({ agentId: artifact.agentId, title: artifact.title, filePath: artifact.filePath, content });
});
```

**Response shape:**

| Field | Type | Description |
|-------|------|-------------|
| `agentId` | `string` | Agent that produced the artifact |
| `title` | `string` | Artifact title (e.g. "Architect Mission Report") |
| `filePath` | `string` | Relative path within the workspace |
| `content` | `string` | Full markdown content of the mission report |

### G2. Added `GET /api/run/:id/artifacts` endpoint (`src/index.ts`)

New endpoint that lists ALL artifacts for a run, each with its full markdown content read from disk. This is used by the dashboard to load all mission reports in a single request.

```typescript
app.get('/api/run/:id/artifacts', async (req, res) => {
    const session = sessions.get(req.params.id);
    const state = session ? await session.getState() : states.get(req.params.id);
    if (!state) { res.status(404).json({ error: 'Run not found' }); return; }

    const artifacts = (state.artifacts ?? []).map((a: any) => {
        const filePath = path.join(state.workspacePath, a.filePath);
        let content = '';
        try { content = fs.readFileSync(filePath, 'utf-8'); } catch {}
        return { ...a, content };
    });
    res.json(artifacts);
});
```

New function that reads and displays the latest agent's mission report from disk. Called automatically after each phase completes in the HITL loop, before the approve/deny/enhance prompt.

```typescript
function printArtifactReport(state: ProjectStateType): void {
    const latestArtifact = state.artifacts?.[state.artifacts.length - 1];
    if (!latestArtifact || !state.workspacePath) return;

    const filePath = path.join(state.workspacePath, latestArtifact.filePath);
    if (!fs.existsSync(filePath)) return;

    const content = fs.readFileSync(filePath, 'utf-8');
    console.log(`\n${'─'.repeat(60)}`);
    console.log(latestArtifact.title);
    console.log('─'.repeat(60));
    console.log(content);
    console.log('─'.repeat(60) + '\n');
}
```

- Gets the last artifact from `state.artifacts` (the one produced by the most recently completed phase)
